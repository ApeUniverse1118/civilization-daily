【01】案例是什么？（普通人视角）

你公司内网现在大概跑着这些东西：几个用 Dify 或扣子搭的 Agent、十几个从 GitHub 或技能市场装来的 MCP Server 和 Skill、一台跑 Ollama 或 vLLM 的机器、还有一个"便宜的"第三方模型 API 中转。

A.I.G（AI-Infra-Guard）做的事很直白：把这些东西挨个"体检"一遍——这个 MCP Server 有没有后门？这个 Skill 会不会偷偷下载远程脚本、读你的 SSH 密钥？你内网的 vLLM 是不是某个已知 CVE 的受害者？那个便宜的中转 API 是不是"掺水"的模型？体检完给你一份带严重等级和修复链接的报告。

【02】为什么今天值得关注？

因为攻击面在过去一个月里集中爆发，而防守工具刚刚更新了一次。

  • 2026-09-22，Akamai 发布《Beyond Identity: Governing the Agentic Enterprise》，指出恶意 MCP Server 可以通过提示词注入操纵 Agent 决策，且攻击可跨多个已连接的 Server 横向扩散；报告同期的行业数据是：一个月内出现 68 个 MCP Server 相关 CVE，审计发现 91.8% 的 MCP Server 缺少基本认证控制。五眼联盟的 Agentic AI 采纳指南、新加坡的 Agentic AI 治理框架，都已经把最小权限与监控列为基线要求。
  • BlueRock Security 分析 7000+ 个 MCP Server，报告约 36.7% 存在疑似 SSRF 风险；OX Security 在 2026-04-15 披露 Anthropic MCP 参考实现的 STDIO 执行模型在设计上允许任意命令执行，累计影响下载量被报道超过 1.5 亿次。
  • Cisco《State of AI Security 2026》报告称，只有约 29% 的组织准备好了把 agentic AI 投入生产——攻击面在扩，防守能力没跟上。
  • 供给端也在变：2026 年 10 月 1 日 12:09（北京时间），AI-Infra-Guard 发布 v4.6.4，新增了提示词注入研究工具包 pikit（Research/pikit），并修复了 Skill-Scan 的推理强度透传问题。

说白了：以前企业的 AI 安全问题还是"要不要上 Agent"，现在变成了"我内网已经跑着 20 个我不知道能不能信的东西"。这件事第一次有了成熟的开源解法。

【03】案例的前世今生

前世（2019 → 2024）｜从"AI 攻防研究"到"扫公开的 AI Web 组件"
项目出自腾讯安全平台部朱雀实验室（2019 年成立，专注 AI 安全实战攻防）。2024-12-25 开源时，A.I.G 的定位还是一个基础设施漏洞扫描器：那个年代大量 Ollama、ComfyUI、vLLM 实例被直接暴露在公网，很多人把 Ollama 的 11434 端口当成"本地服务"其实全互联网都能访问。A.I.G 做的事就是识别组件指纹、匹配 CVE、告诉你该升级了。它最早的问题不是"Agent 不安全"，而是"AI 服务在裸奔"。

发展（2024 → 2026）｜攻击面每长一层，它就长一个模块
从官方 CHANGELOG 能看到一条非常清晰的能力扩张线：
① Agent 出现（企业开始用 Dify / Coze 编排 Agent）→ 新增 Agent Scan，一个独立的、多 Agent 自动化扫描框架，可对 Dify、Coze 上运行的 Agent 工作流做黑盒安全评估（v4.5.1 加入 5 个 OWASP 检测技能与 Web 数据外传检测）。
② MCP 出现（Agent 开始连外部工具）→ 新增 MCP-Scan，支持源码和远程 URL 两种输入，v4.5.2 加入"动态模式工具白名单防 RCE"，v4.6.1 加入"标记空/不完整扫描结果、上下文压缩时保留安全发现"。
③ Agent Skills 出现（Anthropic Skills 之后，技能变成可分发资产）→ 新增 Skill-Scan + SkillTrustBench，并提出了 T01–T09 九类技能安全风险分类法（指令劫持、记忆投毒、远程载荷下载执行、内嵌恶意代码、提权、系统驻留、工具劫持伪装、不安全依赖、不安全编码）。v4.5.2 加了 .pyc 字节码绕过检测和字符集走私防御，v4.6.2 减少无证据误报。
④ 模型 API 转售出现（"便宜的中转"）→ 新增 模型与 API 中转检测（模型指纹、Claude 签名校验、中转黑盒审计、PAMELA、Ventor QTest），v4.6.0 加入 API 投毒检测。

今生（2026-10-01）｜为什么现在值得关注
v4.6.4 本身是一个小版本，但把它放回上面这条线里看，信号很明确：这个项目的重心已经从"扫基础设施"整体迁移到"扫 Agent 供应链"。新增 pikit 说明它在往"提示词注入"这个最底层的攻击面补研究能力。同时它把能力做成了可以在 CI/CD 里跑的命令行工具（pip install aig-skill-scan）和对 Agent 友好的 ClawHub 技能（clawhub install aig-scanner）——也就是说，安全扫描不再是"上线前找安全部门评估一次"，而是可以塞进流水线、塞进 Agent 自己。

下一步可能怎么发展（分析 / 推演，非事实）
基于已观察到的事实可以推测三条路：① 与企业 CI/CD、镜像仓库、技能市场打通，做"发布即扫描"的准入闸门；② 从"扫描器"演进为"运行时护栏 + 扫描"的组合（README 里已出现 docs/api-checker-integration.md 提到的"Agent 嵌入式运行时架构"，说明运行态是他们在考虑的方向）；③ SkillTrustBench 这类基准可能被安全审计方引用为验收参照，进而把"AI 资产清单"变成合规交付物。以上均为推演，不代表产品路线。

【06】解决了什么真实问题？

从用户与企业的处境说，不是从技术说。今天一个中国企业的技术负责人被问到的问题通常是这样的：

  • "我们内网连了 14 个 MCP Server，谁批准的？每个能读什么数据？"（有没有清单）
  • "同事从技能市场装的那个 Skill，会往外发数据吗？"（技能可信吗）
  • "我们那台 vLLM / Ollama / ComfyUI 有已知漏洞吗？"（组件安全吗）
  • "这个便宜的中转 API，真是它宣称的模型吗？"（有没有掺水）
  • "我们让 Agent 跑了半年业务，出过越权行为吗？"（Agent 本身抗不抗得住）

传统安全工具链不覆盖这一层：漏扫扫的是主机和 Web 应用，SAST 扫的是你写的代码，供应商尽调走不到"第三方 MCP 连接"这一层——这正好是一个供应链盲区。A.I.G 把上面五问压缩成几次点击。

【09】它到底是怎么实现的？

核心是"指纹库 + 规则库 + LLM 语义判定"的三层结构，而不是让模型去"猜有没有漏洞"。这样设计的好处是：确定性的问题（版本号对 CVE）用规则解决，语义性的问题（这段 Skill 指令是不是在劫持 Agent）才交给模型。

  • 基础设施扫描是纯指纹 + 版本比对：连上服务、识别组件与版本、匹配 2000+ CVE 规则。输入是"运行中的网络地址"而不是代码仓库——这是官方 FAQ 特意强调的，也是最容易填错的一栏。
  • Skill-Scan把"技能安全"拆成可分类、可评测的九类风险（T01–T09），这意味着它的判定标准是对外公布、可对标的，而不是黑箱。检测目标包括 .pyc 字节码绕过和字符集走私（v4.5.2 加入）。
  • MCP-Scan最关键的设计是"动态模式工具白名单"：因为 MCP 的本质是"执行 OS 命令"，如果扫描器不加约束地按 MCP 描述去调用工具，扫描行为本身就可能变成一次 RCE。
  • Agent-Scan不走静态分析，而是一个多 Agent 自动化扫描框架：用多个 Agent 去黑盒测试另一个 Agent 的工作流，检测 OWASP 类风险与 Web 数据外传。这是"用 Agent 测 Agent"。
  • API 中转检测（模型指纹 + Claude 签名校验 + 黑盒审计）解决的是一个非常中国的问题：市面上大量"便宜的中转 API"，需要验证它给你的到底是不是它宣称的模型。

所以它"能工作"的原因不是模型强，而是先建规则、再上模型：把已知的、可枚举的风险沉到 YAML 规则库里（社区可通过 PR 贡献 data/mcp/ 规则），把需要语义理解的部分留给 LLM。

【10】手把手复现

以下命令来自官方 README（作者原始步骤），非推导：

# Step 1 · 拉取仓库
git clone https://github.com/Tencent/AI-Infra-Guard.git
cd AI-Infra-Guard

# Step 2 · 用预构建镜像启动（Docker Compose V2+ 把 docker-compose 换成 docker compose）
docker-compose -f docker-compose.images.yml up -d

# 或者：一键安装脚本（会自动装 Docker 并启动）
curl https://raw.githubusercontent.com/Tencent/AI-Infra-Guard/refs/heads/main/docker.sh | bash

# Step 3 · 打开 Web 界面
# http://localhost:8088

# Step 4 · 场景 A：扫本地 vLLM / Ollama 的已知漏洞
#   先正常启动 vLLM，界面点「AI基础设施安全扫描」，
#   目标填 http://127.0.0.1:8000（vLLM 实际监听的 IP:端口），开始扫描
#   批量扫一段网段就填 192.168.1.0/24 或 10.0.0.1-10.0.0.20

# Step 5 · 场景 B：扫一个 MCP Server / Agent Skill（不需要把服务跑起来）
#   目标框填 GitHub 仓库地址，例如 https://github.com/user/mcp-server
#   或直接上传本地源码压缩包

# Step 6 · 把 Skill 扫描接进 CI/CD（可选，命令行）
pip install aig-skill-scan
export LLM_API_KEY="your-api-key"
aig-skill-scan --repo /path/to/your/skill \
           -m deepseek-v4-flash \
           --language zh \
           -o result.json

【12】踩坑

来自官方 README/FAQ 与 CHANGELOG 可确认的点：

  • 最经典的错误：填错扫描目标。基础设施扫描要填"正在运行的 AI 服务的网络地址"，不是 GitHub 链接、也不是源码路径。很多人第一次会把 https://github.com/... 贴进去，然后发现识别不出组件。
  • 扫描需要自备 LLM API Key。Skill-Scan 的语义判定依赖模型（LLM_API_KEY），没有 Key 时能力受限。
  • 不要在公网部署。项目暂无鉴权机制，暴露在公网等于把"内网 AI 资产地图"公开。
  • 误报是需要持续对抗的。v4.6.2 的 release note 本身就在修"减少无证据误报"、"避免流式响应卡死"——说明早期版本有误报和卡死问题，建议直接用最新版。
  • 扫描结果为空要警惕。v4.6.1 专门加了"标记空/不完整扫描结果"的能力，也就是说：扫描没报错不等于扫全了，可能是连接失败。这一点在做安全验收时特别致命。
社区反馈的限制：本次检索到大量以"尧图系"（tzjp.cn / bryh.cn / kwkr.cn / xxmr.cn / mtrt.cn / mhpq.cn / qwbw.cn / pcrn.cn 等）为代表的 SEO 内容农场，批量生产了 Dify、MCP、n8n、ModelScope 等主题的伪教程，内容陈旧且互抄。它们对 A.I.G 的描述与官方 README 并不一致，本报告未采用任何此类来源，全部结论以 GitHub 仓库、Release 页与官方文档为准。

【01】案例是什么？（普通人视角）

一个 n8n 工作流，插到你的收件箱上自动干活：每来一封邮件，先判断它属于哪一类（销售线索 / 客服求助 / 发票账单 / 垃圾邮件），再把关键字段抽出来（姓名、公司、金额、单号、紧急程度、截止日期……）。

然后按类别动作：是销售线索 → 自动生成一封回复草稿发给老板；是高优先级客服 → 发一条告警（Telegram）；是发票或垃圾 → 只记录不打扰。每一封都落一行 CSV（可选写 Google Sheets），最后返回一个运行摘要（处理了多少封、平均耗时）。

模型跑在本机——Ollama 上的 qwen3.5:9b，模型文件约 6.6GB。不花 API 钱，邮件内容也不出本机。

【03】案例的前世今生

前世（规则时代）：收件箱分诊从来不是新需求。最早的解法是邮件规则和关键词黑名单：主题含"发票"就归档，来自某域名就标星，含"退订"就丢垃圾箱。问题是它只能抓字面，抓不了语义——"想问一下你们的报价"是销售线索还是客诉？"这个账单好像不对"是客服还是发票？规则会越写越长、越写越脆，而且完全不能定制业务语义（比如"高价值线索"在你公司到底怎么定义）。

发展（三个改进方向）：LLM 变便宜之后，所有人第一反应是"直接喂给模型分类"。然后撞上三堵墙，而这个项目的历史价值就在于它把三堵墙都记住了：
① 成本与单点故障墙——每一封邮件都是一次 API 调用，量一大就是账单；主模型返回 429/5xx 整个流程直接崩。于是出现"模型级联 / 降级路由"这一派（在 n8n 里做 Claude → GPT-4o → DeepSeek 三级降级，用 Continue On Fail 改错误处理、每次 8 秒超时、失败立刻切换而不是重试）。
② 输出格式墙——模型返回自然语言，下游节点解析不了。于是出现"结构化输出 + Schema 校验 + 失败带错误回灌重试"这一派。
③ 数据出境墙——邮件里有客户信息，很多公司不能发到外部 API。于是出现"本地小模型"这一派。

今生（为什么现在值得关注）：这条路线的三个分支第一次合流了。Qwen3.5:9b 这类 6.6GB 的本地模型，质量已经足够做结构化分类与抽取（评测 98.3%）；n8n 提供了可视化编排 + Code 节点做 Schema 校验 + 方便的降级与重试；两件加起来，把"零 API 成本 + 数据不出本机 + 输出可控"同时做到了。更关键的是作者没有停在"我跑通了"，而是做了 60 封合成邮件的评测集、标了 4 类困难样本（ambiguous 8 封、missing_info 8 封、prompt_injection 4 封、mixed_language 4 封）、跑了 3 轮、写了完整评测报告——这是"能跑"和"可交付"之间的分水岭。

下一步可能怎么发展（分析 / 推演，非事实）：① 按社区反馈补上 per-class 指标与 needs review 队列后，这个模式会更容易被企业接受为"可审计的自动化"；② 路由规则从 n8n 转移到可配置的策略层（而不是硬编码），才能卖给不同行业；③ 本地模型可换成更强的国产模型（Qwen 系列新版本、GLM、MiniMax）或走混合路由；④ 云端收件箱（Gmail）之外，国内更可能是企业微信 / 飞书 / 钉钉 + 企业邮箱的接入方式。以上均为推演。

【06】解决了什么真实问题？

从人的处境开始说。小团队和个体户最典型的一天是这样的：早上打开邮箱，40 封未读，里面有 3 封是真询盘、2 封是客户在发火、1 封是发票要到期、其余是营销邮件。你得先花 20 分钟把它们分开，才能开始干活。而"分开"这件事不需要创造力，只需要判断力——这恰好是模型最擅长、人也最容易疲劳的部分。

企业侧的问题更具体：线索响应时效。跨境询盘从收到到回复超过几小时，成交率就明显下降；而漏掉一封高优先级客诉，代价远大于多处理十封垃圾邮件。所以这个案例真正解决的，不是"AI 很酷"，而是"让每一封有价值的邮件在 2 秒内被识别并推给对的人"。

【09】它到底是怎么实现的？

这个案例的价值几乎全在四个设计决策上，作者在 README 里明确列了其中三条：

  1. 职责分离（原文："The model only classifies and extracts; routing rules live in n8n, not in the prompt"）。模型只做两件事：判断类别、抽取字段。所有"如果是线索就……"的路由逻辑全部写在 n8n 的 Switch 节点里，不写进 Prompt。这一条决定了整个系统能不能维护——改业务规则不需要重调 Prompt、不需要重新评测模型，只改编排图。
  2. 输出 Schema 校验 + 一次性回灌重试（原文："Output is schema-checked and retried once with the error fed back"）。模型输出要过 Code 节点的结构校验；不合法时，把具体的错误信息回灌给模型让它改一次。注意是"1 次"而不是"循环重试"——因为在实时链路上无限重试等于无限等待。校验最终失败就老老实实记 status=error，并且在计算准确率时把它算作错误（作者明确说明），这是一个很诚实的评测口径。
  3. 提示词注入防护（原文："Email content is treated as data"）。邮件正文被当作数据处理而不是指令处理，评测集里专门放了 4 封注入邮件，结果 12/12 通过。注意这是作者自述的评测结果，本次未独立复现。
  4. 可复现的评测管线。npm run eval 会触发 webhook 三次（{"dry_run": true}，跳过回复草稿/Telegram/Sheets），对每次产生的 results.csv 打分，输出 eval/results/ollama.json、eval/report.md 与逐轮 CSV。评测集 60 封英文合成邮件，四类各 15 封，标注在 labels.json，工作流从不读取标注文件——这一点很重要，它排除了"答案泄漏"。

还有一个容易被忽略的工程细节：整个 JSON 输出契约由 LLM 节点保证，跨 provider 一致。因为 ollama 和 gemini 的返回包装格式不同，Schema 校验节点实际上承担了"输出归一化"的职责，让下游 Switch 节点不必关心用哪个模型。这正是"换模型不改下游"的关键。

【12】踩坑

  • 改 .env 后 docker compose restart 无效。README 明确写了：必须重新 docker compose up -d 重建容器，restart 不会重载 .env。这是最常见的"改了配置不生效"。
  • Windows 环境门槛比想象中高。需要 BIOS/UEFI 开虚拟化，并启用 Virtual Machine Platform 与 WSL 两个 Windows 功能；作者给出的快捷命令是 wsl --install --no-distribution（管理员 PowerShell），装完要重启。
  • Gmail 触发器拿到的是 snippet 不是全文。在节点的 simple 模式下，正文是 Gmail 的短摘要，不是完整邮件文本——这会直接影响抽取质量。需要完整正文时要改用 full 格式。
  • 语义类字段是最大的短板。精确字段（姓名、公司、金额、币种、发票号、紧急度、截止日期）准确率 95.6%，但柔性字段（need / topic / budget / timeline）只有 73.3%。评测口径是：need/topic 需要去掉停用词后词集 Jaccard ≥ 0.5 才算对，budget/timeline 需要归一化文本或数字集合完全相等。也就是说——"这封邮件想要什么"和"预算多少"这两件事，9B 本地模型还不可靠，这两栏如果要用在业务上，必须加人工确认。
  • 3 轮评测"完全一致"不等于稳定。作者自己在报告里澄清了：temperature 0 下三次运行返回了完全相同的答案，所以 min/max/mean 相等，但这三次不是独立样本，只能说明结果稳定，不能当作统计置信度。
  • 评测数据的局限要认清。60 封是合成英文邮件（15/15/15/15），中等难度样本包括 ambiguous 8 封、missing_info 8 封、prompt_injection 4 封、mixed_language 4 封（土耳其语/英语混合）。没有中文样本，没有真实业务邮件。
  • Gemini 路径没有基准数据。作者明确写了 gemini 分支"已实现但未做基准测试"。所以"本地模型 vs 云模型"的对比目前无数据可比。
  • 开源版是简化版。README 顶部把"预配置好 Gmail/Sheets/Telegram、附带额外 Prompt 变体与安装指南"的版本放在 Gumroad 上作为 Pro 包——这意味着开源仓储里的一些便利配置是有意留白的。
社区指出但尚未修复的问题（截图时的状态）：① 缺少混淆矩阵与 per-class precision/recall——"总体 98.3%"会掩盖"把真线索误判成垃圾邮件"这种高代价错误；② 缺少 needs review 桶，低置信度邮件应进人工队列而不是被硬塞进四个类别；③ 缺少模型版本 + Prompt/Schema 哈希的记录，导致结果难以真正可复现。作者已公开回应会补齐这三项。截至本报告撰写时未见更新提交。

今日 AI 实战观察

把今天这两个案例放在一起看，能读出一条很清楚的变化：中国 AI 实战的竞争点，正在从"能不能跑起来"转向"敢不敢让它上线"。

案例 01 是防守侧的标志。腾讯朱雀实验室的 A.I.G 从 2024 年底的"扫裸奔的 Ollama 实例"，一路长出 Agent Scan、MCP-Scan、Skill-Scan 三条线，10 月 1 日又在往提示词注入补研究能力。这个扩张轨迹本身就是一份行业病历：攻击面每长一层，它就长一个模块。而它之所以现在值得关注，是因为外部数据已经把风险量化了——一个月 68 个 MCP Server CVE、91.8% 缺基本认证、约 36.7% 疑似 SSRF，同时只有约 29% 的组织准备好把 Agent 投入生产。防守工具第一次不再是"安全团队的内部玩具"，而是有一行安装命令、能进 CI/CD、能装进 Agent 自己的标准件。

案例 02 是进攻侧的标志，也是更值得普通从业者抄的那一个。它的价值不在"邮件分类"这件事，而在四个可以被搬进任何 AI 自动化项目的决定：模型只做分类和抽取、路由规则留在编排层、输出强 Schema 校验加一次回灌重试、外部内容当数据不当指令。前两条决定了系统改业务规则时不用重新调模型；后两条决定了它敢不敢碰真实数据。作者把评测集、评测脚本、混淆矩阵口径全部公开，甚至在 README 里写明"柔性字段只有 73.3%""三次运行不算独立样本"——这种坦白，是"能跑"和"可交付"之间真正的分界线。

还有一个信号值得记下来：9B 级本地模型做结构化任务已经够用了。6.6GB 的 Qwen 在 60 封邮件上拿到 98.3% 分类准确率，把"AI 自动化的边际成本"从 API 账单变成了电费。对预算有限的中小企业和个人开发者，这才是门槛真正下降的地方。

两个案例在同一件事上交汇：一个是"怎么防别人注入"，一个是"我自己先不注入"。当 AI 从聊天走向执行，决定一个项目能否活下来的，往往不是模型能力，而是这些不出现在演示视频里的工程细节。
