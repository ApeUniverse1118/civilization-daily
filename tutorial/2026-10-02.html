01｜案例是什么？

一位后端出身的开发者接了一套企业 AI 客服系统，报价 12 万、承诺 3 周交付。他没有招人，而是把项目切成一块块不超过 2 小时人工工作量的模块，每个模块交给一个并行运行的 AI Agent 实例，用 git worktree 给每个实例一个独立目录和分支，用一张飞书多维表格当任务队列，用 CI 当合并门禁。作者自述开发环节约八成代码由 Agent 完成；10-01 发布的这篇文章，是他对读者提问「你用的什么 Agent」的完整回答——拆开三个实例的上下文、工具与模型分档，并交代哪四类活他一条都没交出去。

02｜为什么今天值得关注？

  • 两篇合起来才闭环：09-30 的前作给商业结果（报价 12 万 / 交付 3 周 / 自己投入 10 天 / 成本 2–3 万），10-01 的这篇给工程细节（worktree 生命周期、乐观锁、心跳超时、CI 门禁）。「结果 + 方法」能同时公开的中文案例并不多。
  • 为什么以前不容易做：单个 Agent 能写代码不稀奇，难的是多个实例同时跑——谁在做哪个任务、任务做废了怎么退、实例崩了谁来收。以前这三件事要自建调度框架，维护成本比写业务还高。
  • 为什么现在变得容易：① 把模块切到「不超过 2 小时人工工作量」之后，验收口变成了单测 + 类型检查这种机器可判定的东西，信任被换成了可验证；② 便宜档模型足够覆盖 CRUD，作者自述一开始全用最强档，几天后发现八成任务根本用不上；③ 一张多维表格 + 几十行轮询脚本就够，不需要工作流引擎。

03｜案例的前世今生

前世。2024–2025 年「AI 写代码」的主流粒度是函数级补全：人是主体，模型是加速器。那时的卡点不是模型不够聪明，而是三件事都缺——没有隔离（多个人或多个 Agent 会互相覆盖文件）、没有验收（改完不知道对不对）、没有回收（分支和临时目录越堆越多）。

发展。① 长上下文与工具调用趋于稳定，模型能自己跑命令、自己读报错；② 终端型 Coding Agent 出现，把「写—跑—改」闭环交回模型自己；③ git worktree 这个 2015 年就有的 git 能力被重新发现——它是最便宜的「一个任务一个完整工作区」，比复制目录干净，比 stash 可控；④ CI 成为机器可判定的门禁，「不绿不合」这句话第一次真正可执行。

今生。案例的作者做了两件关键的选择：把模块切分粒度绑定到「人工 2 小时」而不是「代码行数」，把并发实例数绑定到自己的 review 带宽而不是机器性能。他明确写到：加到第 4 个实例之后，产出不是变快了，而是变成排队等我看，总交付时间一点没少。这是一个来自实践的结论，不是理论推演。

下一步可能怎么发展（分析 / 推演）。任务卡里的「验收标准」会从自然语言描述逐步走向可执行测试；「一个人管 3 个实例」的形态会走向「一个团队共享一张任务表」；这套约束有可能被包装成可复用的交付模板或服务，成为外包公司的方法论资产。以上属于推演，不是作者原文结论。

06｜解决了什么真实问题？

这个案例必须从需求侧理解，而不是从技术侧。

中小软件外包最常见的形态是：一家传统企业要一套管理系统或客服系统，预算 10–20 万，常规工期 1–2 个月，交付方配 4 人（2 后端 + 1 前端 + 1 测试）。客户的痛点是慢、贵、改不动；交付方的痛点是人力被钉死在确定性劳动上——真正的判断题只有一小块（架构、权限、事务边界），其余大量是 CRUD、页面、接口对接、测试用例。

作者的做法就是把这块「确定性劳动」整段交给 Agent，把判断题全部留在自己手里，并用 CI 守住质量底线。他给出的边界也很清楚：这套只适合业务逻辑清晰、CRUD 占比高、且代码能被自动验证的企业应用。

09｜它到底是怎么实现的？

剥开业务内容，这套流程真正的技术内核是三个机制：

机制一：隔离 —— worktree 的生命周期管理。每个任务一个独立目录 + 独立分支，失败直接丢掉整个 worktree，不用回滚主干。作者踩到的两个细节：任务重跑时用 attempt 递增避免撞上旧目录；AGENT_CONTEXT.md 是未跟踪文件，git worktree remove 不带 --force 会被 git 拒绝。更重要的是回收纪律——「一个项目下来累计创建了 300 多个 worktree」，最终合进主分支约 180 个模块（作者自述占累计数六成左右）。

机制二：抢占 —— 状态机要做，但真正的原子手段是乐观锁。任务状态只留五个取值：待分派 → 进行中 → 待评审 → 已验收 / 已阻塞。作者特别指出，状态约束本身是 read-then-write，两个实例同一瞬间读会同时看到「待分派」，挡不住重复领；真正让第二个写失败的是 version 字段——写回时带上读到的 version，与表里一致才写成功，不一致就重读重来。他还点出了一个容易被忽略的竞态源：回收脚本和自己的人工 review 回填也是写者，如果这两个写者不走 versioned write，就可能在实例刚写完结果的瞬间把状态盖掉。

机制三：回收 —— 心跳与超时打回。心跳每 5 分钟写一次，写在单独一个「不抬 version」的字段上；30 分钟没有心跳即自动打回「待分派」，阈值取心跳间隔的 6 倍，任务跑慢一点不会被误杀。轮询间隔放到 60 秒以上，原因是表格没有 webhook，只能定时拉，且要避开接口频次限制。

此外还有一条工程纪律：合并前一律过 CI，单测加类型检查，不绿不合，Agent 写的代码和人写的走同一套门禁。作者认为这才是「敢不敢让 AI 写代码」的真正前提。

10｜手把手复现

以下步骤中，除 Step 0 为本文补充的建议外，其余均整理自作者原文（两篇）中明确给出的做法；作者对自己的示例脚本已注明「按你的项目改」。

Step 0（本文补充的建议）。先确认你的项目能被自动验证：有测试、能本地跑起来、错了当天能发现。没有测试覆盖的老系统，这套流程不适用。

Step 1。项目拆解：每个模块的粒度控制在「你自己写不超过 2 小时」。超过就继续切——这一步同时决定 worktree 的存活时间能不能按小时回收。

Step 2。为每个模块写一张任务卡，落进一张多维表格：任务号、模块名、状态、接单实例、接单时间、心跳、version、attempt、worktree 路径、验收标准、产出分支。

Step 3。批量建 worktree 并注入上下文：给每个实例一份 AGENT_CONTEXT.md，写清本次任务模块、验收标准与硬约束（只改本目录文件 / 接口契约见 docs/api-contract.yaml 不得自改 / 不得改权限判定与事务边界 / 完成后写回任务表且禁止自己点合并）。

Step 4。启动实例：同一时刻最多 3 个（数量按你自己的 review 带宽定），每个实例只在被分配到的 worktree 里干活。

Step 5。写一个几十行的轮询脚本：60 秒以上扫一次表，超过 30 分钟没心跳的任务打回「待分派」。作者强调这个脚本是纯轮询，只做扫表 + 打回，不承担编排职责。

Step 6。合并门禁：走 CI 单测 + 类型检查，不绿不合。

Step 7。合并后立刻回收：git worktree remove --force + git worktree prune。

Step 8。明确划红线：权限判定 / 事务边界 / 幂等设计、架构决策、对外接口契约、不可逆操作（改 schema、删数据、首次上生产）四类不交给 Agent。

Step 9（本文补充的建议）。数据脱敏：客户模块名与验收标准属于交付物，进第三方表格前先替换成模块代号。

12｜踩坑

以下均为作者在原文中自述的踩坑，本文未独立复现：

  • worktree 只建不删，两周就能把磁盘和 git worktree list 拖成一屏屏垃圾——worktree 是完整工作区检出，必须边用边回收。
  • AGENT_CONTEXT.md 未跟踪，git worktree remove 不带 --force 会被 git 拒绝。
  • 状态字段的抢占是 read-then-write，挡不住同一瞬间的重复领；必须靠 version 乐观锁。
  • 没有超时打回，实例崩在中间任务永久卡死，而你看到的还一直是「进行中」。
  • 心跳写结论前要重读一次 version，否则任务跑几十分钟后开局读到的版本号早已过期，每次写回都失败。
  • 全用最强档模型纯烧钱——作者自述八成任务用不上那个能力。
  • 合规细节：客户模块名和验收标准属于交付物，进第三方表格前先脱敏成模块代号。

15｜中国企业可以怎么用？

  • 企业场景 1：中型管理系统的乙方交付。CRM、工单、审批、数据看板这类「判断题只占一小块」的项目，把 CRUD 与后台页面交给 Agent，架构与权限判定留人，用 CI 保证底线。这是案例本身的场景。
  • 企业场景 2：企业 IT 的 backlog 消化。用同一套任务卡机制把内部需求池里的低风险改造（表单调整、报表新增、后台页）批量推进，每个改动都过 CI 门禁；因为改动小、可回滚，风险可控。
  • 企业场景 3：集成商 / 外包公司的产能放大器。同一张任务表管理多个客户项目，按客户隔离 worktree 与知识库；注意作者提的脱敏要求——客户模块名和验收标准不能直接落进第三方表格。

16｜中国消费者可以怎么用？

这个案例本质是 B 端交付流程，对纯消费者的直接适用性有限。但对个人有三个务实用法：

  1. 个人接单者（自由开发者）：把同一套约束搬到自己接的小项目上——后台管理系统、数据看板、门店小程序后台，先开 1 个实例跑通，再逐步加。
  2. 小团队内部工具：把「重复出现的运营小需求」（导出报表、字段调整、页面文案批量改）做成任务卡 + Agent 的固定流程。
  3. 自学者：把这套流程当作真实工程训练场——它训练的不是写代码，而是切分、验收、回滚的工程判断力。

09｜它到底是怎么实现的？

这个案例最值得抄的不是功能列表，而是三个工程决策（均来自 dsh-market 的 README 自述）：

决策一：兼容性「只隐藏确认不匹配的」。插件卡片显示 engines.dsh 或 lockstep @deepseek-ai/dsh-* peers 声明的宿主版本要求；可选的过滤器只隐藏已确认不匹配的条目，未声明版本、格式错误、不可用、只在 GitHub 上的条目仍然可见——而不是替用户「猜它不兼容」。这是一个很克制的产品判断：宁可少过滤，不可误杀。

决策二：更新语义防「静默替换」。从压缩包安装的插件，只会从它自己的来源更新；目录里一个只是同名的条目永远不会被当成它的更新。这正是 v1.66.8 修的问题（PR #770：压缩包安装的更新不再被同名 npm 包整个替换）。对一个「一键安装」的市场来说，这条语义决定了用户敢不敢点更新。

决策三：中国下载区域的 GitHub 路由回退。README 自述：在中国下载区域，Git refs、README 内容、头像各自维护自己的回退顺序，并记住上次可用的路由。这条对国内用户有直接体感——它决定了插件市场在弱网/受限网络下是否可用。

辅助设计：备份还原是 merge 语义而非覆盖（备份之后装的插件不会被清掉），写入前校验、失败回滚；把「我为什么装了这个插件」的备注、分组、收藏都存本地（不发送到任何地方）；未处理的通知可以「本次启动内忽略」，而不是每次刷新都再提醒一次。

15｜中国企业可以怎么用？

  • 企业场景 1：内部工具插件化。把 HR、财务、客服团队反复要用的内部工具做成插件，放进 Harness 分发给全员，替代「每人自己配一遍工具链」。价值在于统一入口与统一版本。
  • 企业场景 2：数据不出本地的桌面 Agent。合同、报价、报表在本地目录里处理，Agent 在本地执行——这是桌面型 Agent 相对云端 Agent 的天然优势，对数据敏感型企业尤其相关。
  • 企业场景 3：把交付物做成插件随交付给客户。软件公司可以把「配置器 / 初始化器 / 数据迁移脚本」做成插件，客户在自己环境里一键装。注意：这意味着要承担插件的兼容性与更新责任。

16｜中国消费者可以怎么用？

  1. 把 Harness 当「能动手的桌面助手」：整理混乱表格、生成可编辑的汇报 PPT、批量处理本地文件（官方宣传与媒体实测均提到这类办公场景；具体效果本文未实测）。
  2. 用社区插件补齐具体能力：按目录里的实际条目选（成本追踪、通知、图像识别等方向），一装一卸都在设置页完成。
  3. 用创造模式把「我每天重复的那件事」做成工具：这是普通人第一次可以不写代码就自造工具——但需要能清楚描述需求与验收标准。

17｜如何变成一个赚钱的项目？

插件产品化。找一个足够窄、足够痛的场景（某个行业的报表口径、某类文件的批处理），做成插件。路径是「免费核心 + 付费增强 / 企业定制」，而不是一上来收费。

企业私有市场。给企业做内部插件目录与治理：谁能装、装哪个版本、怎么回滚、怎么审计。这是 IT 部门的真实需求，也是插件生态里最可能先赚到钱的位置——因为它解决的是责任问题，不是效率问题。

咨询与实施。帮企业把现有内部工具接进 Harness，并做安装安全评估（插件是以本机权限运行的代码）。

培训与内容。面向普通用户的「桌面 Agent 上手」课；面向开发者的「插件开发 + 兼容性声明 + 分发」课。

模板与预设。可移植的 Agent 预设包本身就是一个可分发的商品形态——把「一套能干活的环境」做好，比单卖一个插件更有粘性。

已验证 vs 推导：可核实的只有「插件目录已 4200+」「官方仓库 241,847 Star」「市场 v1.66.8 于窗口内发布」这些事实。以上变现路径均为基于案例结构推导的潜在商业模式，暂无任何收入证据。

19｜如果我是一个中国独立开发者（7 天 MVP）

  • Day 1：装桌面端，让它真实完成一件你的工作（整理一份表格或生成一份 PPT），记录 token 消耗与失败点。
  • Day 2：装 dsh-market，浏览目录，挑 3 个与你日常最相关的插件装上，观察它们解决的是不是你真实的问题。
  • Day 3：用创造模式做第一个插件：解决一件你自己每天重复的事（越小越好）。
  • Day 4：把它打磨到「别人也能装」：写清用途、默认值、最低 dsh 版本要求，处理第一次使用的空白状态。
  • Day 5：确定分发方式（npm 包或 GitHub），写清安装命令；顺手做一次自检——安装时会不会请求超出需要的权限。
  • Day 6：找一个真实用户（同事或社群）试用，只记录一件事：他第一次装失败在哪里。
  • Day 7：决定方向：继续做通用插件（拼分发），还是转做某个行业的私有市场 / 定制（拼交付）。

今日 AI 实战观察

今天这两个案例放在一起看，有一个共同的转向：竞争点从「模型有多聪明」移到了「约束与分发」。

案例 01 里，作者没有回答「你用什么模型」，而是回答「上下文、工具、模型怎么叠」。真正让他敢把约八成代码交出去的，不是模型变强，而是两件很朴素的东西：CI 不绿不合这条机器可判定的门禁，和 git worktree 带来的可回收隔离。他甚至把并发上限从机器能力改判成了自己的 review 带宽——加到第 4 个实例，产出不是变快，而是排队等他看。这句话说明 AI 编程的瓶颈已经不在生成侧，而在验收与回滚侧。

案例 02 里，官方 Harness 的价值也不在模型，而在插件：一个把「能力」变成可安装、可更新、可回滚对象的分发机制。社区市场把 4200+ 个插件收进一个目录，中文媒体转述官方口径称约 60% 的用户使用过第三方插件。这同样是约束与分发的问题——能力一旦可分发，个人开发者才第一次有了产品化的可能。

更值得注意的是两边的「不做什么」都写得很清楚：一边列出四类绝不交给 Agent 的活（权限判定、架构决策、对外契约、不可逆操作），一边给插件加上兼容性声明、更新语义和安全提醒。这种克制不是保守，恰恰是这两套东西能进入生产的原因——先写清楚边界，再谈自动化。

对个人开发者来说，这落到两件具体的事上：把交付切成可验证的小块，以及把重复劳动做成可分发的插件。两件事的门槛都不高，但都需要先承认一件事——人不再负责产出，人负责验收。

今日「个人变现机会」

如果一个人每天投入 2–4 小时，今天这两个案例分别对应一条路径：

路径 A（交付侧，源自案例 01）。用「任务卡 + worktree + CI 门禁」的约束，接 1–2 万元级的小型管理系统 / 数据看板。关键建议：先只开 1 个 Agent 实例跑通，再考虑加第二个——因为你的 review 带宽才是真上限。省下的时间不是用来接更多单，而是用来沉淀验收标准库。
