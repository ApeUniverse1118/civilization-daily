01

Datawhale All-in-RAG 新章节：用 LangGraph 手写一个"规划—检索—评估—改写"的 Agentic RAG

AI Agent / RAG 📌 值得收藏 🎓 值得培训 🇨🇳 国产教程 🔓 开源项目 🧑‍💻 开发者向 2026-09-28 前后发布
一句话摘要：Datawhale《RAG 技术全栈指南》第 7 章第 2 节，带可运行代码把传统 RAG 改造成能自己规划查询、评估检索质量、失败重写的自主检索 Agent。

原始资料

  • 作者原文GitCode 博客：Datawhale All-in-RAG 实战 —— Agentic RAG 架构解析与基于 LangGraph 的最小实现
  • 项目 Repogithub.com/datawhalechina/all-in-rag（配套代码在 code/C7/agentic_rag/）

作者是谁

Datawhale（国内最大的开源学习社区之一）All-in-RAG 教程项目组，由社区贡献者以 AtomGit 账号发布在 GitCode 博客。属于教程作者本人发布的一手内容。

教程讲了什么

文章先指出传统 RAG"一次检索、一次生成"的四大局限：无检索质量感知、无法动态调整策略、无工具选择能力、信息融合浅层。随后给出 Agentic RAG 的四大核心能力——查询规划、检索决策、质量自评、迭代改写，并基于仓库 code/C7/agentic_rag/ 中的 LangGraph 完整实现，逐节点拆解状态图、提示词设计与条件路由逻辑，最终跑通一个具备"规划—检索—评估—改写—生成"闭环的自主检索 Agent。

为什么值得收藏

市面上的 RAG 教程大多停在"接个向量库就完事"，这篇是目前中文世界里少见的、把"检索质量自评 + 失败自动改写重查"工程化讲透的教程，且代码就在官方仓库里可以直接跑。学会它等于掌握了把任何 FAQ 问答机器人升级成"会自己判断答案靠不靠谱"的检索系统的方法。

技术栈

模型OpenAI 兼容接口（可替换为 DeepSeek / Qwen / GLM 任意兼容端点）
工具/框架LangGraph（状态图编排）、LangChain、向量检索（项目内置）
语言Python
代码位置all-in-rag 仓库 code/C7/agentic_rag/
部署环境本地 Python 环境即可，无需 GPU（调云端 API）

完整 Workflow

输入：用户提问
↓
规划节点：LLM 拆解问题，生成检索计划 / 改写查询
↓
检索节点：向量库 top-k 召回相关文档片段
↓
评估节点：LLM 判断检索结果是否相关、是否足够回答
↓
条件路由：质量不合格 → 回到"改写查询"再检索；合格 → 进入生成
↓
生成节点：LLM 基于合格上下文生成最终答案 → 输出

手把手复现

  1. 克隆仓库：git clone https://github.com/datawhalechina/all-in-rag.git
  2. 进入 code/C7/agentic_rag/ 目录，按章节 README 安装依赖
  3. 在环境变量中配置 OpenAI 兼容的 API Key 与 base_url（国内可直接填 DeepSeek 或通义千问的兼容端点）
  4. 先跑通最小示例，观察状态图中"评估→改写"循环何时被触发
  5. 把示例知识库换成自己的文档集合，调低评估阈值观察重写次数变化

关键设计点

教程的核心不在代码量，而在两个提示词：评估提示词（让 LLM 给检索结果打相关性分数并说明理由）和改写提示词（基于"为什么不合格"生成下一轮查询）。条件路由边的阈值决定了系统在"答得不准"和"无限重查"之间的平衡点——这是最值得动手调的部分。

踩坑与注意事项

注意：① 评估节点本身也是 LLM 调用，知识库小时开 Rerank/评估反而更慢更贵，几十条文档的场景不必上完整闭环；② 一定要给改写循环设最大次数上限，防止检索永远不合格时死循环烧钱；③ 评估提示词里要求"输出结构化分数"比让模型自由发挥稳定得多。

普通人能不能复现

⭐⭐ 有基础用户可复现

需要：Python 基础、一个国产大模型 API Key（DeepSeek/通义均可，按量计费成本极低）、无需 GPU、无需付费软件。

国内替代方案

原文模型层走 OpenAI 兼容协议，国内用户把 base_url 换成 DeepSeek（api.deepseek.com）、通义千问（dashscope 兼容模式）或智谱 GLM 的兼容端点即可，代码无需改动——这正是该教程对国内读者最友好的一点。

如何迁移到其他场景

企业知识库客服把"评估—改写"闭环接到公司产品文档库，检索不到政策原文时自动换问法，而不是硬答。
法律 / 医疗文献检索对准确性要求极高的场景，用评估节点强制"引用必须来自检索结果"，降低幻觉。
电商售后工单工单问题先经 Agentic RAG 查售后政策，查不到可靠依据自动转人工，天然形成兜底。
培训师点评：这篇教程真正值得教的不是 LangGraph 语法，而是"让系统自己判断答案靠不靠谱"这一工程思想。评估节点和改写提示词是整套系统的灵魂，讲课时 80% 时间应该花在阈值和提示词调参上，而不是画图。

智谱官方 Build Log：用 GLM-5.3 驱动 Infra Agent，两周把自己的推理基础设施优化到 3 倍吞吐

AI Agent / 工程实践 📌 值得收藏 🧩 值得迁移 🇨🇳 国产模型 🧑‍💻 开发者向 2026-09-28 前后发布
一句话摘要：智谱公开如何用自家模型驱动的 Infra Agent 自动优化推理引擎，把 GLM-5.3-Flash 从模型适配推进到生产可用只用了不到两周，并给出三条可照搬的"反馈设计"原则。

原始资料

  • 官方博客Z.ai 博客《Toward Recursive Self-Improvement: How GLM Built Its Own Inference Infrastructure》（经技术媒体转述核实存在）
  • 媒体转述bpdata：Zhipu AI used GLM-5.3 to automate parts of its own infrastructure development
  • 相关官方页GLM-5.3 技术报告（z.ai/blog/glm-5.3）

作者是谁

智谱 AI（Zhipu AI / Z.ai）官方工程团队，属于基础设施优化的当事方自述，一手程度最高。注意：文中性能数据均为官方自述，第三方无法独立复现验证。

教程讲了什么

智谱搭建了一个由"工程师 + Infra Agent + 实验环境"组成的优化闭环：工程师定义目标和系统边界，GLM-5.3 驱动的 Infra Agent 负责分析、提出假设、给出代码修改，实验环境提供分层、及时、可验证的反馈。官方自述：闭环运转后 GLM-5.3-Flash 从初始适配到生产可用不到两周，最终端到端吞吐达到初始基线的 3 倍（该数据来自官方自述）。

技术栈

模型GLM-5.3（智谱自研，驱动 Infra Agent）
系统角色工程师（定义目标与边界）＋ Infra Agent（分析/假设/改码）＋ 实验环境（反馈）
优化对象推理基础设施（引擎启动参数、Kernel、线程、执行间隔、代码路径）
产出GLM-5.3-Flash（更快更低成本的变体，官方称两周内生产可用）

完整 Workflow

工程师：定义优化目标（吞吐/延迟）与系统边界（允许改什么）
↓
Infra Agent（GLM-5.3）：分析现状 → 提出假设 → 生成代码修改
↓
实验环境：分层验证（参考实现对比、测试结果、可对比的实验指标）
↓
反馈回环：反馈足够局部、廉价、客观 → Agent 快速修正方向，进入下一轮
↓
输出：验证通过的性能优化合入，GLM-5.3-Flash 达到生产标准

关键方法：反馈设计三原则（可直接照搬）

  1. 反馈必须足够局部：把反馈绑定到具体的引擎启动参数、代码改动、Kernel 状况、输入配置、线程、执行间隔或代码路径上，Agent 才能缩小问题范围。
  2. 反馈必须廉价且及时：验证周期越短，Agent 越快修正方向，在无效假设上浪费的工作量越少。
  3. 反馈必须客观可验证：改动是否正确、性能是否提升，必须由参考实现、测试结果和可对比的实验指标判定，而不是由人或模型"感觉"。

踩坑与注意事项

注意：① "3 倍吞吐""两周上线"均为智谱官方自述，外部无法独立验证，引用时请保留"官方称"；② 这套方法的前提是团队已经有完善的测试与基准体系——没有客观度量，Agent 优化就是瞎猜；③ 智谱自己也强调：人类在高层设计决策上仍有比较优势，Agent 负责的是"边界内的执行"。

如何迁移到其他场景

数据库 / SQL 调优Agent 改索引与查询，CI 里跑固定基准查询集，执行计划与耗时即客观反馈。
前端性能优化Agent 改打包配置与代码，Lighthouse CI 分数作为可验证指标，形成自动优化循环。
提示词 / 工作流调参Agent 改 Prompt，离线评测集打分作为反馈——本质是同一个闭环换了个优化对象。
培训师点评：这篇 Build Log 最值得教的是"先建度量，再放 Agent"。多数团队引入 AI 编程失败，不是模型不行，而是没有局部、廉价、客观的反馈。这三条原则是检验任何 Agent 自动化项目能否落地的试金石。

Hermes Agent 完全上手指南：一条命令装一个会自己写技能、越用越懂你的开源个人智能体

Open Source / AI Agent 🔥 值得马上实践 🧪 值得实验 🔓 开源项目 🧑‍💻 开发者向 指南为 2026 年 9 月新版
一句话摘要：Nous Research 开源的本地优先个人 Agent，带持久记忆和"自动沉淀技能"的学习循环，原生支持 GLM / Kimi / MiniMax / Ollama，一条 curl 命令装完。

原始资料

  • 上手指南Hermes Agent: The Complete Beginner's Guide (Sep 2026)
  • 项目 Repogithub.com/NousResearch/hermes-agent
  • 官方文档hermes-agent.nousresearch.com/docs

教程讲了什么

指南系统讲解了这个项目的核心主张——Harness Engineering：2026 年的关键不是更聪明的模型，而是模型外面更聪明的"套壳"（指令、约束、反馈、记忆、编排五层）。Hermes 常驻在你的电脑或 VPS 上，跨会话记忆，每完成复杂任务就自动把经验写成一个可复用的 Skill（markdown 文件），并通过 CLI / Telegram / Discord / 邮件等 14+ 渠道触达你。

技术栈

模型任意 OpenAI 兼容端点；原生支持 Anthropic、OpenAI、MiniMax、Kimi/Moonshot、z.ai/GLM、OpenRouter（200+ 模型）、本地 Ollama
工具40+ 内置工具、Skill 系统（~/.hermes/skills/）、cron 定时、MCP Server 入口、Telegram/Discord/Slack/邮件网关
语言Python（uv 管理，需 Python 3.11）
部署环境Linux / macOS / WSL2 / Termux（不支持原生 Windows）；MIT 协议

手把手复现

# 1. 安装（Linux / macOS / WSL2 / Termux）
curl -fsSL https://raw.githubusercontent.com/NousResearch/hermes-agent/main/scripts/install.sh | bash
source ~/.bashrc   # 或 source ~/.zshrc

# 2. 选择模型（国内用户可选 GLM / Kimi / MiniMax / Ollama 本地模型）
hermes model

# 3. 常用命令
hermes tools      # 配置启用的工具
hermes setup      # 完整交互式配置向导
hermes gateway    # 启动消息平台网关（Telegram / Discord 等）
hermes doctor     # 诊断配置问题
hermes update     # 升级到最新版

踩坑与注意事项

注意：① 不支持原生 Windows，必须 WSL2；② 指南把"选模型"称为"第一个周末错误"——新手常一上来选最贵的前沿模型，建议先用便宜模型（或国产模型）把 Workflow 跑顺再升级；③ Skill 是 Agent 自动写入本地的 markdown 文件，意味着 Agent 会修改自己的"行为库"，生产环境建议把 skills 目录纳入 Git 管理以便审计；④ 让 Agent 常驻 VPS 时务必做好网关鉴权，别把无保护的 Bot 暴露在公网。

国内替代方案

模型层：直接用 GLM / Kimi / MiniMax / DeepSeek（OpenAI 兼容），这是官方支持的姿势。框架层：国内同形态的"本地优先 + IM 接入"开源框架可参考 OpenClaw（支持飞书/钉钉/企业微信生态，中文社区更活跃）。

培训师点评：教这个项目时不要陷入安装细节，重点讲"Skill 自动沉淀"这一范式——Agent 把自己的经验写成可复用程序，这是从"用 AI"到"养 AI"的分水岭。
04

Qwen3.6 + Qwen-Agent + MCP 文件系统：让国产模型自己整理桌面、生成网站并存盘

AI Coding / MCP 🔥 值得马上实践 📌 值得收藏 🇨🇳 国产模型 🧑‍💻 开发者向 2026-09-28 前后发布
一句话摘要：官方手把手教程：vLLM 部署 Qwen3.6-35B-A3B，用 Qwen-Agent 挂官方 MCP filesystem server，Agent 自主整理文件夹、生成网站并写入磁盘。

原始资料

  • 官方教程Hyperstack：Step-by-Step Guide to Deploying Qwen3.6 on a GPU Cloud for Agentic Coding
  • 相关项目github.com/QwenLM/Qwen-Agent（教程所用官方 Agent 框架）

教程讲了什么

教程先指导在 GPU 云上用 vLLM 部署 Qwen3.6-35B-A3B 并提供 OpenAI 兼容端点，然后用 Qwen-Agent 的 Assistant 类连接该端点（含 enable_thinking 思考模式配置），再把官方 MCP filesystem server 注册为工具。随后演示两个真实任务：让 Agent 自主整理一个杂乱的工作目录，以及让 Agent 生成一个猫咪主题网站并把 index.html 写入磁盘。

技术栈

模型Qwen/Qwen3.6-35B-A3B（MoE，开启 thinking 模式）
推理vLLM（OpenAI 兼容 API，localhost:8000/v1）
Agent 框架Qwen-Agent（qwen_agent.agents.Assistant）
MCP 工具@modelcontextprotocol/server-filesystem（官方文件系统 server，npx 启动）
部署环境GPU 云（可用任意 vLLM 能跑的环境）

手把手复现（核心代码，来自原教程）

from qwen_agent.agents import Assistant

# 1. 指向本地 vLLM 部署的 Qwen3.6（OpenAI 兼容端点）
llm_cfg = {
    'model': 'Qwen/Qwen3.6-35B-A3B',
    'model_type': 'qwenvl_oai',
    'model_server': 'http://localhost:8000/v1',
    'api_key': 'EMPTY',
    'generate_cfg': {
        'use_raw_api': True,
        'extra_body': {
            'chat_template_kwargs': {'enable_thinking': True}
        },
    },
}

# 2. 通过 MCP 挂载官方文件系统 server（只暴露专用工作目录！）
tools = [{
    'mcpServers': {
        "filesystem": {
            "command": "npx",
            "args": [
                "-y",
                "@modelcontextprotocol/server-filesystem",
                "/ephemeral/agent_workspace"
            ]
        }
    }
}]

# 3. 初始化并运行
bot = Assistant(llm=llm_cfg, function_list=tools)
messages = [{'role': 'user', 'content':
    'Develop a cat website and save it on the /ephemeral/agent_workspace desktop.'}]
for responses in bot.run(messages=messages):
    pass
print(responses)

踩坑与注意事项

注意：① 安全红线：filesystem server 只应暴露专用工作目录，绝不要把整个系统盘挂给 Agent（原教程明确警告）；② MCP server 通过 npx 启动，需要本机有 Node.js；③ 35B-A3B 是 MoE 模型，本地跑仍需相当显存——纯本地体验可换成更小的 Qwen3 dense 模型（如 8B），代码完全一样；④ api_key: 'EMPTY' 只对本地 vLLM 有效，接云端要换真实 Key。

普通人能不能复现

🔴 开发者项目（按原教程需 GPU 云）

降级路线：没有 GPU 的开发者可以把 model_server 指向阿里云百炼的 Qwen 兼容端点或本地 Ollama 跑的小尺寸 Qwen3，MCP 部分代码不变，零 GPU 也能体验完整流程。

培训师点评：这篇教程的教学价值在于"最小完整的 Agentic Coding 链路"——模型、框架、MCP 三层全部官方开源，没有黑盒。讲清楚 filesystem server 的目录白名单设计，就讲清楚了 Agent 安全的第一课。

把 LLM 塞进 2D 游戏世界：Datawhale《Hello-Agents》赛博小镇实战——NPC 有性格、有记忆、还记得住你

AI 奇技 / Agent 🧪 值得实验 🎓 值得培训 🇨🇳 国产教程 🔓 开源项目 博客园连载笔记，近日发布
一句话摘要：Datawhale Hello-Agents 第 15 章实战：Godot + FastAPI + 自研 Agent 三层分离，每个 NPC 一个 Agent 实例，双层记忆 + 好感度，LLM 成本压到 1/3。

原始资料

  • 实战笔记博客园：Agent 速成笔记 · 第 15 章 构建赛博小镇
  • 原始教程Datawhale《Hello-Agents》（GitHub；GitCode 有镜像）

教程讲了什么

赛博小镇是一个 2D 像素风虚拟办公室：玩家用 WASD 走动，靠近 NPC 按 E 即可自然语言聊天。架构三层分离——Godot 管感知与表现，FastAPI 后端管决策（记忆检索 + LLM 生成 + 好感度结算），每个 NPC 是一个独立的 SimpleAgent 实例。核心机制：人设提示词定义性格；双层记忆（WorkingMemory 容量 10 条/TTL 120 分钟 + EpisodicMemory 用 SQLite + Qdrant 语义检索 top_k=3）；好感度 0–100 连续值，由 LLM 情感分析打分并回写系统提示词。

为什么值得收藏

最精彩的是成本优化手法：N 个 NPC 的背景闲话合并成 1 次 LLM 调用（要求 JSON 输出），只有玩家真正对话时才走专属 Agent——作者自述此举把 LLM 调用成本压到原来的约 1/3。这种"混合模式"对所有多 Agent 系统都有直接借鉴价值。

技术栈

模型OpenAI 兼容 LLM（可换 DeepSeek/Qwen）
前端/引擎Godot（2D 场景、Area2D 感知、气泡对话、四方向动画）
后端FastAPI + HelloAgents 框架（SimpleAgent）
记忆WorkingMemory（容量 10、TTL 120min）+ EpisodicMemory（SQLite + Qdrant，top_k=3）
关键机制好感度评分（LLM 情感分析）+ 合并调用降本（N→1 次）

关键设计点

  • 一个 NPC 一个 Agent 实例：人格由系统提示词定义，位置/忙闲由后端状态管理器定义，两者解耦。
  • 记忆分层：WorkingMemory 管对话连贯，EpisodicMemory 管长期"回忆"，语义检索 top_k=3 是实测折中。
  • 成本核心手法：背景 NPC 的闲话合并为 1 次 LLM 调用（JSON 数组输出），玩家对话才走专属 Agent。
  • 前后端边界切干净：Godot 只管感知与表现，所有"智能"都在后端。

踩坑与注意事项

注意：① "成本降至 1/3"为笔记作者基于教程数据的自述，具体比例取决于 NPC 数量与对话频率；② 合并调用要求模型稳定输出 JSON 数组，小模型容易格式崩，建议用 function calling / JSON mode；③ 好感度由 LLM 打分存在主观波动，关键场景应设打分上下限保护。
培训师点评：这个案例的教学核心不是游戏，而是两个工程模式：记忆如何分层、多 Agent 调用如何降本。学员学会"合并 N 次闲聊为 1 次调用"这一招，就值回全部课时。
