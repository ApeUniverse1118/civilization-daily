01｜案例是什么？

Oh Story（仓库 zenstory-ai/oh-story-claudecode，MIT）是一套面向中文网络小说的 Agent Skill 包，覆盖长篇与短篇的全流程：扫榜选材 → 拆解爆款 → 搭大纲写正文 → 去 AI 味 → 生成封面图。它以 13 个 skill 的形式装进你已经在用的编程 Agent（Claude Code、Codex CLI、Google Antigravity、OpenCode、ZCode、OpenClaw、Reasonix 等），写作用的模型就是该 Agent 的模型，不需要 GPU，也不需要另配模型。项目自带 demo 与样例文件，可直接看到「写第 21 章」这个动作从头到尾产出了什么。

02｜为什么今天值得关注？

先把窗口内的事实说清楚：本期窗口（10-03 12:00 → 10-04 12:00）内，该仓库只有 2 次提交，均为 ClawHub 分发链路相关（PR #455「Fix ClawHub updates and add pinned inventory reconciliation」10-03 14:11、PR #456「ci: align source Release and exact ClawHub handoff」10-03 16:56，均为北京时间）。项目最近一次内容版本 v0.8.4 发布于 2026-09-27，早于本窗口。本文收录它的依据是「窗口内完成了分发链路对齐的实质更新 + 项目本身是中文内容创作 Agent 化最完整的一手案例」，而不是「它在 10-03 发布了新写作能力」。这一点请读者务必知悉。
  • 为什么以前不容易做：用 AI 写长篇，最难的从来不是「写出好句子」，而是连续性——第 80 章不能与第 7 章的伏笔打架，角色不能突然知道他还不知道的事。靠对话记忆硬撑，上下文一压缩就丢伏笔。
  • 为什么现在变得容易：① Agent Skills 让「写作方法论」可以被拆成一个个可加载的文件，而不是塞进一段超长提示词；② hook（钩子）机制让「写正文前必须已有细纲」这类门禁可以被程序强制执行；③ 用文件系统做状态存储，不再依赖模型的记忆。
  • 为什么值得花时间：网文是中国独有的、体量极大的内容产业。一个能扛住几百章连续性的写作工作流，其价值不在「AI 写小说」这个噱头，而在「长任务状态管理」这套方法——它可以直接迁移到任何长周期、多步骤的 Agent 任务上。

03｜案例的前世今生

前世。2023–2024 年，「AI 写小说」的主流形态是把设定和大纲塞进一段超长提示词，再让模型续写。这条路在第 10 章左右就开始崩：角色性格漂移、伏笔失踪、时间线错乱——因为模型的上下文是有限的、会被压缩的，而长篇需要的是持久状态。

发展。三件事改变了做法：① RAG 与文件检索让「按需读取设定」成为可能；② Agent Skills 规范（2025–2026）让「一套写法」可以被拆成多个可加载文件、按需注入；③ hook/门禁机制让「流程约束」从「提示词里的请求」变成「程序上的必然」。

今生。Oh Story 的做法是把长篇写作拆成四个可以独立维护的层：设定、大纲、正文、追踪。关键在于「追踪」层——它把连续性写进一份固定 7 栏、硬上限 12KB 的上下文文件，下一章只读这一份，且明确区分「作者真相」与「读者已知」（作者认为这是「角色提前知道答案、伏笔写飞」的主要来源）。写作前有 guard-outline-before-prose.sh 拦截缺细纲的章节，写完跑确定性的检查脚本（查截断、查 AI 句式、查标点），再由 storyctl.py 提交状态并整份重生成派生视图——手改派生文件会被 check 拒绝。

下一步可能怎么发展（分析 / 推演）。这套「用文件系统承载长任务状态 + 用脚本做确定性门禁」的结构，很可能会被搬出网文领域：长周期研究报告、系列课件、产品需求文档、连续剧剧本——任何「需要记住前面写过什么」的创作都可以复用。以上为推演，非事实。

06｜解决了什么真实问题？

从需求侧看，痛点集中在「长篇的持续性」：

  • 需求一（网文作者）。写到第 80 章，前面的伏笔、角色状态、时间线已经多到记不住。人写都容易错，让 AI 写更容易崩；而一旦崩了，改一处要牵动几十章。
  • 需求二（新人入行）。网文行业有明确的方法论（扫榜 → 拆文 → 商业化写作），但新手缺少「把方法论落成动作」的工具，只能靠自己摸。
  • 需求三（多平台分发）。同一部作品要在起点、番茄、晋江、七猫、知乎盐言等不同平台适配，格式与节奏要求不同。
  • 共同点：不是「写不出字」，而是「写长了就守不住规矩」。

09｜它到底是怎么实现的？

这套系统真正的技术贡献有四点，每一点都可以脱离「网文」独立成立：

① 状态与展示分离（Single Source of Truth）。所有派生视图（上下文、伏笔、角色状态、时间线）都由 _tracking-state.json 整份重新渲染，且「手改派生文件会被 check 拒绝」。这直接消灭了「文档和状态不一致」这类最常见的团队协作问题——人写长文档会走样，程序渲染不会。

② 把「连续性」压缩成固定 12KB。控制上下文体积是 Agent 工程的核心约束。作者用「固定 7 栏 + 硬上限 12KB + 不进正文 prompt」三个约束，让续写只依赖一份稳定的状态快照，而不是整部作品的历史对话。

③ 区分「作者真相」与「读者已知」。这是一个非常专业的小说工程概念：作者知道结局，读者不知道。混淆两者，就会出现「角色提前知道答案」这种崩坏。项目把它做成了两份独立的记录文件。

④ 用 hook 把「请求」变成「必然」。「写正文前必须有细纲」如果只写在提示词里，模型可能忘；做成 guard-outline-before-prose.sh 钩子，就变成了流程上的硬约束。这是本案例最值得迁移的一条工程经验。

10｜手把手复现

以下 Step 1–4 整理自项目 README 明确写出的安装步骤；Step 5–6 为 README 中 demo 展示的实际命令；Step 7–8 为本文补充建议，已单独标注。

Step 1（原文）。安装 skill：npx skills add zenstory-ai/oh-story-claudecode -y -g。加 -g 为全局安装（所有目录可用），去掉则只装到当前目录；更新时重新执行同一条命令即可。

Step 2（原文）。也可以直接对 Agent 说一句话：「安装这个 skill https://github.com/zenstory-ai/oh-story-claudecode」（适用于支持导入 GitHub 仓库 / skill 的平台）。

Step 3（原文）。部署环境：在写作项目根运行 /story-setup（Codex 用 $story-setup），它会把 hooks / agents / references 部署到位。

Step 4（原文）。然后新开会话。升级后同样要重跑一次 /story-setup。

Step 5（原文·可选）。若已有连载作品，用 /story-import 把已发布章节反向重建成可续写工程。

Step 6（原文）。写下一章：/story-long-write 写第21章——skill 会先检查细纲是否存在，缺则先补纲，再走写作与检查链。想拆解参考作品用 /story-long-analyze。

Step 7（本文补充的建议）。第一次先只跑「导入 + 拆文 + 补细纲」，不写正文，确认状态卡与伏笔表的结构符合你的写作习惯后，再进入正文生成。

Step 8（本文补充的建议）。把状态卡（12KB 上限）当作你的「写作交接单」：每次收工前确认「下一章承诺」一栏写清楚了，这比让模型记住一切更可靠。此建议为本文推导。

12｜踩坑

以下均为项目 README / docs/hosts.md 自述的已知限制，本文未独立复现：

  • 装完必须新开会话。安装/升级后不新开会话，hooks 与 agents 不会生效——这是最容易踩的坑。
  • 各宿主部署差异大。README 专门列出排查项：Windows 可能报 ENOENT、Antigravity 需 agy -p、目录残留等，见 docs/hosts.md。
  • 派生文件不能手改。追踪状态由工具从 _tracking-state.json 整份重新渲染，手改 上下文.md 之类会被 check 拒绝。新手最容易在这里卡住。
  • 「窗口内没有新内容版本」。本期收录它的窗口事件是分发链路对齐（PR #455/#456），最近一次内容版本 v0.8.4 为 09-27。请勿误以为 10-03 发布了新的写作能力。
  • 质量结论均来自项目自述。demo 的成片、评分表、状态卡 diff 均为作者公开材料，本文未逐项复核。

13｜中国用户能不能直接做？

  • 国内访问：有限制——仓库与 skill 通过 GitHub / npx 分发，直连不稳定，通常需要加速。
  • 注册：无需注册，无账号体系；项目结构完全落在本地文件系统。
  • API：不额外需要 Key；成本发生在你使用的编程 Agent 与模型上。
  • 成本：skill 本体免费开源；主要成本是模型调用（长篇续写属于长任务，token 消耗随章数增长）。
  • 技术门槛：有一定门槛 需要会用命令行、理解 Agent 的 skill / hook 机制；不需要 GPU（README 明确说明）。

15｜中国企业可以怎么用？

  • 企业场景 1｜内容工作室 / MCN。把选题拆解、系列内容规划、跨平台改写做成类似的 skill 包，用状态文件管住长期选题库与人物设定。
  • 企业场景 2｜长文档生产。白皮书、系列课件、产品手册——凡是要写 50 页以上、且前后必须一致的内容，都可以复用「状态卡 + 门禁脚本 + 派生视图重生成」这套结构。
  • 企业场景 3｜版权与合规审查。把「本章退役登记」「作者真相 vs 读者已知」这类记录用于内容审核留痕，形成可追溯的创作过程档案。

16｜中国消费者可以怎么用？

  • 网文创作者：用 /story-import 把手上连载的作品导入，让 AI 帮忙补细纲、查伏笔漏洞，而不是替你写。
  • 长篇爱好者：用 /story-long-analyze 拆解自己喜欢的作品，理解「为什么这段好看」。
  • 写作新手：把「扫榜 → 拆文 → 商业化写作」这条方法论当成入行地图，先学规矩再动手。

17｜如何变成一个赚钱的项目？

产品化：不做「另一个写作工具」，而做「长篇连续性保险」——订阅制的状态管理与一致性审查服务，用户带自己的稿子进来，输出伏笔报告与风险清单。

服务化：给内容工作室做「AI 写作流水线搭建」，交付 skill 包 + 状态规范 + 团队培训。

咨询化：「如何让 AI 参与长篇创作而不崩」本身就是稀缺咨询：帮团队设计角色设定库、伏笔台账、审核门禁。

培训化：《AI 辅助长篇创作实战》——面向网文作者与编剧，2 天训练营，产出可运行的写作工程。

01｜案例是什么？

开发者 KimYx0207 维护的开源中文教程仓库 AI-Coding-Guide-Zh（MIT）：把当前主流 AI 编程工具——Claude Code、OpenClaw、Codex、WorkBuddy——的教学内容组织成四条并行的学习路径（编程 / 助手 / Agent / 办公），目前公开的规模是「50 篇完整教程 + 1 张速查卡 + 80 万+ 内容量 + 1500+ 实操示例」。它最特别的地方不是内容多，而是像软件一样管版本：仓库用 Release 记录每一轮复核的范围与结论。

02｜为什么今天值得关注？

  • 窗口内的事实（可用 API 核实）：2026-10-03 这一天，该仓库在窗口内（10-03 12:00 → 10-04 12:00）连续发布了 三个版本：v5.3（北京时间 17:04）「四主线全面核查与实操修正」、v5.4（19:12）「正文、当前功能与跟练的第二轮复核」、v5.5（22:13）「四工具教学补齐与近期变化复核」。同一天还有 15 次提交在窗口内落地。
  • 为什么以前不容易做：AI 编程工具迭代极快，教程的生命周期常常只有几周——今天写的操作步骤，下个版本就失效。中文圈尤其严重：一手文档多为英文，中文教程多为转载与拼凑。
  • 为什么现在变得值得做：① 工具生态从「一个工具」变成「一个矩阵」（Claude Code / OpenClaw / Codex / WorkBuddy 各有所长），用户需要的是选择与迁移的路径，而不是单点技巧；② Agent / Skill 这些概念让「一套方法能否迁移到另一个工具」成为真实问题。
  • 为什么值得花时间：「教程即产品」是一种很少被认真对待的商业形态——它同时具备内容资产、社群入口、培训素材三重属性。

03｜案例的前世今生

前世。中文 AI 工具教程的第一阶段是「翻译与搬运」：把官方文档翻一遍，配上截图。问题在于更新无机制——工具一升级，教程就成了误导。

发展。第二阶段是「个人经验帖」：某位博主写自己怎么用某个工具解决了某个问题，可读性强但不成体系，也没人负责更新。第三阶段开始出现「仓库化的教程」——用 Git 管内容、用 Issue 收反馈、用 Release 记版本。

今生。本项目属于第三阶段的成熟样本：它不只写内容，还建立了「复核」这个动作。窗口内一天连发三个版本，版本说明写的是「全面核查与实操修正」「第二轮复核」「四工具教学补齐」——这不是新写了一章，而是对既有内容做交叉验证。README 的版本说明（v5.5「四工具教学补齐与近期变化复核」）也印证了这一点。

下一步可能怎么发展（分析 / 推演）。教程类仓库最可能的进化方向是「可执行化」：不只教你点哪里，而是把操作本身做成 skill / 脚本，读者拉下来就能跑；进一步可能出现「教程自动校验」——用程序定期跑一遍文档里的命令，失效就报警。以上为推演，非事实。

09｜它到底是怎么实现的？

这个案例没有模型、没有 Agent、没有代码框架，它值得研究的是「内容工程化」的三条做法：

① 把教程当软件发版。「v5.3 / v5.4 / v5.5」这样的版本号，让读者知道「我看到的是哪一轮复核的结果」。对快速迭代的工具教程来说，这比内容本身更重要——它解决的是可信度随时间衰减的问题。

② 用 PR 与分支表达「这一轮改了什么」。窗口内的分支命名（docs/full-refresh-20261003、docs/round2-content-20261003、docs/refresh-workflows-20261003）本身就是一份维护日志：第一轮全面核查、第二轮内容复核、第三轮工作流刷新。这套流程与软件团队的协作习惯一致。

③ 用「四工具对照」建立迁移价值。单工具教程会被官方文档替代，多工具对照教程不会——因为「A 和 B 的差别在哪」是官方文档天然不会写的。

为什么它可以工作？因为它把「更新」当成核心功能，而不是附带动作。绝大多数教程仓库死于「写了就不管」，而这个仓库用 Release 机制把「我得持续复核」变成了公开承诺。

Step 1（原文/仓库可观测）。clone 仓库，从速查卡开始建立全局印象，再按自己身份选一条主线（编程 / 助手 / Agent / 办公）。

今日 AI 实战观察

10-04 这一天的两个案例都不是「新模型」「新产品」，而是同一种现象的两个切面：中文内容生产正在被「工程化」。

第一，AI 写作的瓶颈不在生成，在于「记住」。案例 01 用 12KB 的状态卡和一份 _tracking-state.json 解决长篇连续性，这说明业界已经意识到：让 AI 写得好不难，难的是让它在一百次对话之后仍然保持一致。这个认知对整个 Agent 领域都成立。

第二，「把要求写成钩子，而不是写成提示词」正在成为共识。「写正文前必须有细纲」如果只写在提示词里，模型可能忘；做成 guard-outline-before-prose.sh，就变成了流程上的必然。这是本日最值得带走的一条工程经验——凡是不能失败的约束，都不该交给模型自觉。

第三，教程也在变成产品。案例 02 一天连发三个版本，版本说明是「全面核查与实操修正」「第二轮复核」。在中文化语境里，这是一种很新的做法：把「持续更新」从道德要求变成版本制度。它解决的是一个更普遍的问题——在工具每周都在变的时代，「我读过的最新一版」是有价格的。

第四，两个案例都选择了「不依赖单一工具」。案例 01 支持 8 款编程 Agent，案例 02 覆盖 4 款工具。这不是巧合，而是对现实的判断：工具会换、模型会换，能被沉淀下来的是流程、状态结构和判断标准。对于做 AI 落地的人来说，这是一个明确的信号——不要把资产建在工具上，要建在流程上。
