一句话结论：真正稀缺的不是「AI 能出一段视频」，而是有人把「一部 50–100 集短剧」的续集、接镜、断点续跑与重做范围，写成了可运行的工程结构。

01｜案例是什么？

一位中文开发者 binwu1 在 GitHub 开源了 Drama Series Agent（内称 runtime 为 Hermes）：它把「做一部短剧」当成一个有状态的系列任务来做。你在同一个系列对话里依次说「立项 / 写第 1 集」「出片第 1 集」，Agent 就自动写出系列设定（大纲、世界观、角色、画风、分集目录）和单集剧本，把「谁出现在哪一镜」写进分镜任务表，生成可渲染文件交给本机 ComfyUI + MiniMax H3 Ref2VA 排队渲成视频，再用 ffmpeg 抽尾帧当下一镜首帧自动接片，最后拼成 master.mp4。中途断了可以按集从断点续跑；某一镜不满意只重渲那一镜；改了设定则只作废需要重做的下游步骤。项目 10-08 15:26（北京时间）首次公开建仓，Apache-2.0。

02｜为什么今天值得关注？

  • 为什么现在变得容易：① 参考图驱动的 Ref2VA（参考图 → 视频）让角色一致性从「靠 Prompt 硬撑」变成「靠一张定妆图」；② ComfyUI 把视频模型变成可编排的 API 图，工作流可分档（加速 / LoRA / 极速 / 质量）；③ Agent + SKILL 结构可以把「编剧方法论」和「渲染任务」拆成不同技能分别加载；④ 国产视频模型（MiniMax H3）与国产 LLM 端点（ModelScope 免费额度、通义百炼 Qwen、DeepSeek）同时可用。
  • 为什么值得花时间：「AI + 内容」在中文一手来源里长期稀缺，多数是「生成一张图 / 一段视频」的演示；这次是一套把内容生产按「系列」单元组织起来的工程实现，并且把付费短剧的创作方法论（钩子、节奏曲线、付费点、反派设计）一并开源进来了。

03｜案例的前世今生

前世。2023–2025 年，AI 视频生成的主体是「文生视频模型 + 单次生成」：给一段提示词，出一段几秒的片段。创作者的真实困境不在「能不能生成」，而在三件事：角色不连贯（下一镜主角的脸变了）、镜头接不上（前后镜之间跳跃）、没法管进度（一集几十镜，靠人脑记哪个镜重跑过）。当时的可行解法只有「人工 + 剪辑软件」，成本高、不可复制。

发展。三条线先后成熟：① 参考图驱动 / 首尾帧续接类能力（README 中的 Ref2VA、fl2va 与「尾帧抽出来当下一镜首帧」）把「一致性」从提示词工程变成了素材工程；② ComfyUI 成为视频模型的事实标准编排层，工作流可导出为 JSON 由外部程序提交，这为「Agent 驱动出片」提供了接口；③ Agent 的 SKILL / 记忆分层结构成熟，可以承载「编剧方法论」这种长文档知识，而不必把它塞进系统提示词。

今生。这个项目没有发明新模型，做的是「把上述零件组织成一个有状态的系列容器」。它的关键设计不是渲染，而是 series_id 作为状态锚点：系列设定、角色定妆、每集进度、任务轨迹全部挂在同一个系列上，于是「下一集接着往下做」在结构上成为默认行为。窗口内它新增了工作台的任务视图（Jobs UI）、技能目录布局与双语文档，并首次公开了 demo 视频——也就是说，它从「一个人的私有工具」变成了「别人能看懂、能尝试的项目」。

下一步可能怎么发展（分析 / 推演）。三条可推演方向：① 从「单机自渲染」走向「渲染队列化 / 云端出片」，因为本地显卡是当前最大的落地瓶颈；② 从「剧本 + 出片」延伸到「批量投流素材」——同一部剧自动切出几十条投放切片，这已经是短剧行业的标准动作；③ 从「个人创作」走向「小型工作室流水线」，把选角、定妆、出片拆给不同角色并行。以上为推演，非事实，也非作者声明。

06｜解决了什么真实问题？

从需求侧看，而不是从技术侧看。

需求一（短剧创作者 / 小团队）：量产能力缺口。微短剧是「集数换留存」的内容形态：一部剧 50–100 集，靠前几集的钩子拉付费。创作者真正的瓶颈不是「写不出一个好点子」，而是把一个点子稳定地摊成几十集，并且每集都能对上脸、接上镜。手工状态下，这一层的成本随集数线性上升。

需求二（个人创作者）：状态管理缺口。「我今天做到第几集、哪几镜渲过、改了设定之后哪些要重做」——这些问题过去只能靠人脑或表格维护。README 把这件事说得很直白：改了设定或重写剧本，系统只作废需要重做的下游步骤，而不是默认整集重来。这就是把「项目管理」内建进了 Agent。

需求三（行业方法论）：把爆款经验结构化成可执行技能。编剧 Skill 给出了 8 份方法论文件：钩子设计（hook-design）、开篇规则（opening-rules）、节奏曲线（rhythm-curve）、爽感矩阵（satisfaction-matrix）、反派设计（villain-design）、付费点设计（paywall-design）、赛道指南（genre-guide）、合规清单（compliance-checklist）。付费点设计被单独列为一等公民——这意味着技能作者理解短剧的商业本质是「在哪一集、因为什么、让人付费」，而不是「写一个完整的故事」。

09｜它到底是怎么实现的？

剥开业务内容，有四个可迁移的工程机制（均来自作者 README 自述，非本文推测）：

机制一：把「系列」而不是「一次生成」当作状态单元。所有产物都挂在同一个 series_id 下：系列设定是共享上下文，分集是系列下的条目，进度是系列下的运行时状态。好处是「第 2 集」天然继承「第 1 集」的世界观、角色与画风，而不需要每次都重新灌一遍背景。

机制二：角色一致性靠「素材」而不是「提示词」。这是短剧工作流与普通文生视频最本质的分野。README 的写法是：H3 出片提示等放在 skills/，分镜表里带「角色图 / 音色引用」，渲染时以定妆图作为参考图输入。也就是把「这个人长什么样」从文本描述变成了图像条件——文本描述漂移，图像条件不漂移。

机制三：镜头之间用「帧」物理接续，而不是靠剪辑对齐。抽上一镜尾帧 → 当作下一镜首帧，这是把「连续性」从一个创作问题降级成一个 ffmpeg 命令。README 把它列为功能亮点，原文表述为「上镜尾帧 → 下镜首帧，自动接片，无需手动剪辑」。

机制四：增量失效，而不是整集重算。「改了设定或重生剧情时，只作废需要重做的下游步骤，尽量少重渲。」这需要一个显式的依赖图（哪些步骤消费了哪一版设定），否则无法判断下游。作者没有在 README 里给出依赖图的实现细节，本文不推测其数据结构。

技术边界的诚实提示：README 非常明确：仓库不附带 ComfyUI，也不附带 MiniMax H3 权重；未装好时「仍可在工作台做立项 / 写集 / 定妆——视频任务会失败」。因此这个案例应被理解为「一条被工程化的生产链」，而不是「装完就能出片的软件」。作者也提示：请用 start.sh/start.bat 启动以便断点续跑与恢复。

AI Automation / Dify AI Research / 知识库 全本地 · 零 API 成本 窗口内建仓 10-08 19:05 Python / MIT（见说明） 1 Star、作者身份无法确认、数据均为自述
一句话结论：它最有价值的部分不是「把视频转成文字」，而是那条被真实踩出来的工程判断——Dify 同步工作流 60 秒超时，所以长视频入库必须拆成「受理 + 后台异步」，以及一套「怎么知道它坏了」的质量闸门。

01｜案例是什么？

一个面向中文短视频平台的知识库入库流水线：你把抖音 / 小红书 / B站 的视频链接丢进 Dify 的一个对话框，系统自动判断你是「要入库」还是「要提问」，入库时先回一句「收到，任务编号 xxx」，然后在后台把视频下载、抽音频、用 faster-whisper 本地转写、用 LLM 分块纠错、做合规过滤、切成向量存进 Qdrant；之后你就可以直接提问，答案带来源标注。整套 ASR 与向量检索都在本机跑，作者标注为零 API 成本。作者给出的实测是：11 分 37 秒的视频，从粘贴链接到可以提问耗时 147.2 秒（该数据为作者自述，无法独立验证）。

02｜为什么今天值得关注？

  • 窗口内的事实（可核实）：仓库首次提交在 2026-10-08 19:05（北京时间），建仓时间 10-08 19:40，末次推送 10-08 22:22。窗口内提交包含 feat: 质量保障层 + B站分P + 内容去重 + 评测体系、重做架构图（加入质量保障层）、补齐技术文档「坑 27–33」。也就是说：它是一个在窗口内被集中补全到「可交付」状态的工程。
  • 为什么以前不容易做：「视频 → 知识库」这个需求长期存在，但三座山挡着：① 语音转写要钱（云 ASR 按分钟计费），转 100 条视频的成本不可忽略；② 长视频入库慢，而 Dify 的工作流是同步的、默认超时 60 秒，长视频必然失败；③ 转写稿质量参差——口头语噪音、专名被「纠错」改错、LLM 输出被 max_tokens 截断导致内容整段丢失，而没有任何机制告诉你它坏了。
  • 为什么现在变得容易：① faster-whisper 让本地 ASR 到了一台普通机器可用的程度；② Ollama 提供了本地 embedding（本案例用 nomic-embed-text）与本地 LLM 选项；③ Dify 提供了可视化的意图分流 + 知识库混合检索，把「工程」压缩成「编排」；④ 也是最重要的：有人把「怎么知道它坏了」这件事做成了 5 道闸门与 3 层评测，这才是从 Demo 到可交付的分界线。
  • 为什么值得花时间：「AI + 内容 / Research」方向在中文一手来源里长期被内容农场占据（大量复读式「10 个工具」），而这份材料是带评测集、带基线、带 30+ 条踩坑记录的工程复盘，且主动处理了合规问题。这类一手程度在近期很少见。

03｜案例的前世今生

前世。「让内容可被检索」的第一代方案是人工做笔记：看完视频，手打摘要。第二代是平台自带的字幕 / 文字稿，但它不可检索、不可跨视频提问。第三代是「云 ASR + 向量库」的组合，问题在于按量付费与同步阻塞——转一条 10 分钟视频等几分钟，转 100 条就是几小时与一笔账单，而且要自己盯着有没有转错。更根本的问题是「信任」：转写稿错了，你不知道，检索结果就一直是错的。

发展。四条线汇合：① faster-whisper 把 ASR 从「云服务」变成「本机函数」，边际成本归零；② 分块 + map-reduce 的纠错范式出现，让 LLM 能处理长转写稿而不会被上下文截断；③ Dify 把「意图分流 + 知识库检索」变成可视化编排，使「对话式入库」成为可能；④ 音频指纹去重、专名漂移检查这类质量工程手段开始被引入个人项目。

今生。这个项目没有发明任何新技术，它做的是把「一次性转写」升级成「可运营的知识库入库服务」：把入库拆成独立进程（零依赖 Python 标准库 http.server，端口 8090，POST /ingest 立刻返回 202 + job_id，后台线程跑完整链路），并给出任务状态机（queued → running，进度 5% 下载 / 25% 转写 / 60% 纠错 / 80% 入库 → done / failed），任务落盘（_ingest-jobs.json）以便重启后历史仍在。窗口内它补齐了评测体系、去重与架构图——也就是把「我知道它能跑」变成了「我知道它什么时候坏」。

下一步可能怎么发展（分析 / 推演）。① 从「个人知识库」走向「团队知识库」需要一个权限模型（谁能问、谁能入库、什么内容不该入库）——目前是单机单库。② 「质量闸门」这套思路很有机会被抽成独立组件，用于其他长文本 LLM 流水线（合同、论文、会议记录）。③ 一旦素材规模上千，检索侧需要增量索引与主题治理。以上为推演，非事实。

06｜解决了什么真实问题？

先看需求，不看技术。

需求一（个人学习者）：视频里的知识「不可回查」。作者对痛点的描述非常具体：「看技术视频时想回看某个点，得拖进度条一段段找。11 分钟的视频，想定位到『他讲显存那段』，基本靠运气。」这不是「想要 AI」，而是想要一个能按语义找时间的搜索框——而平台不提供这个功能。

需求二（内容 / 培训团队）：素材散落，无法跨视频检索。几十个课程视频、直播回放、选题参考躺在收藏夹里，人和人之间的知识传递方式是「你再去看一遍那个视频」。把视频统一入库后，一次提问可以跨视频取答案并标注来源。

需求三（被大多数人忽略的）：怎么知道它坏了？这是这个项目真正与众不同的地方。作者的表述是：质量保障层「不参与数据流，只回答一个问题：怎么知道它坏了」。5 道闸门各自治一类具体病：规则清洗治 ASR 句首口头语；分块 map-reduce 纠错治「LLM 输出被 max_tokens 截断导致内容全丢」；校验闸门（真检查）治「有标题但标题下没内容」的假通过并拒绝入库；专名漂移检查治「LLM 纠错反而把正确专名改错（Act → Actor）」；内容去重（音频指纹）治同一节课被重复投稿按链接入库两次。这四类病，恰恰是所有「视频转知识库」教程都不会提的。

09｜它到底是怎么实现的？

三个机制值得单独讲（均来自作者文档自述）：

机制一：异步受理，把「重活」移出同步工作流。这是本案例最有迁移价值的一条工程判断。作者把两条约束摆在一起：① 员工不会用命令行 → 入库必须走对话；② 入库慢到不能同步等（11 分钟视频要 147 秒，而 Dify 工作流默认 60 秒超时）→ 必须有异步。两条约束合起来只剩一条路：Dify 只做「受理 + 回执」，真正的重活在外面跑。于是入库被拆成独立进程，用 202 + job_id 立刻应答。还有一个细节值得学：作者刻意没有为 4 个端点引入 FastAPI，理由是「机器上没装，而服务只有 4 个端点……为了 4 个端点去装一个框架、还会污染 Python 环境，不划算」。这是很罕见的、反「技术堆料」的取舍。

机制二：质量保障层与数据流解耦。质量层「不参与数据流，只回答一个问题：怎么知道它坏了」。5 道闸门对应 5 类具体故障（口头语 / 截断 / 假通过 / 专名漂移 / 重复入库）。这里最关键的是校验闸门是 fail-closed 的——发现「有标题但标题下没内容」就直接拒绝入库，而不是写进去再说。作者用一句话点了要害：「怎么知道它坏了」比「怎么让它跑起来」更难，也更能决定这个系统能不能被信任。

机制三：合规不是声明，是数据流设计。作者搬出著作权法的「思想 / 表达二分法」：结构、知识点是「思想」不受保护；他人具体说的话是「表达」受保护。据此把纠错输出改成三段式，默认只入库「知识点 + 问答对 + 关键参数摘录」，丢弃「校对稿」（他人完整原文）。并给出三条限制防止变相保留全文：只摘含数值或已知参数名的句子（纯观点句不摘）、总长封顶 700 字、明确标注「原文摘录」。作者还特意指出一个反直觉结论：「就算是『只给一家公司内部用』也不构成豁免」。另一个意外收获：去掉原文后检索反而更准——问答对的命中得分（0.489）比原文（0.455）还高。

诚实提示（来自作者）与本文补充：作者已明确标注哪些是自测数据（性能表、检索通过率、命中得分）。本文补充：这些数字均为作者单机自述，无第三方复现，也无法独立验证；评测集与基线文件虽在仓库中，但本文未实际运行。请按「作者自述」而非「已复现结论」引用。

12｜踩坑

作者自称技术文档含 30+ 条踩坑，README 中明示了以下几条（均为作者原文，非本文推测）：

13｜中国用户能不能直接做？

国内访问可行但需代理　Dify / Qdrant / faster-whisper 均为可本地部署的开源件；GitHub 克隆与部分模型下载需代理或镜像。运行过程本身不依赖任何境外服务。
注册无需任何平台注册（全本地）。若要用云 LLM（如 DeepSeek）则需常规实名注册；也可全程用 Ollama 本机模型做到零注册。
API不需要付费 API：ASR 本地、Embedding 本地（Ollama nomic-embed-text）、向量库本地；仅「纠错 / 意图判断 / 作答」这一步需要 LLM，可用 DeepSeek 或本机 Ollama。这是本案例对中国用户最友好的一点。
成本作者口径为「全程零 API 成本」。需注意这是作者自述，且前提是「本机跑 ASR + 本机 embedding」；若用云 LLM 做纠错，长视频会产生实际 token 费用（作者未给成本估算）。硬件侧需一台能跑 faster-whisper 的机器（CPU 亦可，只是更慢）。
技术门槛开发者级　需要 Docker、Dify 自托管、Python 环境、多个本机服务（Ollama / 入库服务 / 抓取服务）联调；导入工作流后还有 7 项手工配置。作者也明说了这一点（把「只想看代码」列为推荐路径）。
合规风险需自行评估　抓取他人视频并转写，涉及平台服务条款与著作权。作者已做了数据流层面的规避设计（丢弃原文、只存知识点与摘录），但这不构成法律意见；企业使用前应自行评估。

14｜国产替代方案

15｜中国企业可以怎么用？

企业场景 1｜培训与知识管理团队：把内部直播 / 培训视频变成可检索资产。企业每年产出大量培训直播与会议回放，命中率极低。用这套管线把视频转为可提问知识库，员工问「去年那场培训里讲的报销额度是多少」即可得到带来源的答案。本案例的「关键参数摘录 ≤700 字」设计恰好适合这类「问数字、问参数」的高频企业问答。需注意：涉及内部资料时应关闭对外抓取，只处理自有素材。

企业场景 2｜内容 / 电商团队：竞品与素材研究自动化。把同类账号的公开视频批量入库，形成「竞品话术库」，用于选题与话术参考。但这一条合规风险最高：作者的设计已尽量规避「复制表达」，企业若采用应先做法律评估，并优先只入库自有或已授权素材。

企业场景 3｜把「质量闸门」本身当成可复用资产。这套闸门不绑定视频场景：任何「长文本 → LLM 处理 → 入库」的流水线都会遇到同样的四类病（截断 / 假通过 / 专名漂移 / 重复入库）。合同解析、论文综述、会议纪要管线都可以直接借鉴。对企业的价值可能大于「视频知识库」本身。

反面提醒：本案例无任何企业客户、无部署案例、无商业结果；作者身份亦无法确认。上表为基于公开结构的可行性分析，不是已验证的落地经验。企业引入前必须自行做安全与合规评估。

16｜中国消费者可以怎么用？

  1. 备考 / 自学：把自己的网课视频、公开课回放批量入库，考前直接问「这块知识点讲了什么、参数是多少」。这是最直接、也最无合规争议的用法（素材为自己购买或公开授权内容）。
  2. 内容创作者：建立自己的「选题素材库」——把行业相关视频入库，写作时跨视频检索，替代反复拖进度条。

17｜如何变成一个赚钱的项目？

  • 产品化：做成「企业内部视频知识库」的私有化交付包——Docker Compose 一键起 + 预置闸门 + 主题治理脚本。卖点不是「能问答」，而是「出错了会告诉你」与「零 API 成本、数据不出内网」。

19｜如果我是一个中国独立开发者

前提：1 个人、预算有限、有基础编程能力、使用国产模型。7 天 MVP（以下排期为本文设计，不是作者方案）：

Day 1｜只跑 ASR。照 README 路径 B：pip install faster-whisper opencc numpy requests + test-asr2.py，用自己拍摄或已授权的一段视频跑通。目标：确认本机算力够、知道自己机器的实时倍率。

↓
Day 3｜导入两个工作流并补齐 7 项手工配置。这一步是集中踩坑日：重选知识库、重选模型、建「主题」字段、打标签、改元数据 ID、配 SSRF 白名单。目标：问答工作流能返回结果（哪怕内容还很少）。
↓
Day 4｜跑通命令行入库。先不接对话式入库，直接用 one-click-pipeline.py 入 3–5 条视频。目标：看到 done(100%)，并在知识库里看到带主题标签的文档。

↓
Day 6｜做主题治理脚本 + 交付模板。把 sync-topic-prompt.mjs 的流程固化成一条命令；写一份「客户自己加视频后要做什么」的一页纸说明（否则客户加完新视频就再也检索不到）。
↓

20｜如何迁移到其他行业

① 会议 / 培训录音把「视频链接」换成「录音文件」，同一套 ASR + 纠错 + 闸门 + 入库；「关键参数摘录」变成「决议项与数字」。
② 客服通话质检音频指纹去重可直接用于「同一通录音重复上传」；但要从「知识库」改为「质检标签 + 结构化字段抽取」。
③ 论文 / 长文档把 ASR 换成 PDF 解析；分块 map-reduce 纠错、专名漂移检查、fail-closed 校验闸门三条设计原样可用。
④ 合同审查「关键参数摘录 ≤700 字」的思路可迁移为「关键条款摘录」；但合同场景对「漏项」的容忍度极低，需把 fail-closed 做得更严。
⑤ 医疗 / 法律长文归档合规设计部分需要重做（行业有专门规范），但「异步受理 + 状态机 + 可观测」的骨架不变。
⑥ 内容出海把入库后的知识点/问答对做多语翻译，形成可检索的多语知识库——这一层不涉及原文，合规压力小。

今日 AI 实战观察

今天这两个案例，行业属性完全不同——一个是短剧内容生产，一个是视频知识库入库——但它们其实在回答同一个问题：当一项 AI 任务的周期从「几秒」拉长到「几十集」或「几百条素材」时，工程上的关键是什么？两个案例给出的答案高度一致，而且都不在模型层。

第一，Agent 正在从「会话」变成「有状态的流程」。短剧 Agent 把状态锚在 series_id 上：系列设定、角色定妆、每集进度、工具轨迹分层存放，于是「下一集继承上一集」与「断点续跑」成为默认行为。视频知识库把状态锚在「任务」上：202 + job_id、queued→running→done 状态机、任务落盘。两者都在做同一件事——把「我记得我做到哪了」从人的脑子里搬进系统里。

第二，真正拉开差距的是「失败可见性」，而不是生成质量。短剧 Agent 的 series_runtime.json 让「改设定后哪些要重做」可被精确圈定；视频知识库的质量保障层更直接——它不参与数据流，只回答「怎么知道它坏了」，并且是 fail-closed 的。这标志着一个成熟度拐点：中国 AI 实战正在从「能不能做出来」转向「做出来了能不能被信任」。

第三，合规开始进入数据流设计，而不只是免责声明。视频知识库把纠错稿改成三段式、默认丢弃他人完整原文、只留知识点与限额摘录——这不是文案层面的规避，而是数据流层面的重构。短剧项目则把「合规审核」做成了一个独立 Skill 命令。当一个项目开始为了合规而改变自己的数据结构时，说明它已经越过了 Demo 阶段。

一个必须泼的冷水：这两个案例的验证强度都不高。短剧项目无性能与成本数据、无企业验证；知识库项目是 1 Star、作者身份不可确认、全部数字为自述。今天更准确的说法是——中国 AI 实战正在出现「工程纪律」的样本，而不是出现「已被验证的商业成果」。对从业者来说，值得拿走的是那几条判断（异步受理、fail-closed、有状态容器、克制），而不是它们的效果截图。

今日商业机会雷达

声明：以下为基于今日案例结构推导的商业模式分析，不代表已验证的商业成功，也不构成收益承诺。

机会 1｜微短剧「前期开发」外包

  • 客户：中小短剧制作团队、出海 MCN、独立制片人
  • 痛点：一部 50–100 集的剧，最大成本是「设定漂移」与前期开发人力；真正缺的是可评审的立项包
  • 实现方式：编剧方法论（MIT 可合规引用）+ 任意国产模型（DeepSeek / Qwen / ModelScope）产出立项包、分集目录、首集剧本——不需要显卡
  • 可能商业模式：按剧 / 按集交付的策划服务；或转向培训
  • 窗口优势：技术门槛与硬件门槛今天都处在低位，且方法论刚刚以开源许可公开

机会 2｜企业内网「音视频资产化」私有化交付

  • 客户：企业培训部门、知识管理团队、连锁机构（大量标准化培训视频）
  • 痛点：培训视频命中率极低，人只能反复看；云 ASR 按分钟计费，长视频不经济；数据不能出内网
  • 实现方式：Dify + faster-whisper + Ollama + Qdrant 全本地，附质量闸门
  • 可能商业模式：私有化部署实施（项目制）+ 年度运维；差异化卖点是「零 API 成本 + 数据不出内网 + 坏了会报警」
  • 现实约束：只处理企业自有素材，避免第三方版权风险

机会 3｜LLM 流水线的「失效检测」专项服务

  • 客户：已经上线 RAG / 知识库 / 抽取流水线的企业
  • 痛点：系统「跑得挺好」，但没人知道它在哪一刻开始给错答案
  • 实现方式：照今日案例的闸门范式（截断 / 假通过 / 专名漂移 / 重复）做失效分析，把所有闸门改成 fail-closed，并建评测集与基线
  • 可能商业模式：专项咨询 + 后续可靠性培训。稀缺度高于「帮你搭一个 RAG」
  • 为什么现在：过去两年企业完成了「搭起来」，接下来一年会集中面对「搭起来了但不敢信」
