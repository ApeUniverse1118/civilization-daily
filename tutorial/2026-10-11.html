01｜案例是什么？

Lead Signal Listener 是一个本地的销售线索发现工具。它的定位一句话说清：「在竞争对手之前，找到那些正在公开描述『你能解决的问题』的人。」它监听 Reddit、X、LinkedIn 帖子、LinkedIn 招聘、Facebook 帖子与群组、Instagram 话题与 Reels、融资新闻、Hacker News、YouTube、新闻与 RSS——也包括 Treg 目录里的 3800+ 个数据端点，还能捕捉「正在招人」「刚拿到融资」这类触发信号。每条线索会被打分、去重、排队，你可以先看分最高的。评分规则是一份可编辑的 JSON，改完点一下就能对已有线索重新打分。整个工具跑在你本机，只监听 127.0.0.1，不联网托管。

02｜为什么今天值得关注？

  • 为什么是现在：2026-10-10 首次开源（北京 15:20），当天完成全部推送。它是本期窗口内唯一一个把「AI 销售自动化」做到可运行、成本可量化、且默认配置自带真实运行数据的开源项目（README 明确写出：默认关键词示例运行得到 284 条线索，花费 $0.073）。
  • 以前为什么不容易做：线索发现长期是两难：买现成的 B2B 数据服务（贵、且名单是通用的，不针对你的问题）；或者人工刷平台（不可能覆盖十个来源）。用 LLM 直接扫平台也走不通——成本高、结果不可复现、而且你无法解释「为什么这条排第一」。
  • 为什么现在变得容易：三个条件同时到位：① 公开内容的检索接口可以按次计费（Treg 这类聚合层把 Reddit / X / LinkedIn 等统一成一次调用 $0.0005–0.03）；② Hacker News、RSS 这些免费源本身就能承担冷启动；③ 规则引擎足够便宜——评分不用 LLM，用关键词规则就能筛掉 90% 噪音，把 LLM 留到「需要深入判断」的最后一步。

03｜案例的前世今生

前世。「监听公开讨论找线索」这件事本身不新——早年是舆情监控，靠关键词告警；后来是社交聆听工具，靠人工配置规则看板。痛点始终一样：监控结果是一堆帖子，不是一份可跟进的名单。销售拿到的还是噪音，得自己一条条看。

发展。LLM 出现后，第一波解法是「把帖子喂给模型判断是不是线索」。这条路线的代价很快显现：按条计费成本不可控、同一批数据跑两次结果不同（不可复现）、而且没法解释排序依据。于是出现了一个反向思路——把「可判定的部分」交还给规则，把「需要理解的部分」留给模型。

今生。2026-10-10，作者开源了这个项目，把上述判断落成了具体设计：评分完全基于规则（痛点短语、意图短语、人群词、互动量、是否提问、负面短语），透明、免费、可编辑；想更深入时，导出 JSON 交给 LLM 做资格判定，而不是让 LLM 从头扫一遍。同时它把成本控制做成了一等公民：单次调用上限、单次运行预算、1 小时内幂等重放不重复计费、token 失效或余额为零自动中止整次运行。
另一个值得记录的细节：作者在仓库里放了一份 docs/showcase.html，完整展示了「从想法到开源发布」的一次 AI 对话记录——项目本身被作者标注为「在一次 AI 对话中构建完成」（提交记录中多处共同署名为 Claude Opus 5.5）。这让本案例同时成为「AI 辅助开发」的一手样本。

下一步可能怎么发展（以下为分析 / 推演，非事实）：① 从「通用找线索」细化为垂直行业监听器（外贸、SaaS、跨境电商各有各的痛点短语库）；② 与 CRM 打通，形成「发现 → 跟进 → 记录」闭环；③ 评分规则库可能成为可交换的资产（谁来维护「什么叫高意向」的判断标准）；④ 国内替代路径是把 Treg 换成国内数据源，做本地化版本。

06｜解决了什么真实问题？

从使用者视角，问题非常直白：「我知道我的客户会在网上抱怨这个问题，但我没办法每天盯着十个平台看。」

  • 外贸与跨境服务：买家会在 Reddit / X 上直接描述痛点（「我们的物流成本又涨了」「有人推荐靠谱的供应商吗」），但这些帖子存在时间很短，错过就没了。
  • SaaS 与 B 端服务：高意向信号往往不是「我想买」，而是「谁能推荐一个工具」「我们正在找人做这件事」——这类表述有很强的时效性。
  • 招聘与融资触发：「正在招某个岗位」和「刚拿到融资」是最经典的采购前置信号，但需要有人持续盯着。
  • 现有工具的痛点：通用 B2B 名单不针对你的具体问题；舆情工具给你的是帖子不是名单；LLM 全量扫描成本不可控且不可解释。

08｜完整 Workflow

① 描述你在找谁（Listeners 页）：填写目标人群描述，勾选启用的来源，逐行添加关键词
↓
② 抓取（Listen）：按关键词并发查询各来源。免费源（HN / RSS）与付费源（经 Treg）混用；每个关键词每次运行最多抓 max_pages 页（Reddit / X 默认 3 页，LinkedIn 默认 2 页）
↓
③ 打分（Scoring）：纯规则匹配——痛点短语（如 "traffic dropped"）、意图短语（如 "looking for" "recommend an agency"）、人群词（如 SaaS vs DTC）、互动量、是否为提问、负面短语（自我推广 / 招聘贴 / 垃圾信息）
↓
④ 去重入库：store.py 写入 SQLite 并去重
↓
⑤ 人工审核：按分数排序，状态板切换 All / To review / Qualified / Contacted / Replied / Ignored，可加备注（Ctrl+Enter 保存）
↓
⑥ 输出：导出 CSV / JSON（GET /api/export?fmt=csv|json）
↓
⑦ 反馈调优（回路）：在 Listeners → Scoring rules 里用 JSON 改规则，点 Rescore all leads 对已有线索重新打分
↓
⑧ 可选：交给 LLM 深判：导出 JSON，交给 LLM 做更深入的资格判定（README 明确建议的用法）

内置成本控制机制（README 原文）：单次调用上限（由 Treg 通过 X-Treg-Route-Max-Cost 强制）、单次运行预算（达到即停止分页与后续付费调用）、幂等重放（同一查询 1 小时内重跑不重复计费）、自动中止（token 无效返回 401 或余额不足返回 402 时取消本次运行剩余部分）。花费与调用次数直接显示在 Leads 面板上。

09｜它到底是怎么实现的？

几个关键设计值得单独拆出来：

  • 为什么不用 LLM 打分（本案例最重要的判断）：三个理由——成本（按条调用不可控，规则免费）、可复现（同一批数据两次运行结果一致）、可解释（每条线索的分数来自哪几条规则命中，能指给人看）。把 LLM 推到最后一环（对已筛出的线索做深判），成本从「按条」变成「按需」。
  • 免费源承担冷启动：没有 Treg token 也能跑——Hacker News、RSS、Import 三条路径完全免费。这让工具可以先被试用、再决定是否付费扩容，是一处很聪明的产品设计。
  • RSS 是隐藏的万能接口：README 举例说明可用 Google Alerts、reddit.com/r/NAME/new/.rss、hnrss.org/newest?q=... 等——等于把任意平台的可订阅内容都变成了线索源，且零成本。
  • 安全设计（本地优先的完整实现）：服务仅绑定 127.0.0.1、检查 Host 头（阻止 DNS rebinding 攻击）、写请求必须带 JSON Content-Type、token 在界面上掩码显示且从不写入日志、所有数据留在 data/ 且被 git 忽略（README 明确警告「切勿提交或分享」）。
  • 可审计的架构：职责切得很干净——treg_client.py（HTTP 客户端 / 成本 / 上限 / 幂等）、sources.py（内置源与解析）、generic.py（RSS / 自定义端点 / 导入 / 目录检索）、scoring.py（规则评分）、store.py（SQLite + 去重 + 导出）、runner.py（一次监听）、server.py（本地 API + 调度）。
  • 无界面也能跑：python app.py --run-once 支持放到 cron 或 Windows 任务计划里定时执行；TREG_TOKEN 可走环境变量，密钥永不落盘。

12｜踩坑

坑 1 · 默认关键词只是示例。README 原文明确：默认关键词与评分规则只是一个例子（示例场景是「找那些在 AI 搜索可见性上有困难的公司」），必须换成你自己的目标人群与问题。直接拿默认配置跑，得到的线索跟你的业务无关。
坑 2 · 付费源的失败会中止整次运行。README 原文：token 无效（401）或余额为空（402）会取消本次运行剩余部分。首次配置时务必先 Verify。
坑 3 · 抓取深度有限。每个关键词每次运行受 max_pages 限制（Reddit / X 默认 3 页、LinkedIn 默认 2 页）。也就是说单次运行看不到全部公开讨论，需要靠定时运行累积。
坑 4 · 规则评分的边界。评分是规则化的、不是 LLM 原生判断，因此无法理解反讽、隐喻和上下文。README 给出的应对是导出 JSON 交给 LLM 深判——这也意味着「最后一道判断」仍然需要人工或额外的模型环节。
合规红线（README 明确写出）。原文要求：只采集公开内容，遵守各平台与 Treg 提供商的条款；这是「研究与线索发现工具，不是垃圾邮件加农炮」；触达时必须遵守 GDPR、CAN-SPAM 等规则。界面截图使用的是虚构演示数据，个人昵称已打码。

一句话结论：它是「企业开放 MCP 之后，个人开发者能做什么」这个问题目前最好的答案——不堆功能，只做一件事：把「这单到底该不该点」算清楚，并且宁可少报也绝不编造。

01｜案例是什么？

麦麦省钱助手是一个基于麦当劳中国官方 MCP 的点餐成本优化 Skill，做两件事。短期——这一单怎么点最省：拉取当前门店的实时菜单与价格、拉取你账户里当前门店可用的优惠券，枚举「单品 / 套餐 / 券组合 / 加购凑单」的候选方案，然后用 MCP 的 calculate-price 逐方案真实计价（而不是猜），输出最省方案，并解释「为什么不推荐那个更便宜但你吃不饱的选项」。长期——你白扔了多少钱：手上几张券即将过期（沉默成本）、近几个月花了多少、客单价是否偏高、哪些单品该改成套餐。作者的立场写得很直白：「别处都在帮用户花钱，我们在帮用户止损。」

02｜为什么今天值得关注？

  • 为什么是现在：2026-10-10 首次开源（北京 20:59），并于当天 13:00 提交参赛、13:59 获得官方回复「作品已成功参赛」。截至数据快照已 278★ / 19 Fork——在麦当劳 MCP 大赛涌现的 100+ 件作品中位居榜首（第一名）。它落在 10-11 期窗口内（10-10 期窗口截至 12:00，本案例创建于 20:59）。
  • 为什么以前不容易做：「帮你点得便宜」这类工具长期做不准，原因是价格和券的可用性都是动态的——不同门店不同价、券有适用范围与叠加规则、凑单要不要加购取决于你本来的消费意图。用模型去估这些数字，一定会编。
  • 为什么现在变得容易：麦当劳中国把点餐业务做成了 MCP（mcp.mcd.cn），开放了 query-meals、order-list、calculate-price、query-my-coupons、available-coupons 等工具。于是「价格」和「券状态」第一次变成了可调用的真实数据，而不是需要模型猜测的知识——这让整类「消费决策优化」应用变得可做。

03｜案例的前世今生

前世。「怎么点最省」是个长期存在的小需求。早期解法是人工整理的「省钱攻略」帖——但攻略是静态的：券会过期、价格会调、不同门店不一样，所以攻略写完就过时。后来出现过计算器式的工具，但需要用户手工录入价格和券，录入成本高且容易错。

发展。MCP 出现后，企业把业务能力开放成工具，出现了新可能：工具可以直接查真实菜单、真实价格、真实券包。但随之而来的是一个新问题——很多团队会用模型来「估算」价格和券价值，因为那样实现最简单。这恰恰是这类应用最不能犯的错：算错钱的助手比没有助手更糟。

今生。2026-10-10，作者开源了这个 Skill，它的核心选择非常明确：「杜绝模型幻觉价格」是设计前提。作者把「券到底值多少钱」拆成两条可验证的路：首选是把券的商品码 + couponId 传给 calculate-price，返回的 discount 就是精确价值；兜底是从菜单反查原价（满减券取减免额、买一送一取商品单价、免费券取商品单价、固定价券取「菜单原价 − 固定价」）。两条路都走不通时，一律取 0 并标注「价值未知」，绝不估算。
更值得注意的是它引入了一个别处少见的概念——券的净价值：净价值 = 券面价值 − 为用这张券、你本来不会花的那部分钱。由此把券分成四类：顺手可用 / 努一把 / 纸面富贵（明确劝退）/ 无法判断。一个「帮你省钱的工具」主动劝退，这是它区别于同类的地方。

下一步可能怎么发展（以下为分析 / 推演，非事实）：① 同样的「净价值 + 排程」框架可迁移到外卖、电商、机票、酒店、会员权益——凡是「券 / 权益 + 约束条件」的场景都适用；② 成为跨平台的消费决策层（一个地方管所有平台的券）；③ 企业侧反向应用：品牌可以用同一套净价值逻辑评估自己的券策略是否在制造「纸面富贵」。

06｜解决了什么真实问题？

从消费者视角，问题是这样的：「我手里有一堆券，但我不知道哪张该现在用、哪张其实不值得为它多花钱；我甚至不知道我每个月因为券过期白扔了多少钱。」

  • 信息不对称：券的价值不是面值。「满 40 减 10」看起来值 10 元，但如果你本来只想花 25 元，为了用这张券你得多花 15 元——这张券的净价值可能是负的。这是绝大多数「省钱工具」都算不清的地方。
  • 动态数据：不同门店菜单与价格不同，券的适用范围不同，所以任何静态攻略都会失效。
  • 沉默成本：券会过期，过期就是损失，但没人提醒你「哪张券你其实用不上了」。
  • 决策疲劳：套餐 / 单品 / 加购 / 券组合的排列组合很多，人算不过来。

09｜它到底是怎么实现的？

这个项目最有价值的不是算法，而是三条自我约束：

  • 约束一：不用模型估价，用官方接口计价。券的价值首选走 calculate-price（返回 discount 即精确值）；兜底才从菜单反查原价（满减券取减免额、买一送一取商品单价、免费券取商品单价、固定价券取「原价 − 固定价」）；两条路都走不通时一律取 0 并标注「价值未知」。作者的原话是「宁可少报，不可编造」。
  • 约束二：不知道就不说。两个刻意的克制写在了 README 里：① 不输出券的剩余天数——因为有效期未知，套用 expiry_text() 会把 None 说成「无期限」，那是编造；② 不擅自替用户领券——auto-bind-coupons 是写操作，必须取得用户明确同意。
  • 约束三：券状态不认识就排除。available-coupons 的状态只有「已领取 / 可领取」两种；没见过的状态一律判「无法识别」并排除——宁可漏报，不可误报。

另一个值得记录的工程细节：作者在 MCP_INTEGRATION.md 里写出了官方文档没写、但跑通链路必需的 12 条实测调用契约，包括「门店查询的必传参数」「calculate-price 的字段名」「分 vs 元：两个接口方向相反的坑」。这份文档本身就是本案例最有价值的可复用资产——它记录的是「文档与实现之间的缝隙」，是下一个开发者最需要的东西。作者还做了自纠：文档里曾把契约条数写成 17（实际 19）、把「三种券型」写旧（实为四种：满减 / 买一送一 / 免费 / 固定价），都在后续提交中修正，并在 README 中公开了这些不一致。

12｜踩坑

坑 1 · 官方文档没写的关键契约。作者指出有 12 条「文档没写但跑通链路必需」的实测契约，其中包括「分 vs 元」两个接口方向相反的坑。这是接入任何 MCP 都会遇到的典型问题——文档描述与实现之间存在缝隙，只能靠实测补齐。建议：接入前先对着 MCP_INTEGRATION.md 核对，别自己重新踩一遍。
坑 2 · 免费券可能被高估。作者明确写出：若某张券实际要求「随单购买」，券面并无体现，此时会高估净价值。这条限制被写进了 docstring 与契约文档——属于作者已知但未解决的口径问题。
坑 3 · 可领取券信息不完整。available-coupons 不返回 couponId、面值与有效期，因此无法用带券计价实测、也无法参与用券排程。作者的处理是把它降级为「该不该领」的框架复用，而不是硬塞进排程。
坑 4 · 排程建立在假设之上。用券排程有三条假设：窗口内本来就会点 K 单、每单最多用 1 张券、用券不改变点单次数。作者明确说明「自然消费基准」取自历史订单客单价，是保守近似而非精确值，且假设写在报告里。（本报告补充：依赖历史客单价意味着新用户的排程结果可信度更低，这一点原文未特别提示。）
坑 5 · 数据口径不一致（作者已自查）。README 与 MCP_INTEGRATION.md 中「实测调用契约」的条数曾出现 12 / 17 / 19 三处不一致，另有「三种券型」的表述过期（实为四种）。作者已在后续提交中修正并公开说明。本报告在引用时采用其修正后的口径，并标注此处曾存在不一致。

今日 AI 实战观察

把今天这两个案例放在一起看，会看到同一个问题被从两个方向回答了：AI 给出的答案，凭什么可信？

lead-signal-listener 的回答是「把可判定的部分从模型手里拿回来」。它的评分完全基于规则——痛点短语、意图短语、人群词、互动量、是否提问、负面短语——不用 LLM 打分。理由很实际：按条调用模型成本不可控、同一批数据跑两次结果不同、而且没法向人解释「这条为什么排第一」。规则打分是免费、可控、可复现、可解释的；模型被推到最后一环，只对已筛出的线索做深判。这一步让整件事的成本从「按条」变成「按需」，也让「为什么是这条」这个问题有了答案。

mcd-coupon-strategist 的回答更硬核：「宁可少报，不可编造。」它坚持用官方接口的真实计价替代模型估价，做券的价值换算时明确接受「有两条路都走不通」的情况，此时一律取 0 并标注「价值未知」。它还主动放弃了两件「看起来更聪明」的事：不输出券的剩余天数（因为有效期未知，说了就是编）、不擅自替用户领券（那是写操作）。一个帮人省钱的工具，甚至专门设计了「纸面富贵」这一档来明确劝退用户。

两个案例的技术难度都不高，但都做出了一个在 2026 年越来越重要的判断：在要付钱、要发消息、要下单的场景里，可信度本身就是产品力。过去两年大家比的是「AI 能不能做到」；现在比的是「AI 敢不敢说自己做不到」——因为前者靠模型能力就能解决，后者需要设计者放弃短期的好看。

对个人开发者来说，这里有一条很具体的启示：你的差异化机会，往往不在「让 AI 多做一点」，而在「让 AI 在某个地方明确停下来」。算不准就不说，不确定就不判，不认识就排除——这三句话可以直接写成你项目的设计原则。

机会 1 · 「意向名单」订阅服务

  • 客户：外贸公司、SaaS 销售团队、跨境服务商、自由职业者
  • 实现方式：用公开信息监听（本项目架构）+ 行业化的高意向表述规则库 + 每周交付一份可跟进名单

  • 为什么现在：工具层面的门槛已经降到 git clone + 一条命令，稀缺的是「这个行业的人怎么说话、什么话代表真需求」这类知识，而这类知识只有做过这行的人才有
  • 合规前提：只采公开内容、遵守平台条款与个人信息保护法规、绝不群发。这一点必须写进交付说明

机会 2 · 「真实数据优先」的 AI 应用改造

  • 客户：已经做了 AI 应用、但因为「AI 算错 / 编数据」被业务方质疑的团队
  • 实现方式：盘点流程中所有「由模型猜测」的数字与状态，逐个替换为可调用的真实接口；无法获取的直接标注为未知
  • 可能商业模式：改造项目制 + 开发规范咨询

机会 3 · 权益与优惠券的诊断服务

  • 客户：连锁餐饮 / 零售品牌的会员运营部门、会员权益平台
  • 实现方式：用「净价值 = 券面价值 − 为用这张券你本来不会花的钱」这一框架，反向诊断一套券策略里有多少属于「纸面富贵」
  • 可能商业模式：券策略体检报告（项目制）+ 后续按月复诊
  • 为什么有需求：传统核销率分析回答不了「为什么发了券但复购没起来」，而净价值视角能指出「你的券在诱导用户做他本来不想做的事」，这是运营真正想知道的答案
