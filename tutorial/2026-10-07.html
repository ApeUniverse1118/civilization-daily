用一个开源浏览器 Agent（ReAct + MCP + 多 Agent）把写好的 Markdown 自动发到掘金与知乎，并让它自己写完自己的项目 Wiki

AI Agent / 浏览器自动化 MCP 实战 AI + 内容运营 一手原文 10-06 / 10-07 开源 MIT 项目 Star 仅 13，热度低
一句话结论：它真正的价值不在「能点页面」，而在于把中文编辑器那些刁钻的注入姿势一个个踩清楚并公开了。

01｜案例是什么？

一位中文独立开发者 xiwc 开源了一个浏览器扩展 AI Helper（Chrome / Edge，MIT）：它让大模型在你的浏览器里真的动手——点击、填表、拖拽、上传文件、跑终端命令，并通过 MCP 协议扩展能力。10-06 他写了篇实战文，讲怎么用「一个主助手 + 三个子助手」把写好的 Markdown 自动发布到掘金与知乎；10-07 另一位作者 weFri 在 InfoQ 记录：用同一个插件，让它自己把项目 Wiki 从零写成 8 页中文 + 8 页英文，并同步到 Gitee。项目在 10-08 发布 v2.0.0。

02｜为什么今天值得关注？

  • 窗口内的事实（可核实）：AI Helper 在 48 小时窗口内连续发布 5 个版本——v1.17.4（10-06 20:49）、v1.17.5（10-06 21:01）、v1.17.6（10-07 11:49）、v1.17.7（10-08 08:43）、v2.0.0（10-08 08:56）；两篇一手实战记录分别落在 10-06 与 10-07。
  • 为什么以前不容易做：浏览器自动化长期是「写代码的人的活」（Playwright / Selenium / 油猴脚本），选择器一变就全废，普通内容创作者根本碰不到；而中文平台各有各的富文本编辑器内核，通用方案一注入就乱码、丢字、串位。
  • 为什么现在变得容易：① 浏览器扩展 + LLM 把「操作网页」变成了自然语言；② ReAct 循环让 Agent 自己决定下一步调哪个工具，而不是人预先写死流程；③ MCP 让「浏览器控制 / 文件读写 / 命令执行」从内置绑定变成可插拔工具；④ 有人把中文编辑器的坑逐个踩完并写成文章。
  • 为什么值得花时间：「AI + 内容」这个方向在中文一手来源里长期稀缺（过去多期由内容农场垄断），这次是少见的、带真实代码与真实踩坑的执行记录。

03｜案例的前世今生

前世。2023–2025 年，浏览器自动化的主体是程序员写的脚本：selenium 到 Playwright 再到油猴脚本，共同点是「人先假设页面长什么样，再写选择器」。页面改版 = 脚本报废。早期「AI + 浏览器」也只是让模型生成选择器，本质仍是脚本，换不来鲁棒性。

发展。四条线先后成熟：① 长上下文与多模态让模型能读 DOM、也能看截图；② ReAct 范式（Thought → Action → Observation）把「想一步、做一步、看结果、再决定」变成可循环的工程结构；③ MCP 在 2025 年成为事实标准后，浏览器控制、文件读写、终端执行可以统一挂成工具；④ Chrome 扩展作为载体，绕开了「让普通用户先装 Python 环境」这道硬门槛。

今生。AI Helper 没有发明新模型，做的是「把上述零件装进一个浏览器扩展，并把 AI 操作中文网页的工程细节做到可用」。作者的公开记录里有两条真实使用路径：内容分发（知乎 Draft.js / 掘金 ByteMD）与文档自动化（项目 Wiki 双语化 + Gitee 同步）。这两条路恰好一份覆盖 B 端、一份覆盖个人创作者。

下一步可能怎么发展（分析 / 推演）。浏览器 Agent 会从「帮你点一个页面」走向「帮你守一个流程」——定时盯页面、变化告警、异常自动处理；企业侧可能出现「内部系统操作 Agent」，把没有 API 的老系统（老 ERP、老 CRM 网页端）用浏览器 Agent 兜住。以上为推演，非事实。

06｜解决了什么真实问题？

这个案例要从需求侧看，不从技术侧看。

需求一（内容创作者）。一个同时维护掘金、知乎等多阵地的创作者，一篇稿子写完只是开始：复制粘贴到各平台编辑器格式经常乱、代码块要重贴一遍缩进全丢、每个平台的话题与标签规则不同、发布前还得反复核对分类封面摘要。作者的原话是这些活「重复、机械、还容易出错，典型该被自动化」——他要的不是「AI 帮我写」，而是「AI 帮我把写好的东西发出去」。

需求二（开源维护者）。项目 Wiki 从零写到双语、还要同时维护 GitHub 与 Gitee 两套，纯手工极其耗时。InfoQ 那篇记录的场景是：Wiki 是空白页，要基于源码写一整套文档，还要英文版与跨平台同步。

两者的共同点：不是「不会写」，而是「不值得人写」——重复、规则明确、量大、错了要重来。

09｜它到底是怎么实现的？

剥开业务内容，这套流程真正的技术内核是三个机制（均来自原文自述）：

机制一：能力抽象 —— 工具原子化，流程交给 Agent。原文的原话是「关键在于：把『能力』抽象成工具，把『流程』留给 Agent 自己规划。这样换一个平台，只要加一个工具，不用改整套逻辑。」这是浏览器自动化与「写死的 Playwright 脚本」最本质的分野：确定性交给工具，不确定性交给规划。

机制二：注入要因地制宜 —— 先侦察编辑器内核，再选方法。这是原文踩坑最多、也最有迁移价值的部分。同样叫「编辑器」，底层实现天差地别，用错方法就是白干（原文给出的对照表）：

Draft.js伪造 ClipboardEvent('paste')。直接改 DOM 或 execCommand 会和它内部状态打架，表现为文字串位、莫名删除
CodeMirror / Monaco拿实例调 setValue()。掘金切到 Markdown 模式后是 ByteMD，内核 CodeMirror 5，直接写最稳
原生 textarea直接赋值 + 触发 input 事件
contenteditable谨慎，优先走粘贴事件
// 原文给出的知乎（Draft.js）注入方式
const dt = new DataTransfer();
dt.setData('text/html', html);   // 保留标题、列表、链接
dt.setData('text/plain', plain); // 兜底纯文本

editor.dispatchEvent(new ClipboardEvent('paste', {
  clipboardData: dt,
  bubbles: true,
  cancelable: true
}));
// 原文给出的掘金（ByteMD / CodeMirror 5）注入方式
const inst = document.querySelector('.CodeMirror').CodeMirror;
inst.setValue(markdownText);

机制三：编排要扁平 —— 平台的硬限制决定了架构形状。原文明确写到：平台对子助手的嵌套分派最多 2 层（主 → 子 A → 子 B 可以，子 B 再往下派就会被拦）。所以「编排层要尽量扁平，别指望无限套娃」。这条限制直接决定了主助手必须自己承担决策，而不能层层下放。

此外还有一条工程纪律（来自 InfoQ 那篇）：不是「生成完就交」，而是「生成完逐页核对」。作者发现原文档写 9 个标签页、实际只有 7 个，且知识库 RAG 整页漏掉——这类「文档与代码不一致」是 AI 写文档最容易出的错，所以必须回到源码交叉验证。

10｜手把手复现

以下 Step 1–3、5–6 整理自两篇原文明确写出的做法；Step 4 为原文架构图的直接还原；Step 7–9 为本文补充的建议，已单独标注。作者未提供完整的「从零到发布」编号教程。

Step 1（原文）。安装扩展：Edge 用户走扩展商店；Chrome / Chromium 用户下载 Release 里的 ai-helper-*.zip 解压，打开 chrome://extensions/ → 开启右上角「开发者模式」→「加载已解压的扩展程序」→ 选择解压后的文件夹。发布记录说明该产物由 GitHub Actions 自动构建。

Step 2（原文）。配置模型 provider：在扩展里保存一个 OpenAI 兼容配置（端点 / 密钥 / 模型列表）。可选多家，切换时先选 provider 再选模型。

Step 3（原文）。挂 MCP 工具：把「浏览器控制（点击 / 输入 / 执行 JS）」「文件读写」「命令执行」按需挂上；若要让 Agent 碰本地文件与终端，装可选的本地 Agent 服务（原文提到三级命令安全策略）。

Step 4（原文架构图还原）。建一个主助手负责编排，再建三个子助手：A 浏览器自动化、B 内容处理、C 数据回收。注意保持扁平——不要试图三层以上嵌套。

Step 5（原文）。先侦察目标编辑器的内核，再决定注入方式：查 .CodeMirror 之类特征判断是不是 CodeMirror；拿不到实例再退到伪造 paste 事件。

Step 6（原文）。每一步都加断言：填完一步就校验 DOM，别等最后才发现某步没生效；出错优先点编辑器的「撤销」按钮回退，比强行改 DOM 安全。

Step 7（本文补充的建议）。第一次只跑单平台、单篇文章：把「打开编辑器 → 注入 → 选标签 → 停」跑通，先不让它点发布。

Step 8（本文补充的建议）。把发布、删除、修改状态这类不可逆动作设为人工确认。原文自己的终点也是「一句话 + 一次确认」——即最后那一下是留给人的。

Step 9（本文补充的建议）。把中文标签映射成平台实际提交的 value（原文踩坑第 3 条），先建一张映射表再动手，而不是让 Agent 现场猜。

12｜踩坑

以下均为两位作者在原文中自述的踩坑，本文未独立复现：

  • 键盘输入 ≠ 可控：某些编辑器上「全选 + 输入」会清空全文，务必先确认光标位置。
  • CDP 的 Input.insertText 不通用：对 Draft.js 无效，对 CodeMirror 却好用，别一刀切。
  • 中文选项要映射成 value：表单里的中文标签，实际提交的可能是英文 value，先建映射表再动手。
  • 每步都要断言：填完一步就校验 DOM，别等最后才发现某步没生效。
  • 出错先撤销：优先点编辑器的「撤销」按钮回退，比强行改 DOM 安全。
  • 知乎粘贴后第 0 个块会丢文字：需要事后把光标移回去补一次。
  • 嵌套分派最多 2 层：子助手再往下派会被拦截，编排必须扁平。
  • Gitee 与 GitHub 的 3 个差异：_Sidebar/_Footer 不被 Gitee 识别（被当普通页显示，只能删除）、侧边栏按字母排序无分组、带锚点 URL 不自动滚动（需点页内链接才滚动）。
  • macOS bash 3.2.57 的坑：set -u 下 $VAR 紧跟全角括号会把首字节并入变量名（报 WORKDIR unbound variable），统一改成 ${VAR} 花括号规避。
本文补充的风险提示（非原文）：这类浏览器 Agent 是以你的浏览器登录态、用你的账号权限在网页上操作的。它能替你点「发布」，也能替你点到别的东西——把不可逆动作纳入人工确认，不是保守，而是必须。另外，为 Agent 开启本地文件与终端能力时，请先读一遍它的三级安全策略具体拦了什么。

产品化。不是重做一个浏览器 Agent（那是红海），而是把「某个垂直场景的稳定操作流」做成可交付物：例如「一篇稿子自动分发到 5 个平台（含格式适配与标签规则）」的预设包 + 使用说明。交付即用、不需要服务器。

咨询化。帮企业找「哪些网页操作值得自动化」——尤其是没有 API 的老系统。这一步最难也最值钱：找错流程，Agent 就是个更慢的手动操作。

01｜案例是什么？

一位中文开发者开源了 agentic-kb（MIT，Python）：一个面向中文规程文档的本地知识库智能体。它把检索做成「稠密 + 稀疏」两路并用——用 bge-m3 一次前向同时产出两路向量，服务端做 RRF 融合，再用 bge-reranker-v2-m3 重排；在此之上加了 GraphRAG 与「上下文定位语」，让答案里的 [文档名 (块 3)] 可以点回原文块。它还做了版本化索引：规程换版后旧版本默认不再召回，需要时可显式翻出废止条款。检索侧全部本地推理，只有问答与联网搜索走外部 API。

02｜为什么今天值得关注？

  • 窗口内的事实（可核实）：该仓库创建于 2026-10-07 09:29（北京时间），同日 09:56 完成最后推送；当前 58 Star / 1 Fork；MIT 协议；带完整目录结构（agent / api / embed / eval / frontend / ingest / llm / retrieve / store）与四份文档（usage / architecture / evaluation / gotchas）。
  • 为什么是现在：企业 RAG 的讨论已经从「怎么检索到」转向「怎么证明它检索得对、怎么管住它的写操作」。这个项目罕见的把「评测设施」和「审计日志」当成一等公民，而不是事后补。
  • 为什么以前不容易：① 中文规程文档有天然难点——条款要能溯源（答错是安全事故）、换版频繁（废止条款还得能查）、代词密集（「该系统」「上述参数」单看一块判断不出在说什么）；② 通用 RAG 方案对这三件事基本不处理；③ 让 Agent 自己调写工具，企业最怕的就是「它擅自改了状态还查不出来」。

03｜案例的前世今生

前世。2023–2024 年的企业知识库主流是「切块 → 向量化 → 余弦相似度召回 → 丢给模型」。它有一个被反复吐槽的天花板：检索不可解释（为什么召回了这一块？）、不可控（换了版本旧条款还在召回）、不可审计（谁改了什么不知道）。对规程类文档，这三条都是硬伤。

发展。三条技术线先后成熟：① 混合检索成为共识——稠密向量负责语义、稀疏向量负责关键词，中文术语与编号（如条款号）靠稀疏那一路才稳；② 重排器（cross-encoder reranker）把粗排结果精排，显著改善「召回对但排得差」；③ 上下文增强（Contextual Retrieval）在入库时给每块补一句「它在原文什么位置、讲的是哪件事」，专门救代词密集的段落；④ GraphRAG 补上多跳关系。

今生。agentic-kb 把上述零件装成一个可本地运行的整体，并额外做了三件企业关心的事：版本化索引（status / doc_version / effective_from 落在 payload 上）、可溯源问答（答案里的块引用可点开原文）、受控写工具（默认全关 + 三道闸 + 审计日志）。作者还自建了一套评测集来量化每个改动的收益，而不是靠「感觉变好了」。

下一步可能怎么发展（分析 / 推演）。这类「可溯源 + 可版本化 + 可审计」的知识库形态，很可能会成为企业合规与安全生产领域的基础设施；下一阶段的竞争点可能从「检索精度」转向「变更治理」——规程改版后如何自动标记影响范围、如何生成差异报告。以上为推演，非事实。

09｜它到底是怎么实现的？

四个值得抄的工程决策：

决策一：混合检索用「一次前向」而不是两个模型。bge-m3 一次前向同时产出稠密与稀疏两路向量，服务端做 RRF 融合，再交 bge-reranker-v2-m3 重排。作者公开了自建评测集上「重排关 / 开」的差值（其余配置完全相同）：hit@1 0.867 → 1.000、MRR@1 0.867 → 1.000、nDCG@1 0.790 → 0.962、recall@1 0.678 → 0.811，其中 contextual 类题 0.500 → 1.000。

决策二：上下文定位语（Contextual Retrieval）单独量化。只在「入库时给每块补一句位置与主题」这一个变量上做对照（重排关）：hit@1 0.800 → 0.867。作者的解释很朴素——代词密集的段落靠定位语补全语义、靠重排救回来。这是「为什么要多花一次 LLM 调用」的直接证据。

决策三：版本过滤挂在两条召回路径的共同出口上。两条召回路径共用同一套分块，版本过滤同时挂在那两条上；而 mark_superseded 改的 status 字段，正是那道过滤读的那个字段。作者还处理了兼容性：加字段前入库的老数据按 current 处理，不报错也不漏。

决策四：写工具默认全关 + 三道闸 + 审计日志。export_report / mark_superseded 是仅有的两个写工具，需经「白名单 → 显式确认 → 参数校验」三道闸，且默认全部关闭；每次调用向 logs/audit.jsonl 追加 intent / result / denied 三条记录。这是把「Agent 能不能改知识库状态」这个责任问题用工程手段回答。

其他设计取舍（作者在 architecture.md 中说明）：图的写入不用 LlamaIndex；ReAct 走文本协议而不是 function calling；并发被限成 1。前两条本文不转述未核实的理由，第三条与「本地单机推理、避免显存争抢」的常见工程判断一致。

17｜如何变成一个赚钱的项目？

产品化。把 agentic-kb 作为内核，做成「某行业规程知识库」的一体机 / 私有化部署包：预置该行业的文档处理规则（编号体系、条款层级、版本规则），客户导入自己的文档即可用。卖点不是「AI 问答」，是「可溯源 + 可审计」。

服务化。给企业做知识库的实施与调优：文档清洗、分块策略、评测集共建、检索参数调优。这类服务有一个天然优势——它需要行业知识，不是纯技术外包。

咨询化。帮企业做「知识资产治理」：哪些文档该入库、版本怎么管、废止条款怎么追溯、谁有权改状态。这是 IT 与业务部门之间的空白地带，也很少有人能做。

培训化。课程价值极高：它可以把「企业级 RAG 与 Demo 级 RAG 的差别」讲得非常具体——混合检索为什么必要、重排为什么值那一次调用、评测集为什么必须自建、写工具为什么要三道闸。学员带走的是判断力。

内容化。拆成系列：一次前向出双路向量是怎么做的 / 上下文定位语值不值一次 LLM 调用 / 版本化索引怎么设计 / Agent 的写工具该不该默认关闭。每一篇都是企业技术选型时会搜的问题。

行业化。把「行业文档规则包 + 评测集 + 检索参数基线」沉淀成行业资产，一个行业一套。行业越多，复利越明显——这也是这类项目最容易形成壁垒的地方。

已验证 vs 推导：可核实的只有「仓库存在且 MIT 开源」「创建与推送时间在 10-07 窗口内」「作者公开了上述技术方案与自建评测数据」这些事实。作者未公开任何商业使用或收入信息；以上所有变现路径均为基于案例结构推导出的潜在商业模式。

案例 01 里，浏览器 Agent 的价值不在「它能点页面」——能点页面的工具早就有了。真正让它可用的是那些琐碎的证据：Draft.js 只认 paste 事件、CodeMirror 直接 setValue、粘贴后第 0 个块会丢字、每步都要断言、出错先点撤销。这些不是模型能力，是工程经验。作者甚至把发布这一步留给了人工确认——终点是「一句话 + 一次确认」，而不是全自动。

案例 02 更直白。它几乎是在回答一个问题：在规程这种答错就是事故的场景里，AI 凭什么可以被信任？ 答案不是「换更强的模型」，而是四件很笨的事：答案里的块引用能点回原文、旧版条款默认不召回但可显式翻出、写工具默认全关且过三道闸、每次调用都留审计记录。作者还自建了评测集，把「重排开了 hit@1 从 0.867 到 1.000」这种数字连同口径和小样本的局限一起摊开——这本身就是一种证据链。

更值得注意的是两边都主动承认了边界。案例 01 的作者写明了嵌套分派最多两层、写明了哪些坑他踩过；案例 02 的作者写明了评测语料是自造的、不是正式标准原文，甚至专门建了一份文档说明「失败方式几乎都是不报错」。

对个人开发者来说，这落在两件具体的事上：一是把「不确定的流程交给 Agent、把确定的动作做成工具」这个分工真正做出来；二是先建评测集再改参数。两件事门槛都不高，但都需要先接受一个前提——AI 从「能演示」走到「能交付」，中间隔着的不是模型，是证据。

今日商业机会雷达

机会 1｜「无 API 系统」的网页操作自动化

  • 客户：仍在用老 ERP / 老 CRM / 老 OA 的传统企业（尤其是制造业、政务、医药）
  • 实现方式：浏览器 Agent（ReAct + MCP 工具）+ 编辑器 / 表单注入适配 + 不可逆动作人工确认
  • 解决的是：「系统没有 API，但人每天要在这上面重复操作两小时」这个具体成本
  • 可能商业模式：项目制实施 + 按系统数量的年费维护

机会 2｜行业规程 / 合规知识库的私有化交付

  • 客户：安全生产、法务合规、医疗器械、金融内控等强合规行业
  • 实现方式：混合检索 + 重排 + 版本化索引 + 可溯源答案 + 写工具三道闸 + 审计日志
  • 解决的是：「答错是事故」的场景里，AI 凭什么能被采信——即责任与审计问题，而不是效率问题
  • 可能商业模式：私有化部署项目 + 年度运维 + 行业规则包授权

机会 3｜「浏览器 Agent 注入姿势」的知识产品

  • 客户：所有在做 RPA / 自动化 / 内部工具的技术团队
  • 实现方式：把「编辑器内核 → 注入方式」的映射做成可查手册与代码片段库，按系统类型持续扩充
  • 解决的是：自动化项目里最耗时、最不体面、也最难外包的那一段调试工作
  • 可能商业模式：手册 / 代码包一次性售卖 + 社群订阅 + 配套培训

今日「个人变现机会」

如果一个人每天投入 2–4 小时，今天这两个案例分别对应一条路径：

路径 A（内容侧，源自案例 01）。把「浏览器 Agent + 某个平台的操作流」做稳定，然后横向复制到更多平台。这条路径的独特之处在于：它不需要客户、不需要报价、不需要交付会议，你自己的账号就是第一个用户。建议的起手式是——先攻克一个平台（含注入方式与校验），再横向铺开；同时把踩坑过程本身写成内容，形成第二份资产。

路径 B（企业侧，源自案例 02）。选一个强合规行业，用 agentic-kb 这类内核 + 自己做该行业的规则包与评测集，从「帮一个部门把文档管起来」开始。这条路径的门槛更高（要本地环境、要行业语料），但它的壁垒也更实——行业知识不是下载来的。建议的起手式是：先用公开文档跑通全流程，再拿下一个真实部门做试点。

不建议做的：① 同时铺开三条以上路径；② 在没建评测集的情况下反复调 RAG 参数（那只是在猜）；③ 把不可逆动作（发布、删除、改状态）交给 Agent 而没有人确认环节。

不承诺收益，也不虚构收入。以上为基于今日案例结构推导的方向，未经验证。
