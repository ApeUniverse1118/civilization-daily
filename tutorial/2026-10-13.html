把《党政机关公文格式》国标变成可执行代码：gongwen-kit 让公文出稿当场过三道机检

垂直行业工具 Agent Skill GB/T 9704-2012 本地离线 首版 2026-10-13 24★ / 5 Fork
一句话结论：把“公文版式国标”从人力经验变成机器规则，写稿人只管内容、数字对不对得上交给机检——这是党政机关与央国企最刚性的场景里，第一份开源可复现的实现。

01｜案例是什么？

gongwen-kit 是一个 Node.js 工具包（同时是一个 Agent Skill）。它做三件事：生成——按 GB/T 9704—2012《党政机关公文格式》产出标准 Word 公文（通知、报告、请示、函、纪要、管理办法、条例），包含红头、发文字号、签发人、版记、附件页等全部构件；机检——每份稿子写盘后自动跑三道机器检查（体例 / 数字自洽 / 文风），哪一道不过就非零退出，不算出稿；修复——手写的、旧模板出的、别人发来的 .docx 也能整份修，版式直接改、体例改动写成 Word 修订痕迹逐条接受或拒绝、数字问题只插批注不替人改数。整个过程完全在本机跑，安装后不联网。

02｜为什么今天值得关注？

  • 为什么是现在：2026-10-13 首次开源，当天 8 次提交、连出 v0.2.1 → v0.3.1 四个版本（GitHub 提交与 Release 时间戳已逐条核对），说明不是“一次性 Demo”，而是一天内被真实使用反馈推着迭代。
  • 以前为什么不容易做：公文工具长期卡在两处——版心、红头、双线这类尺寸“看着差不多”，但差 0.5mm 就不符合国标且没人能证明；改别人的稿子只能靠人工重排，无法把改动变成可审计的修订痕迹。这两件事都要落到 OOXML 层面才有解。
  • 为什么现在变得容易：① docx / jszip / sax 这类库已能精确控制 Word 底层结构；② Agent Skill 形态成熟，工具可以挂进 Claude Code / OpenCode / Codex 等宿主，由模型负责“写内容”、代码负责“量尺寸”；③ 涉密与内网合规让“本地离线”从加分项变成硬门槛，而本项目的定位正是“文件进文件出、不联网”。

03｜案例的前世今生

前世。GB/T 9704—2012 是 2012 年发布的国家标准，配套依据还包括《党政机关公文处理工作条例》（中办发〔2012〕14 号）以及 GB/T 15834（标点）、GB/T 15835（数字用法）等。十几年来，公文排版的主流解法是“WPS/Word 模板 + 人力校对”：模板解决版式，错字与体例靠人一页页看；数字对不对得上（正文说“以下三点”只列了两点、表格合计与分项不符、同一指标多处取值不一致）几乎全靠经验。

发展。过去几年，大厂与开源项目在“按国标排版”和“查错别字”上都有投入——作者自己在 README 里承认“有的版式比本仓全”，并附了一张横向对比图（标注来源为各厂商官网与公开资料、2026-10-13 核对、厂商口径）。这条赛道的缺口不在版式，而在跨段落的“数字自洽”检查和把修改变成可审计的修订痕迹。

今生。2026-10-13，作者 imhuhe 把仓库首版开源（MIT），并在同一天把这两件事都做进了仓库：checks/check-num.js 做数字自洽（分段求和、比率行列不加总、跨表同一指标、正文列举条数），lib/fix/revisions.js 把体例修正写成 Word 修订。关键尺寸不再是“目测”，而是用渲染后量测脚本出数：版头标志上缘距版心 35.05 mm（标准 35）、信函双线长 170.01 mm（标准 170）——量测脚本与全部校准值都写在 docs/版式.md。

下一步可能怎么发展（以下为分析 / 推演，非事实）：① 接入内网或本地部署模型，让“起草 + 排版 + 机检”整条链不出网，这是涉密单位唯一能接受的形式；② 机检报告落盘成合规凭据、对接 OA 流转审批；③ 从“单机工具”变成“部门级文书质量门禁”。

06｜解决了什么真实问题？

从用户需求出发，而不是从 AI 技术出发——三类人每天被同一件事消耗：

  • 机关与事业单位的文书岗：一份通知退回来，往往不是内容不行，而是版心、层次序数、发文字号括号用错（该用〔〕写成【】）、成文日期编了虚位（“05 月 08 日”应为“5 月 8 日”）。改一处就要重排一遍。
  • 央国企的部门写稿人：日常最多的是非红头的企业内部报告、请示、工作方案。这类文书没有现成模板，格式全靠“前人留下的稿子”抄，抄错就一错一片。
  • 所有需要“数字对得上”的人：正文写“以下三个方面”，后面只列了两点；表格合计与分项对不上；同一指标在正文与表格取值不一致。这类错人力最容易漏，也最容易被上级一眼抓住。

再加一条隐性刚需：涉密材料不能上传到云端工具。本项目的“本机运行、安装后不联网”直接命中了这条边界。

09｜它到底是怎么实现的？

  • “版式可证明”靠量测，不靠目测。tools/measure-banji.py、measure-letterhead.py、measure-xinhan.py 在 Word 渲染出 PDF 后测量实际尺寸，把校准值写进 docs/版式.md；遇到字体回退（没装方正小标宋）时脚本拒绝出数，避免用错基准。
  • 修复分三档，是刻意设计的安全边界。lib/fix/ 下 ooxml.js / runs.js / layout.js / revisions.js / comments.js / text-rules.js 各管一层：版式直接改；体例与规范层文风写成修订痕迹；数字与需要判断的项只插批注。“全部拒绝修订，正文逐字等于原文”——作者把可逆性写成了硬约束。
  • 机检用“双向标本”防误报。每条规则都配一份“必错的标本”做负对照（规则报不出来测试就失败），靠标签匹配、可能误报的规则只提示不拦稿，另有“必过的标本”防误报。这是工程质量意识，而不是堆规则。
  • 内容判断交给人。README 明确边界：不做内容与政治表述校对，不做 OFD、印章图像、流转审批。数字一律不自动改——“合计错还是分项错，工具判断不了”。
核心技术取舍：它选择了“文件进文件出”而不是“服务端处理”。代价是不能做协同与流程，收益是涉密材料不出本机。在中国政务/央企场景，这个取舍几乎是唯一的正确答案。

12｜踩坑

仓库 GitHub Issues 为 0 条（截至 2026-10-14 核对），因此这里的坑来自作者自己的提交信息与文档，不是社区反馈。

  • 字体问题最容易翻车。标题与发文机关标志默认方正小标宋简体，需自行安装；样张 PDF 是在“没装该字体”的机器上出的，用 Songti SC Black 代替。回退字体时量测脚本会拒绝出数——如果你打算自己改版式，先解决字体，否则量不出可信的尺寸。
  • 首行缩进是连锁反应。v0.3.1 专门修了这个问题：默认样式加首行缩进后，主送机关、居中/右对齐段落、表格、文本框、红头都需要补“首行不缩进”。自己改样式时会撞到同一堵墙。
  • 不要把“提示”当“报错”。数字机检分拦截项与提示项；提示项（如正文取值对照）在“不同主语、不同口径”时属于正常，不必为了消提示改写原文。
  • 量版式前先读 docs/版式.md。作者的原文提醒：校准值与坑都在那里。

15｜中国企业可以怎么用？

  • 场景 1｜党政机关 / 事业单位的文书岗：把 check-doc.js --strict 当“发文前最后一道闸”，退稿率直接下降。对一批历史公文跑一遍，能一次性摸清本单位最常犯的体例错。

01｜案例是什么？

轻舟（qz，qingzhou）是阿里巴巴开源的 Chrome 扩展（Manifest V3），把浏览器变成 AI 可操作的“研究工作台”。它能：看 DOM 或截图操作页面、填表单、跨标签页协作、并行跑子任务并在执行中随时打断或补上下文；把表格、媒体、网页内容抽成本地结构化数据集，在侧边栏里预览、编辑、导出；用 Skill 在目标网页里跑 JavaScript（可打包指令、脚本、工具、自定义界面，甚至按站点自动启用）；模型自己选（任何支持工具调用、协议兼容的服务商，含本地模型服务）；可选 MCP Bridge 把浏览器工具与任务控制开放给外部 Agent。所有会话、Skill、采集数据都存在浏览器本地。

02｜为什么今天值得关注？

  • 为什么是现在：仓库 2026-10-12 首次开源（初始提交 09:54:22 UTC），同日发布 v0.1.0（11:40:11 UTC）；10-13、10-14 连续提交（依赖与安全扫描修复、CI 跨平台加固、测试夹具加固）。这不是“挂了半年突然被发现”，而是两周内的新事件。
  • 最近发生了什么变化：模型侧，“OpenAI 兼容 / Anthropic Messages + tool calling”已成事实标准，接自家模型变得极其便宜；浏览器侧，Chrome 的扩展权限与 CDP（chrome.debugger）足以支撑“真操作页面”而不是“点截图”；合规侧，企业对“浏览器自动化但登录态与数据不上云”的要求越来越硬。
  • 以前为什么不容易做：云端 Browser Agent 的通用做法是把浏览器托管在服务器上——数据出网、登录态托管、按次计费，且遇到验证码/复杂交互容易栽。本地做又缺三样：能真操作页面的权限通道、能落地的结构化数据层、能被外部 Agent 复用的接口。
  • 为什么现在变得容易：轻舟把这三样一次补齐——CDP 页面操作、本地 Data 表、MCP Bridge。并且它是扩展形态：不用 Docker、不用一台服务器、不需要把账号交给第三方。

03｜案例的前世今生

前世。“让模型点网页”这件事最早由 Python 侧跑通（Playwright / browser-use 一类）：无头浏览器 + 截图或可访问性树 → 模型决定动作。它能跑，但对普通用户不友好：要装环境、登录态难维护、数据在服务器上。

发展。随后出现两个分叉：一是协议化——把浏览器能力做成 MCP 工具，让任意 Agent 调用（Claude 侧 DevTools MCP 是代表）；二是本地化——把 Agent 放进用户自己的浏览器里，复用已登录的会话，模型由用户自带。轻舟明确站在第二个分叉上，并且把第一个分叉也接了进来（MCP Bridge）。

今生。2026-10-12，阿里把轻舟以 Apache-2.0 开源，仓库挂在 alibaba 组织下，附带少见的完整文档矩阵：docs/architecture.md（运行时映射与任务生命周期）、docs/benchmarks.md（基准与可视化回归方法）、docs/permissions.md（19 项权限逐条说明用途）、docs/providers.md（如何加模型服务商）、AGENTS.md（开发规则）。代码量约 14MB（JS 6.3MB / TS 5.7MB / Python 1.46MB，1821 个文件），MCP Bridge 是独立 Python 服务。

关联信号（非同一项目，勿混淆）：同期阿里云在云栖大会上联合英特尔发布“Agentic Browser”——把 Chromium 的 Blink/V8 面向 Agent 场景裁剪调优、以预编译 SDK 交付、跑在弹性基础设施上，支持一次拉起上百个浏览器实例，并提出“首次用 Agent 推理、跑通后沉淀为可复用 RPA 流程”的成本思路；官方口径称单实例内存最多降约三成、单任务成本可降百倍量级（该量化口径为厂商自述，第三方分析明确提示需真实业务压测验证）。轻舟与 Agentic Browser 是两个不同的东西（一个在本地端侧，一个在云侧集群），但指向同一判断：浏览器是 Agent 的执行层。

下一步可能怎么发展（以下为分析 / 推演，非事实）：① 能力包与 Skill 生态长起来，出现“行业 Skill 包”（招投标、比价、情报）；② 企业版：内网私有模型 + 私有 Skill + 权限策略；③ 端云协同：本地轻舟做“人机协作与登录态”，云侧做规模化并发。

06｜解决了什么真实问题？

从企业与个人的实际工作出发：

  • “网页上的活”没有 API 可调。绝大多数网站（供应商报价页、政府公开信息、电商后台、行业名录）只做人看的界面。企业要做竞品监控、价格采集、信息汇总，只能靠人一页页复制。
  • 买 RPA 太贵也太脆。传统 RPA 靠写死的选择器，页面一改就崩；维护成本比人工还高。
  • 用云端 Browser Agent 心不安。数据出网、登录态托管在别人服务器上、按次计费——这三条在多数中国企业里过不了安全评审。
  • 最痛的一步其实在“落地”。很多工具能把信息“看到”，但抽出来的结果留在对话里或截图里，不能编辑、不能导出、不能给下一道工序用。轻舟把抽取结果直接放进本地 Data 表，这一步才是真正省人的地方。

09｜它到底是怎么实现的？

  • “页面操作”与“任务编排”是分开的两层。Background 拥有任务状态与持久化、Side Panel 只负责呈现，两者通过显式协议通信；工具处理函数跑在后台 service worker，可把动作或脚本执行委派给活动标签页。好处是：页面崩了、标签页关了，任务状态还在。
  • “写租约 + 每 Session 串行”解决并发乱写。命令进入监督器的按 Session 队列，一次 run 拿到写租约才允许提交——这是并发正确性的工程解法，也是多数玩具级 Agent 缺的东西。
  • 用 CDP 而不是纯截图。走 chrome.debugger 能操作页面、截图、检查请求、打印 PDF，比“截屏+猜坐标”稳定得多。
  • 抽取结果必须“落得下来”。表格、媒体、页面内容进入本地集合，可在侧边栏预览、编辑、导出——把“一次性问答”变成“可复用的数据资产”。
  • MCP Bridge 是双向的、且默认最小暴露。只绑定 loopback、Bearer + 配对 token、校验 Host/Origin、扩展端拒绝 HTTP 重定向并在配对撤销后丢弃迟到的轮询命令。设计取向很明确：不为了便利牺牲边界。
  • 权限面是显式的。docs/permissions.md 逐条列出 19 项权限的用途与主要调用方（含 debugger、<all_urls>、history、bookmarks）——这在开源扩展里并不常见，是给企业安全评审看的。
最关键的一处取舍：坚持“本地优先 + 自带模型”意味着放弃了开箱即用——用户必须自己准备模型服务与 Key。换来的东西很值钱：数据不出本机、登录态不出浏览器、成本由自己的模型决定。

12｜踩坑

仓库 Issues 为 0 条（截至 2026-10-14 核对），所以下面这些坑来自官方文档与第三方独立分析，而非社区反馈：

  • Node 版本是硬门槛。构建需要 Node.js 24 LTS。第三方独立审计明确指出：其环境里是 Node 22 而非要求的 24，因此没能跑完整的 JS 测试套件；同时区分了“文件数量”和“通过的断言数”——不要把仓库的规模当成质量证明。
  • 是开发者模式加载，不是商店安装。这意味着扩展会随 Chrome 更新/策略变化而需要重新加载；企业统一分发需要自行打包策略。
  • 权限面很宽，安全评审会问。包含 debugger、<all_urls>、history、bookmarks、unlimitedStorage、desktopCapture 等 19 项。文档把用途写清楚了，但“写清楚”不等于“被接受”——企业落地前务必先过一遍 docs/permissions.md。
  • 没有公开的对比基准结论。第三方分析的原话值得引用：当前 commit 无法支撑任何关于抽取准确率、Agent 成功率或速度优势的主张；docs/benchmarks.md 自陈给的是“协议与工具”，不是已公布的结果。所以任何“比 X 快 N 倍”的说法都不该从这份仓库里读出来。
  • 能力包 API 仍标为实验性：深度定制（尤其涉及 provider 与工具注册）要做好跟随上游变化的准备。
  • MCP Bridge 的 token 管理要小心。官方提醒：token 只放本地配置、从共享日志里打码；换 token 必须重新配对。

14｜国产替代方案

这个案例的位置比较特殊：它本身就是“国产替代”的供给方。所以这里反过来看“它能替代谁 / 谁替代它”。

它可替代云端无头浏览器类 Browser Agent（数据出网、登录态托管的那类）——结构性替代（同目标、不同形态），但官方未发布任何对比数据，不构成性能优于的结论

轻舟面对的是完全相反的问题：网页没有 API、登录态不能外流、模型要自带。阿里的解法是把浏览器变成“本地优先的工作台”：CDP 操作页面、数据落本地、Skill 沉淀重复流程、再通过 MCP Bridge 把浏览器借给外部 Agent。它的价值不在于“能点网页”，而在于把不确定性留给模型、把正确性写进代码（按 Session 串行、写租约、去重）。同时它也诚实地把局限摆出来：能力包 API 是实验性的，基准文档只给协议不给结论，第三方分析甚至明确说“当前版本支撑不了任何性能优势主张”。

更值得注意的是两件事的时间重合。轻舟在 10-12 开源，24 小时内连续提交；gongwen-kit 在 10-13 首版开源，同一天出四个版本。它们都不是大厂 PR 稿，而是能 git clone 就跑的东西。这提示一个重要变化：企业侧的 AI 落地正在从“做一个智能体平台”转向“把一个具体行业的规则做成可执行、可验证、可回滚的代码”。

对个人开发者来说，今天这两个案例的价值不在于学会某个库，而在于看见一条更现实的路：你不必比大厂更懂模型，你只需要比大厂更懂某个行业的规则与边界。公文格式、招投标流程、页面上每天要点的那几下——这些“脏活”才是可以卖钱的地方。
