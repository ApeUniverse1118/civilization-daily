01｜案例是什么？

麦当劳中国做了一个叫「麦当劳 MCP」的官方服务：一个远程托管的 MCP Server，地址是 https://mcp.mcd.cn，走 Streamable HTTP，用 Authorization: Bearer <Token> 认证。开发者到官方开放平台 open.mcd.cn/mcp 用手机号登录、点「激活」就能拿到 Token。

拿到 Token 之后，任何支持 MCP 的客户端（WorkBuddy、Cherry Studio、Cursor、TRAE、VS Code……）都能让 AI 去查当天有哪些活动、查门店能卖什么、算价格、下单、取消订单、查积分、领券、抽奖、预约生日派对。官方文档列出的工具覆盖麦乐送点餐、到店取餐、团餐、积分兑换券、活动日历等场景。

2026 年 10 月 9 日 10:30，麦当劳中国同时开启了「麦当劳程序员创意开发大赛」：开发者用这套 MCP 做 Skill（套餐推荐、省钱助手、活动推荐等），开源到 GitHub，按 公开 Star 数排名，前 100 名进榜获奖。WorkBuddy（腾讯）是本次活动的官方合作伙伴。

03｜案例的前世今生

前世（为什么要做这个？）消费品牌的数字化服务长期停留在「App / 小程序 / 公众号」三种形态：用户必须到品牌的场子里用品牌给的界面。AI 时代出现了一个新问题——用户开始用 AI 助手直接说「帮我订个麦当劳」，而 Agent 没有眼睛也没有手指，它只能调接口。品牌如果不开接口，就会被第三方用爬虫和逆向「代劳」，既不可控也不安全。MCP 在 2025 年被 Anthropic 提出并被各大厂商迅速接受后，给了品牌方一个标准答案：与其被逆向，不如主动开放。

06｜解决了什么真实问题？

从用户需求而不是从 AI 技术讲起，这条链路原本卡在三处：

  • 用户侧：点餐前的决策成本。「今天吃什么、有什么活动、我有什么券、券后多少钱、哪家店还有名额」——要把这些拼起来，用户得在 App、公众号、活动页之间来回跳。麦当劳自己的活动尤其如此：生日派对、读书会、品鉴会这类「场次 + 名额」型活动，信息分散且时效性强，用户很难自己扫完。
  • 开发者侧：合规的接入路径缺失。想做一个「帮我点麦当劳」的小工具，私人开发者唯一的路径是逆向，随时可能失效、且明确违规。
  • 品牌侧：AI 流量入口的失位。当越来越多用户的第一入口变成 AI 助手，品牌如果没有可以被 Agent 调用的标准接口，就会在这场迁移里彻底隐身。

官方 MCP 一次性回应了三方：用户得到「一句话问出结果」，开发者得到合规接口，品牌得到进入 Agent 生态的入口。

08｜完整 Workflow

用户输入：「这个周末附近哪家麦麦有生日派对还有名额？」（自然语言）
↓
Agent（Skill）：识别意图 → 判定需要「城市 + 日期 + 活动类型」→ 缺城市则先做 IP 级城市定位并请用户确认
↓
Tool 调用链（MCP）：campaign-calendar 找活动线索 → mall-points-products → mall-product-detail 拿 spuId → query-party-city → query-party-store（返回门店名/地址/经纬度/营业状态）
↓
Tool 调用链（续）：query-party-store-date 查可预约日期 → query-party-store-session 查场次；只有 leftNum > 0 才标「有名额」
↓
规则层（确定性，不交给模型）：日期/城市/关键词筛选、去重、价格单位核对、把「只有活动日历」的结果降级为「待核实」
↓
输出：单文件自包含 HTML 卡通活动地图（门店按官方经纬度线性投影、辖区与道路为卡通示意并明确标注「示意图」）+ 活动卡片，可筛选、可导出 .ics 日历
↓
Human-in-the-loop：party-order-create（下单）默认不调用，必须用户明确确认；不自动支付

09｜它到底是怎么实现的？

把「为什么它能工作」拆成四层来看：

  • 第一层｜能力层（官方负责）：把业务原子化成幂等的工具。query-meals 查菜单、calculate-price 算价、create-order 下单、cancel-order 取消、query-my-coupons 查券——每个工具只做一件事，参数与返回结构由官方定义。这正好对应企业 Agent 设计的核心原则：模型负责不确定的语言，系统负责确定的事实。
  • 第二层｜编排层（Skill 负责）：把「用户的一句话」翻译成一串有依赖顺序的工具调用。spuId 必须来自上一步真实返回，不能从标题猜；门店经纬度只用于地图投影，不做逆地理编码。这一层的价值不在于模型多聪明，而在于依赖关系被显式建模。
  • 第三层｜不变量层（阈值与闸门）：「可预约」= 官方接口返回的 leftNum > 0；价格单位未核实就不换算；只有活动日历线索时展示「待核实」。这类「不变量」是 Agent 不产生幻觉的真正原因——把结论收敛到可核验的字段上。
  • 第四层｜交付层：输出不是一段文字，而是一个可交互的单文件页面。这是《AI 极客实战》系列一直强调的趋势：Agent 的交付物正在从「回答」变成「可直接使用的产物」。

顺带看一个很重要的负面信号：作者公开指出，官方文档页把两个工具写作 query-partystore-date / query-partystore-session，而线上 tools/list 实测为 query-party-store-date / query-party-store-session。文档与线上不一致，在 MCP 生态里是常态——所以成熟的做法是运行时读取工具 schema，而不是把字段名硬编码进提示词。

10｜手把手复现

Step 1（官方原文）· 申请 Token
浏览器打开 open.mcd.cn/mcp → 右上角【登录】→ 手机号验证码登录 → 点【控制台】→ 点【激活】→ 同意服务协议 → 一键复制 Token。

Step 2（官方原文）· 把 MCP 配进客户端
官方给了通用 JSON，粘进客户端的 MCP 配置即可：

{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": { "Authorization": "Bearer YOUR_MCP_TOKEN" }
    }
  }
}

官方特别提示：一定记得把 YOUR_MCP_TOKEN 换成真实 Token；确保客户端支持 Streamable HTTP；Token 妥善保管，不要泄露。

Step 3–6（来自参赛作品公开文档）· 用 WorkBuddy 装载 Skill 并跑通

  • Step 3：在 WorkBuddy 对话框里直接说「帮我安装这个技能：<仓库地址>，把 skill/<name> 复制到 ~/.workbuddy/skills/」；或下载仓库的 dist/*-skill.zip 走图形界面「技能 → 添加技能 → 上传技能」导入。
  • Step 4：新开一轮会话（Skill 目录扫描在会话启动时进行，不重开会话不生效——这是最常见的第一次失败原因）。
  • Step 5：对 Skill 说一句自然语言（如「查附近的活动」），它会先确认城市，再开跑。
  • Step 6：首次使用贴一次 Token，Skill 内置的 setup-connector.mjs 会写前备份、保留其他服务器条目、不回显 Token、在线验证后提示「Trust → 启用 → 重开会话」。之后免配置。

12｜踩坑

坑 1｜官方文档与线上工具名不一致。文档写作 query-partystore-date/query-partystore-session，线上实测为 query-party-store-date/query-party-store-session。解法：不硬编码工具名与字段名，运行时读取连接器实际 schema。（来源：参赛作品公开文档，作者原话）

坑 2｜装完 Skill 不生效。Skill 目录在会话启动时扫描，装完必须新开一轮会话。（来源：参赛作品公开文档）

坑 3｜Token 是唯一的身份凭证，泄露 = 别人用你的账号下单。官方要求妥善保管；项目做法是配置文件写前备份、不回显 Token、示例文件只放环境变量占位符。（来源：官方文档 + 参赛作品公开文档）

坑 4｜限流。600 次/分钟/Toke，超限 429。多轮工具链（一次查询可能串 7 个工具）很容易把频率打上去，尤其在批量扫城市/门店时。（来源：官方文档原文）

坑 5｜「有活动」不等于「有名额」。这是最容易让 Agent 说错话的地方。官方活动类目（生日派对 1>6>20、主题派对 1>6>21、体验营 1>6>22、品鉴会 1>6>25、读书会 1>6>34）只是线索，必须走到 query-party-store-session 才能确认名额。（来源：参赛作品公开文档）

13｜中国用户能不能直接做？

  • 国内访问：可以。服务在中国大陆境内，官方明确「面向中国大陆地区（不含港澳台）使用」。
  • 注册：很方便。手机号验证码登录，无需企业资质，个人即可申请 Token。
  • API：容易获得。登录后点「激活」即得 Token，一键复制。
  • 成本：MCP 服务本身官方未公布计费——截至采集时点，官方文档与活动规则中均未提及收费。我们不假设它永久免费，使用者应以官方条款为准。其余成本主要是客户端与模型费用。
  • 技术门槛： 普通用户可上手 —— 只想用的话，配好 JSON、粘 Token 就能在对话里点餐、查券、查活动；AI 用户可做 Skill —— 要做成可复用的 Skill，需要理解 MCP 工具边界与文件结构；开发者做产品 —— 要做成独立产品需 Node.js / 前端能力。
  • 参赛资格：必须是中国大陆合法居民、年龄 ≥18 周岁（未满 18 需监护人同意）；项目仓库必须公开可访问；项目创建时间需落在 2025-12-25 00:00 至 2026-10-25 23:59 之间。

14｜国产替代方案

原方案麦当劳中国官方 MCP（mcp.mcd.cn）+ 任意支持 Streamable HTTP 的 MCP 客户端
中国用户方案本身即国产：服务方麦当劳中国（金拱门），官方推荐客户端含 WorkBuddy（腾讯）、TRAE（字节）、Cherry Studio（国内开源）。不存在「需要替换」的问题。

15｜中国企业可以怎么用？

企业场景 1｜连锁餐饮 / 零售：把「活动 + 库存 + 权益」做成 Agent 可调用能力。麦当劳已经示范了完整链路：活动日历 → 商品目录 → 门店与场次 → 名额核验 → 下单。任何有「门店 × 场次 × 名额」结构的业务（餐饮、健身、影院、医美、教培试听、连锁门店预约）都能照搬这个工具切分方式。

企业场景 2｜企业内部系统接入 MCP，替代「写死的工作流」。把 CRM 查客户、ERP 查库存、工单系统建单封装成 MCP 工具，让不同 Agent（客服、销售、运营）共用同一套能力，而不是每个场景重写一遍 API 调用。

企业场景 3｜用「公开 Star 排行」这种机制低成本征集外部创意。本次大赛的组织方式（开源 + 公开排行 + 小额奖励 + 官方自动化报名校验）是一套极低成本的外部创新征集模板——用 Issue 机器人做合规校验、用 Star 数做公开排序、用少量品牌权益做奖励。活动规则还把「内容合规」「原创性」「不得诋毁品牌」全部前置到参赛声明文件里，法务成本被大幅摊薄。

16｜中国消费者可以怎么用？

  1. 省钱场景：让 AI 先查「我有什么券」+「当前门店能卖什么」+「券后价」，再决定点不点——把「领券 → 算价 → 对比套餐」合并成一句话。
  2. 活动场景：查询附近门店的生日派对、读书会、品鉴会场次与名额，导出 .ics 进日历。这是传统 App 里最难找、最容易被忽略的信息。
  3. 家庭/团队场景：多人点餐、拼单分账、按热量或预算选套餐——这类「多约束求解」正好是模型擅长的，而人类自己在菜单上做很累。

17｜如何变成一个赚钱的项目？

先说清楚边界：官方条款明确禁止「商业售卖、付费分发、引流变现、暗示官方背书」。所以下面所有路径都必须建立在「拿到品牌授权」或「把价值做在品牌业务之外」这两个前提上，否则不建议做。

产品化：把「场景化点餐决策」做成一个轻量 Web / 小程序工具（多人拼单、热量预算、活动日历聚合）。核心资产不是接口，而是交互设计与规则沉淀。

服务化：更现实的路径是「MCP/Skill 交付服务」——把「把企业某个业务封装成 MCP 工具 + 写一份 Skill + 做工具边界说明书」做成标准化交付。本次大赛产出的 MCP_INTEGRATION.md 结构，本身就是一份很好的交付物范本。

咨询化：帮消费品企业做「品牌能力 MCP 化」的方案设计：哪些业务适合原子化成工具、工具边界怎么划、如何用排行榜机制做外部征集。

培训化：「从 0 做一个 MCP Skill」是最好的入门级 Workshop 题材——门槛低、有真接口、当天能出成果、还能顺手参赛。详见第 21 节。

内容化：「我用官方 MCP 做了个 XX」是天然的实操内容题材（B站 / 小红书 / 公众号），尤其是「一句话查出附近还有名额的生日派对」这类有画面感的结果。

行业化：把「活动 × 门店 × 名额 × 下单」这套模式抽象出来，复用到连锁服务业的任意细分——这是本次案例最值钱的抽象。

19｜如果我是一个中国独立开发者

假设：1 个人、预算有限、有基础编程能力、使用国产模型。目标：7 天做出一个能参赛、也能留在作品集里的最小可行版本（MVP）。

  • Day 1｜拿 Token，跑通最小闭环。申请 Token → 配进客户端 → 只调用一个工具（如 query-meals），确认能拿到真实菜单。验收：一句话问出今天的菜单。
  • Day 2｜画工具边界表。把要用到的 5～8 个工具列出来，每个写清「返回什么 / 不代表什么」。这一步决定后面会不会说错话。
  • Day 3｜定义不变量。确定哪些结论必须来自字段（如「有名额」= leftNum > 0），哪些必须降级为「待核实」。把这些写成硬规则，不交给模型。
  • Day 4｜串第一条多步链。活动日历 → 商品 → 城市 → 门店 → 日期 → 场次，跑一遍真实数据，记录每一步的真实返回结构（不要照抄文档字段名）。
  • Day 5｜做交付物。把结果渲染成一个自包含的单文件 HTML（可筛选、可导出 .ics），而不是只输出一段文字。
  • Day 6｜补异常路径。限流 429、Token 失效、工具名不符、字段缺失、无结果——每一条都要有明确提示，而不是让模型猜。
  • Day 7｜打包 + 写文档 + 报名。整理 README.md / CONTEST_DECLARATION.md / MCP_INTEGRATION.md / mcp-config.example.json；写 workbuddy.md；发报名 Issue。

现实提醒：这份 7 天计划假设你每天能投入 2–4 小时，且当天就能拿到 Token。真正的瓶颈通常不在写代码，而在 Day 3 的不变量设计——想清楚「什么话绝对不能说」，比多加两个工具重要得多。

01｜案例是什么？

AIHOT 是一个「自己找热点、自己写日报」的网站框架。它每天从一批信源里收资料，用大模型先筛一遍、再独立打两次分，挑出真正值得看的，写成中文标题和摘要；把不同来源说的同一件事聚成一个「事件」，按有多少人在说排热度，每天早上出一份日报。

作者把引擎本身开源了：网站、后台、精选流程、聚簇与热度算法、以及全部提示词原文和入选门槛，都在仓库里。他自己在 README 里说得很直白：「把信源换成你的，把精选标准换成你的 KnowHow，它就是你的行业热点站。」

仓库自带 18 个公开的海外 AI 资讯源做示范，够跑起来看效果；真正的信源和运营数据不在仓库里。

02｜为什么今天值得关注？

  • 因为它正在被「工程化」而不是被「展示」。窗口内（10-09 → 10-10 UTC）该仓库有 15 次提交，集中在引擎侧的质量控制：撤下/补齐导航隐藏入口、修复「首个日报之前结束的周/月报不该出刊」的排期 bug、给「读者用词替换」补齐步骤说明、把撤回过的报道从聚簇证据里排除、隐藏掉桥接证据被撤销后的关联事件。这些改动说明它已经从「能跑」进入「跑得稳」阶段。
  • 因为它的成本被压到了个人可承受。部署只需要 Docker + Node 24 + 一个 OpenAI 兼容的模型 Key，默认按 DeepSeek 配置，README 明确支持千问、智谱。一条命令起站。
  • 因为它是「AI + 内容」方向少见的完整闭环。本系列连续多期找不到合格的「AI + 内容创作」一手案例，多被内容农场占据。这一个不是教程、不是工具推荐，而是一条可部署的完整流水线，附全部提示词。

如实说明本期的窗口证据强度：AIHOT 在窗口内没有发布新版本（该仓库不使用 GitHub Releases），窗口事件是 15 次引擎提交，属渐进式更新而非重大版本。我们仍将其收录，因为：① 「新更新」本身符合收录口径；② 其可复现性、一手程度与可迁移性在当日候选中最高；③ 当日没有第三个案例达到收录标准。我们同时提示一个指标异常：7022 ★ 对应 1723 Fork，而仅有 22 个 Watcher，Star/Fork 比例明显高于开源项目常态，其增长质量无法独立验证。

03｜案例的前世今生

前世（为什么会出现？）「把信息汇总成日报」这件事，过去十年经历了三代：第一代是 RSS 阅读器（人自己筛），第二代是爬虫 + 关键词（规则筛，误报多、重复多），第三代是 LLM 摘要（一句话总结，但没有取舍——所以每天都能生成一份「什么都说了等于什么都没说」的日报）。真正没被解决的那个问题，是「取舍标准」本身。

发展（这个项目自己讲的很清楚）

  • 作者自述是设计师出身，「半年前还看不太懂代码」，这套代码是他和 AI 一起重写的——这是典型的 2026 年现象：非传统程序员用 AI 做出了产品级系统。（来源：作者 README 原文，属自述）
  • 关键转变是「把标准外置」。大多数类似项目把筛选逻辑写死在代码里；AIHOT 把每一步的提示词放进 industry/prompts/，「改标准不用改代码」。这一步让它从「一个网站」变成了「一个可被改造的框架」。
  • 然后是「可校准」。它提供 SelectBench，用你自己标注的样本去校准评分门槛；仓库里还带 gold.example.jsonl、relation-gold.example.jsonl、story-digest-eval.example.jsonl 等评测样例文件。

06｜解决了什么真实问题？

  • 「看不过来」的下一层是「看错了」。同一个消息，官网发一篇、媒体转十篇、朋友圈刷一天。人真正的负担不是信息量，而是去重与判断重要性。AIHOT 对这个问题的回答是把「事件」而不是「文章」当作基本单位：48 小时内每个独立来源只算一次热度、24 小时减半——所以排名靠前的是真正有很多人在说的事，而不是某家媒体发得最多的事。
  • 「我不需要一个 AI 帮我总结，我需要一个 AI 帮我取舍。」这是本项目与「RSS + 大模型摘要」的根本区别：摘要解决「看懂」，取舍解决「值不值得看」。而取舍标准，是可配置、可校准、可用自己标注的样本去验证的。

信源层：RSS / 网页列表 / JSON / X / 微信公众号 / 自定义脚本推送 → 同一网址同一内容只留一份
↓

↓

↓

↓

↓

↓

09｜它到底是怎么实现的？

这套系统里真正有技术含量的，不是「调模型写摘要」，而是三个反直觉的设计：

  • ① 两次独立评分，而不是一次打分。单次 LLM 打分方差大，同一个条目今天说 80 分明天说 55 分。它用「同一份标准独立打两次，两次之和 ≥ 2 × 门槛」来对抗这种抖动。这是把「模型的随机性」当成工程参数处理，而不是靠调提示词祈祷。
  • ② 门槛按信源分级，而不是一刀切。T1（官方一手）容忍低分——官方发的就是重要的；T3（媒体与个人）要求高分——因为噪音大。这等于把「信任度」显式建模成了评分函数的输入。
  • ③ 热度按事件算，每个来源只算一次。如果按文章数算热度，一家媒体发十篇就赢了。按「独立来源数」算，只有一个来源反复报道的事件不会进榜。这条规则直接决定了榜单的信息价值，而不是它的工作量。

另外两个工程细节值得单独记下来：

  • 「旧文不刷屏」：没有可信发布时间的资料先不公开，读到原文日期后再判断新旧——这是自动日报最容易被忽略的失真源。
  • 「有正文才写文案」：X 帖子没有正文或只有链接时，保留原帖的链接、图片和引用，不调用写作或翻译模型。这一条把一个高风险的幻觉路径直接砍掉了。

12｜踩坑

坑 1｜把「摘要」当成了「取舍」。很多人做自动日报的第一反应是「抓下来让模型总结」。结果每天都能生成一份内容，但读者依然不知道什么重要。解法：先定义门槛，再定义摘要。（来源：项目设计逻辑，本报告归纳）

坑 2｜只有标题就敢让模型写文案。这是幻觉的高发区。项目的处理是硬规则：只有标题/摘要的普通文章先等待材料，不评分、不写文案；X 帖子无正文时保留原帖链接与图片，不调用写作或翻译模型。（来源：docs/selection.md）

坑 3｜旧文刷屏。没有可信发布时间的资料如果直接公开，会把几个月前的旧闻当成今天的新闻推。项目的处理是「旧文不刷屏」：读到原文日期后再判断新旧。（来源：docs/selection.md）

坑 4｜单次 LLM 打分的方差。同一个条目两次打分可能差 20 分以上。解法：独立打两次、要求和 ≥ 2 × 门槛。（来源：docs/selection.md）

坑 5｜按文章数算热度 → 一家媒体刷榜。解法：按事件算，48 小时内每个独立来源只算一次，24 小时减半。（来源：作者 README）

坑 6｜出刊排期边界。窗口内的一次提交正是修这个 bug：「在第一个日报之前结束的周/月不该出刊」——月中建站时会凭空生成一份空周报。（来源：窗口内提交记录，10-09）

坑 7｜「读者用词」改不干净。作者自述曾在一个分支统计过：入选的 166 条里，靠提示词里写「不要用某些词」并不能真的让模型不写。解法：写完之后按行业用词表再让模型只改这些词一次（独立的 mend-wording.md 步骤）。（来源：窗口内提交记录中的说明文字，属作者自述）

原方案AIHOT 引擎 + 任意 OpenAI 兼容模型

15｜中国企业可以怎么用？

企业场景 2｜企业内部舆情 / 竞品情报台（对内）。把信源换成竞品官网、行业媒体、政策发布平台、社交账号，产出一份每天早上 8 点到岗的内部简报。关键收益是把「人肉搜 + 群转发」替换成一条固定流水线，且每条都带原文出处。

企业场景 3｜销售 / 采购线索雷达（对外作战）。本案的「事件聚类 + 独立来源数计热度」正好对应「一件事有多少人在说」——这在采购线索、招投标信息、政策变动预警上，比关键词匹配准确得多。

16｜中国消费者可以怎么用？

  3. 自建家庭 / 小区信息站：把本地政务、交通、天气预警、业主群公告聚成一份日报——技术上是同一套。

17｜如何变成一个赚钱的项目？

产品化：「模板 + 托管」是最直接的形态：给某个行业起一个站，作者原话是「换上你自己的名字，它就是你的站」。可做独立站订阅，也可以做成只读的公开站 + 会员看历史与全文。

服务化：「帮你做一个你行业的 AIHOT」——交付范围清晰（选信源、定门槛、调提示词、部署上线、跑通日报），因为引擎开源，交付成本远低于从零开发。作者本人说「做不了，我不懂你们的行业」——这句话本身就是市场需求证明，也是差异化壁垒所在。

咨询化：门槛与「什么算重要」是行业 KnowHow，这部分最贵。可以做「信源审计 + 取舍标准设计」的轻咨询，也可做长期的月度校准服务。

培训化：「用开源引擎搭一个你行业的 AI 日报」是极好的实操课，学员当天能看到自己的站在跑。详见第 21 节。

内容化：项目本身就是一个内容题材（「我用 AI 做了个行业日报站，每天只看 10 分钟」），而站本身又是内容载体——内容与产品互相导流。

行业化：本案例最典型的「多行业复制」结构，同一份引擎可以长出 N 个垂直站。

19｜如果我是一个中国独立开发者

假设：1 个人、预算有限、有基础编程能力、使用国产模型。目标：7 天上线一个垂直行业热点站。

  • Day 1｜选行业，不选技术。选一个你真正懂取舍的细分行业（法律、宠物、母婴、地方政务、某个制造业）。判断标准：你能说出「什么算重要」。
  • Day 2｜列信源清单。列出 15–25 个源，按 T1/T2/T3 分级。重点补微信公众号类源——这是别人抄不走的壁垒。
  • Day 3｜部署跑通。git clone → node scripts/init-env.ts --llm-key <DeepSeek Key> → docker compose up -d --build，先看示范信源的默认效果。
  • Day 4｜换信源 + 换站名。改 industry/sources.json、site/site.ts、taxonomy.ts；按 docs/customize.md 走一遍。
  • Day 5｜改取舍标准。重写 rules-domain.md、调 selection-score.md 与门槛。这是工作量最大也最值钱的一天。
  • Day 6｜标注样本校准 + 配用词表。标 30–50 条样本进 SelectBench；把不想出现的词写进 wording.ts。
  • Day 7｜上线 + 铺分发。部署 + 域名 + HTTPS，打开 /agent 拿到 MCP / RSS 接入方式，把 RSS 挂到自己的分发渠道。

现实提醒：这份计划里唯一不能压缩的是 Day 5。技术部署一天就够，取舍标准一周都未必够。真正的护城河不在代码，在「什么算重要」这个判断上。

20｜如何迁移到其他行业

① 法规合规情报法规发布平台 + 判例 + 监管公众号 → 每日合规简报，服务律所、财税、企业法务。
② 招投标 / 采购线索招投标公告 + 行业媒体 + 政府发布 → 事件化线索雷达，服务销售与代理商。
③ 跨境电商选品情报平台政策 + 品类趋势 + 竞品社交账号 → 每日选品与合规预警，服务卖家与代运营。

迁移方法完全一致：换信源清单 → 重写行业规则提示词 → 重新标注样本调门槛 → 换站名上线。代码不动，这也是本案最值得抄的地方。

21｜培训课程设计

课程名称《给你的行业做一个 AI 日报站：从信源到取舍标准》
适合人群独立开发者、内容/媒体从业者、想做垂直情报产品的产品经理、企业市场与战略岗
建议时长半天（3.5–4 小时），可拆出 30 分钟 Demo 与 60 分钟 Workshop
30 分钟 Demo现场 git clone + 一条命令起站，让学员看示范信源跑出的每日精选与事件时间线。
60 分钟 Workshop学员各自列 10 个行业信源并分级，改 sources.json 后试抓，看自己的信源进来后精选质量如何。
半天课程上半场：自动日报的三代演进、为什么「取舍」比「摘要」难（30 分钟）→ 部署动手（60 分钟）。下半场：两次评分与信源分级（45 分钟）→ 聚簇与热度（30 分钟）→ 门槛校准与用词表（45 分钟）→ 上线与分发（30 分钟）。
课程目标学员最终能够：独立部署一个站；按 tier 给自己的行业信源分级；说清「两次评分」「按事件算热度」为什么必要；标注样本完成一次门槛校准。
现场 Demo「同一件事，官网发一篇、媒体转十篇」——现场演示聚簇如何把它们折成一个事件、热度只算一次独立来源。
学员练习给自己的行业写 10 条「什么算重要 / 什么不算」的判断，作为 rules-domain.md 的草稿。
课后作业上线一个自己行业的只读站，产出连续 3 天的日报截图，并交一份门槛调整记录。
企业迁移把课程主体换成企业内部情报台：信源怎么选、权限怎么管、与现有内容流程怎么并存、如何避免变成又一个没人看的日报。

22｜培训师点评

点评：这个案例真正值得教的是「把判断标准外置并允许校准」这个动作。两次独立评分是为了对抗模型抖动，按信源分级定门槛是为了把「信任度」写进函数，按事件算热度是为了防止刷榜——三条都是可迁移的工程直觉。而它最值钱的一课其实与代码无关：先定义什么算重要，再让 AI 去执行。

今日 AI 实战观察

把今天这两个案例放在一起看，会看到一件比「又出了什么新模型」重要得多的事：AI 实战正在从「做一个东西」转向「把能力标准化」。

麦当劳中国这一侧，是企业把业务开放成标准件。九个版本的 MCP 迭代，把点餐、到店、团餐、活动、积分逐条原子化成工具，再交给外部开发者去拼装。这件事真正的意义不在于「麦当劳支持 MCP 了」，而在于它宣告了一种新的品牌-开发者关系：品牌提供能力与规则，开发者提供创意与场景，双方用一个公开排行榜来完成筛选与激励。对开发者来说，过去做消费级 Agent 最大的门槛从来不是技术，是「拿不到合规接口」——昨天这个门槛在中国第一次被一个大型消费品牌主动拆掉了。

AIHOT 这一侧，是个人把工作流沉淀成可复制的引擎。它做对的关键动作不是用了什么模型，而是把「什么算重要」这条判断从代码里搬出来，变成 25 份可读、可改、可校准的提示词，外加一套用自己样本去校准门槛的机制。这让它从一个网站变成了一份可以被上百个行业各自改造的蓝本。更值得注意的是作者的画像：自述设计师出身、半年前还看不太懂代码，却交付了产品级的完整工程——2026 年「谁有资格做软件」这个问题，正在被重写。

两条线交汇处，是一个对中国从业者很关键的判断：AI 的价值正在从「模型能力」转移到「能力供给」与「流程沉淀」上。模型已经是公共品——麦当劳的 MCP 不绑定任何模型，AIHOT 默认用 DeepSeek 也支持千问与智谱。当模型不再稀缺，稀缺的就变成了两样东西：有没有可被调用的真实业务能力，以及你能不能把模糊的行业判断说清楚并固化下来。

也因此，今天两个案例的变现路径都指向同一个方向：不做产品，做交付。把企业业务 MCP 化、帮某个行业搭一套取舍标准——这两件事的共同点是「工程可复制、KnowHow 不可复制」。这大概会是接下来一段时间，中国 AI 实战里最实在的一类机会。

今日商业机会雷达

机会 1｜企业业务能力的 MCP 化交付

  • 客户：有门店/场次/库存/权益结构的连锁消费企业（餐饮、医美、健身、教培、影院、票务）、有内部审批流的中大型企业。
  • 解决什么：把「人能点的界面」变成「Agent 能调的工具」，让企业进入 AI 助手入口，同时避免被第三方逆向。
  • 实现方式（参照本案）：梳理业务原子操作 → 划工具边界 → 写「能力/边界对照表」（MCP_INTEGRATION.md 那种） → 配客户端 → 做 Demo Skill。
  • 可能商业模式：项目制交付 + 年维护；或「先做一个可演示的 Skill，再谈整体开放」的自证式打法。
  • 为什么是现在：MCP 已是国内客户端事实标准（WorkBuddy / TRAE / Cherry Studio / Cursor / VS Code 都内置），企业侧最大障碍从「技术不确定」变成了「要不要公开」。

机会 2｜垂直行业的「取舍标准」设计与校准服务

  • 客户：律所 / 财税 / HR SaaS / 券商研究 / 大宗商品 / 跨境电商等需要持续情报输入的机构。
  • 解决什么：不是缺信息，而是缺「什么算重要」的判断，且这个判断必须可复现、可交接、可校准。
  • 实现方式（参照本案）：用开源引擎做底座 → 重建信源清单与分级 → 重写行业规则提示词 → 标注样本做门槛校准 → 上线日报/周报。
  • 可能商业模式：建站交付（一次性）+ 门槛校准（周期性）；行业知识越深，议价能力越强。
  • 为什么是现在：引擎已经开源，交付成本骤降；而行业 KnowHow 依然稀缺——技术变便宜了，判断没变便宜。

机会 3｜「MCP Skill 开发」正在成为一个新的接单品类

  • 客户：想赶上这一波但内部没有工程能力的中小企业、品牌方、以及各类开放了 MCP/API 的平台方。
  • 解决什么：平台方开了接口但没人做应用；企业有场景但不会做 Skill。中间是空的。
  • 实现方式：接单 → 按官方规范产出 README / 交付文档 / 可运行 Skill → 交付并维护。
  • 为什么是现在：本次赛事把「Skill」的交付标准（文件清单、边界说明、脱敏配置示例）明确写进了规则，等于行业已经有了统一的验收口径——有标准，就能报价。
声明：以上三条均为基于当天案例结构的商业模式分析，不是已验证的商业成功。案例 01 的官方条款明确禁止未授权的商业售卖与引流变现，相关机会需先取得授权。

今日个人变现机会

假设一个人每天投入 2–4 小时，从今天这两个案例出发，能启动什么：

  • ① 参赛 + 作品集双收（见效最快）：用 7 天做一个 MCP Skill 参加到 10-25，成本≈0，回报至少是一个可开源、可写进简历的作品，且当前入榜门槛并不高（10-10 排行榜末位约 4–5 ★）。这是本报告认为当天性价比最高的动作。
  • ② 垂直行业情报站（复利最强）：选一个你真正懂的细分行业，部署一套开源引擎，7 天上线。资产可累积、可订阅化、可作为获客入口。难点在持续运营，不在技术。

  • ④ 培训 / 内训：两个案例都天然适合做「一天 Workshop」——一个教 MCP Skill，一个教信息流水线。门槛低、当天出成果、企业买单意愿明确。
  • ⑤ 接单接活：MCP Skill 开发、行业站搭建、门槛校准。定价可低可高，取决于你是否能提供「判断」而不只是「工程」。
