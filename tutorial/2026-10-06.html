一句话结论：它把「AI 推荐谁」这件原本说不清的事，变成了有快照、有置信区间、有共识度（kappa）的可复核分数——这一点比它的数据量更值钱。

01｜案例是什么？

EEO 是 Everything Engine Optimization 的缩写，它是这个社区给 SEO、AEO、GEO、LLMO 起的统称（Apache-2.0，Node 18+，零依赖）。项目做三件事：① 建一个全球品牌目录（eeo.brand.v1 结构，含网站、行业、国家、LEI 法人识别码等字段）；② 提供一套「审计工具」，向真实的 AI 引擎提出真实买家会问的问题、把每次原始回答存档、再给品牌的可见度打分——工具以六种形态分发（单文件网页、CLI、自托管服务、MCP 服务、GitHub Action、浏览器扩展），内置 26 个引擎预设，其中 11 个是中国本土引擎；③ 让品牌通过公开 PR 完成域名验证，「认领」自己的名片。所有判定文件都存档在仓库里可供逐行审计。

02｜为什么今天值得关注？

  • 窗口内的事实（可用 API 核实）：该仓库创建于 2026-10-05T12:24:03Z，即北京时间 10-05 20:24，落在本期窗口（10-05 12:00 → 10-06 12:00）内；此后持续推送（至 10-08）。
  • 它回答了一个正在变成刚需的问题：当买家问 AI「推荐几个奶茶品牌」，模型的回答是从它读过的内容里拼出来的，而品牌自己的说法很少以结构化形式进入模型。这个项目就是冲着这个缺口去的。
  • 为什么以前不容易做：「AI 可见度」这件事过去只能靠手工问几句、截图留证——分数不稳定、无法比较、更无法证明改进有效。它本质上缺的是度量方法，不是一个工具。
  • 为什么现在值得花时间：它同时做了两件稀缺的事——把中国本土引擎放进预设（11 个），把度量方法写成了可复现的流程（冻结引擎快照、双引擎采样、双裁判立场判定并公布 kappa=0.909、Wilson 置信区间、Bradley-Terry 排序）。对做 GEO 服务的人来说，这套方法论本身就是可交付物。

03｜案例的前世今生

前世。SEO 时代，品牌关心的是「搜索页排第几」——这件事有确定答案，因为搜索页是固定的那一屏。品牌只要做好内容与链接，就能被看见。

发展。生成式 AI 改变了前提：买家不再看到一屏链接，而是拿到一段结论。于是「排第几」变成了「模型提没提你、怎么提你、在什么语境下提你」。行业把它叫做 AEO / GEO / LLMO，但很长一段时间里，这些说法都停留在「刷内容、塞关键词」的玄学层面，缺少可验证的度量。

今生。EEO 的做法是「把度量当第一性问题」：不先卖优化服务，而是先建可复现的评测——固定问题面板、冻结引擎快照、字节级可复现打分、双引擎采样、双裁判判定立场分歧（并公开 0.909 的一致性 kappa）、Wilson 置信区间、改写鲁棒性检查、Bradley-Terry 排名。作者明确说了它要回答单次审计的两个致命质疑：分数不稳定，以及把「被提及」误当成「被推荐」。

下一步可能怎么发展（分析 / 推演）。这类「AI 可见度」评测很可能成为品牌营销的常规预算项——就像当年的 SEO 报告一样。更值得关注的是它的两个衍生方向：一是「品牌事实源」的标准之争（谁的结构被模型优先采信），二是「优化服务商的行业行为准则」（README 中提到了一份五条的服务商行为 pact）。以上为推演，非事实。

06｜解决了什么真实问题？

从需求侧看，痛点是「品牌在 AI 眼里是透明的」：

  • 需求一（品牌方）。花了大钱做内容与公关，但顾客现在问 AI「哪个牌子好」，答案里可能压根没有你；更糟的是，你无法证明「做了之后有没有变好」。
  • 需求二（营销服务商）。客户问「GEO 到底怎么做、效果怎么衡量」，行业里拿不出一套可复现的度量——只能凭感觉汇报。
  • 需求三（买家侧的可信度）。如果 AI 的回答里混入了大量品牌自己灌的水，最终受损的是使用 AI 的人。所以「品牌用结构化方式声明事实 + 可审计」，对双方都有价值。
  • 共同点：不是「AI 不提我」，而是「没人知道 AI 为什么提我，也没人能证明我改了之后有没有用」。

09｜它到底是怎么实现的？

这个项目最值得拆的不是数据量，而是它把「度量」当成工程问题来解决的四个动作：

① 明确定义并解决「分数不稳定」。单次问 AI 得到的答案会漂。项目的应对是：固定问题面板 + 冻结引擎快照 + 字节级可复现打分。这三者合起来，把「一次问答」变成了「一次可重复的实验」。

② 区分「被提及」与「被推荐」。这是 GEO 评测里最容易被糊弄的地方——模型提到你的名字，不等于在推荐你（可能是反面举例）。项目用双裁判判定立场并公开一致性 kappa（0.909），等于把「主观判断」也纳入了可审计范围。

③ 统计上不打折扣。Wilson 置信区间回答的是「这么小的样本量，这个排名可信吗」；Bradley-Terry 排名回答的是「两两对比如何汇总成全局顺序」；改写鲁棒性回答的是「换个说法问，结果还稳吗」。这三条一起出现，说明作者是按评测集的标准在要求自己，而不是按「demo 能跑就行」。

④ 数据质量可逐行审计。1,497,628 个候选经五轮逐条目 AI 判定，剔除 46,883 个非组织实体（单场活动、个人、地点、列表页、虚构、网页与垃圾）；每一份判定文件都存档在仓库里，清洗规则是可读代码，并用 LEI 法人识别码交叉验证。作者还立了一条规矩：数字必须与来源一起引用，STATS-FULL.md 每次合并后从实时数据重新生成，是唯一权威统计口径。

12｜踩坑

以下为依据项目公开信息整理的提醒，本文未独立复现：

  • 数据规模是「项目自述」。你会在 README 不同位置看到略有差异的条目数（如正文写 1,542,995、Numbers 表写 1,542,575）。作者自己的规矩是「数字必须与来源一起引用」，并以 STATS-FULL.md 为权威——引用时应以该文件为准，而不是正文里的近似值。
  • 「分数」不等于「生意」。被 AI 提及度提高，与销量提升之间没有直接因果。这套工具度量的是可见度，不是商业结果。
  • 引擎是会变的。正因为会变，项目才用「冻结快照」——这意味着跨快照版本比较需要谨慎，否则会把引擎更新误读成品牌改进。
  • 仓库极新且单人维护。创建于窗口内（10-05），仅 1 个仓库的账号在维护；长期可持续性未经验证。
  • AI 参与制作的已知边界。作者已声明数据由 AI 逐条目判定 + 人工审核；但 AI 判定必然存在误判，46,883 条被剔除的实体中是否有个别误伤，外部无法核对全部。

13｜中国用户能不能直接做？

  • 国内访问：GitHub 直连不稳定；但项目自提供 eeo-local.html 单文件形态，下载一次后可离线使用，是比较友好的一点。
  • 注册：无需注册；密钥保存在浏览器本地。
  • API：要真正跑审计需要各家引擎的访问方式；只浏览数据不需要任何 Key。
  • 成本：软件免费；成本在引擎调用与人工复核时间。零依赖 Node 18+ 意味着不需要服务器也能跑单机版。
  • 技术门槛：普通用户可以试用（打开单文件网页）／有一定门槛（CLI 与评测流程）。

15｜中国企业可以怎么用？

  • 企业场景 1｜品牌 AI 可见度体检。用固定面板定期审计：顾客问「这类产品推荐哪个牌子」时，自家品牌出现频率与语境（被推荐还是被提及）。
  • 企业场景 2｜营销效果的新指标。把传统 SEO 报表加上「AI 可见度」一栏，作为内容投放的第四类效果指标。
  • 企业场景 3｜公开事实源建设。参考其认领机制，把公司基本信息以结构化方式发布并验证，让模型更容易正确引用你的事实。

16｜中国消费者可以怎么用？

  • 核对 AI 的推荐是否靠谱：用工具看看某个品类里，AI 到底提到了哪些品牌、依据是什么线索——有助于理解「AI 推荐」的局限。
  • 自己创业/开店：确认自家小店在 AI 眼里是否可见，以及该怎么描述自己的业务。
  • 做本地探店内容：用审计结果作为选题线索（「AI 眼里本地奶茶 TOP10 和我心里的差在哪」）。

17｜如何变成一个赚钱的项目？

产品化：做垂直行业的「AI 可见度月报」——例如只做餐饮、只做宠物、只做医美，按月交付固定面板的趋势报告。这是最直接可规模化的形态。

服务化：GEO 诊断 + 事实源建设服务：帮企业把品牌事实结构化并提交验证，再按月跟踪可见度变化。

咨询化：帮品牌重新组织内容策略——从「写给搜索引擎」转向「写给模型读」，这是一个正在成形的咨询需求。

培训化：《GEO 入门：当顾客开始问 AI「买哪个」》——面向品牌市场部，半天课就能讲清方法论。

内容化：「AI 眼中的奶茶品牌排行」这类选题天然有传播力（项目自己就用「奶茶」做了首个公开面板）。

02

用便宜 99% 的判定模型做论文筛选：dailypaper-skills 把「追论文」做成一条可固定成本的流水线

Agent Skill 包 AI + Research 成本工程 窗口内提交 10-05 14:39 / 14:46 Apache-2.0 成本对照为单次自测
一句话结论：它把「每天筛几篇论文」这件高频小事，拆成了「便宜的判定模型做初筛 + 贵的主模型做精读」——这是所有 Agent 流水线都该学的一次分工。

01｜案例是什么？

dailypaper-skills（Apache-2.0）是一套面向研究者的 Agent Skill 包：你说一句「今日论文推荐」，它会从 HuggingFace Daily/Trending 与 arXiv 发现论文、按你配置的研究兴趣筛选（默认关注大模型 RL、RL infra、世界模型/JEPA、灵巧手操作与物理仿真）、给出有态度有依据的分流（必读 / 值得看 / 可跳过），再对「必读」论文生成完整笔记（含公式、图表、概念链接），全部落进你自己的本地知识库（Obsidian 或普通 Markdown 目录）。它由 7 个 skill 组成，可装进 Claude Code、Codex、Cursor、GitHub Copilot、Gemini CLI、OpenCode、OpenClaw 等。最特别的一点是它明确做了一次成本工程：把高频的「主题相关性打分」交给一个便宜得多的判定模型（Jev），把贵的主模型留给点评与全文精读。

02｜为什么今天值得关注？

  • 窗口内的事实（可用 API 核实）：该仓库在 2026-10-05 14:39 与 14:46（北京时间）出现两次提交——「Initial commit: daily paper research skills」与「Merge daily paper skills with Jev scoring and product documentation」，均落在本期窗口内；README 中公布的 Jev 成本对照也明确标注为「2026-10-05 单次对照」。
  • 它给了两个具体数字：同一批 30 篇候选、两组都推荐 10 篇——GPT-6 Astra 约 $0.109264 / 10.35 秒，Jev 1.13.0 约 $0.000576408 / 0.52 秒；按官方标价折算费用降低 99.47%，两组入选重合 9/10。
  • 为什么以前不容易做：「AI 追论文」的常见做法是全部交给一个强模型——效果不错，但每天都在烧钱，且相关性打分这种「重复劳动」用贵模型是浪费。
  • 为什么值得花时间：它把一个通用的架构问题摆到了台面上：一条 Agent 流水线里，「判断相关性」和「生成内容」应该用不同的模型。这个分工思路可以套用到几乎任何高频 Agent 任务上（邮件分诊、工单分类、情报筛选……）。

03｜案例的前世今生

前世。「追论文」的第一阶段是订阅与手工：arXiv 邮件列表 + 关键词检索 + 自己判断。信息过载是常态，真正的问题不是「看不到」，而是「筛不动」。

发展。LLM 出现后，第二阶段是「把论文丢给聊天模型问它有没有用」。可行，但有两个问题：一是成本随论文量线性增长，二是模型越强、每次问「这篇跟我有关吗」越浪费。

今生。第三阶段出现了两个变化：① Agent Skills 让「一条研究工作流」可以被拆成可安装的包（抓取 / 点评 / 笔记各司其职）；② 判定模型这类「只输出概率分布、不生成文本」的小模型，让「高频判断」的成本降到可以忽略。dailypaper-skills 正是这两者的结合——并且它把成本对照做成了公开的、可复现的文档。

下一步可能怎么发展（分析 / 推演）。「贵模型做生成、便宜模型做判断」很可能成为 Agent 流水线的标准分工，就像数据库里「索引」与「存储」分工一样自然。进一步，这类判定模型还可能被用来做「质量门禁」——先由便宜模型把不合格的输出筛掉，再让贵的模型只处理值得处理的。以上为推演，非事实。

06｜解决了什么真实问题？

从需求侧看，痛点是「筛选成本」而非「获取成本」：

  • 需求一（研究者 / 研究生）。每天新增论文远超可读量，真正费时间的是判断「哪些和我的研究有关、哪些值得读全文」。而这件事每天都要做一遍。
  • 需求二（长期跟进者）。读了以后要留下什么。「读完就忘」是普遍状态，缺少从「读过」到「能复用」的链路。
  • 需求三（成本敏感的个人）。用强模型每天筛论文，一个月下来账单可观；而这类判断任务其实不需要强模型。
  • 共同点：不是「找不到论文」，而是「每天都得重新判断一遍，还留不下痕迹」。

09｜它到底是怎么实现的？

这个项目最值得学的是三层分工：

① 便宜的模型做高频判断，贵的模型做低频生成。相关性打分是每天都发生、每次都很「轻」的任务；点评与精读是低频但需要高质量的任务。把前者交给判定模型（Jev），后者留给宿主主模型，成本结构立刻改变。作者给的数据是：同样 30 篇候选取 10 篇，强模型 $0.109 / 10.35 秒，Jev $0.00058 / 0.52 秒，约 99.47% 的费用降幅、20 倍左右的速度差，入选重合 9/10。

② 用「不凑数」保护信噪比。README 明确写「默认每天最多 10 篇，相关论文不足时不凑数」——这是做信息产品的关键纪律。每天硬凑 10 篇只会让人取消订阅。

③ 把「笔记」做成可长期积累的结构。推荐页 → 论文笔记 → 概念库三层互相链接；「下次读到相似方法时，可以顺着链接找到已有积累」。同时支持从 Zotero 已有文献库出发，接入用户既有的阅读习惯而不是另起一套。

一条值得注意的诚实之处：作者在成本对照旁明确标注——「这是 2026-10-05 的单次评分测量，计入主模型缓存；不代表整个阅读流程的费用，也不是订阅账户实际扣款。重合率不等于人工质量评价。」这句话本身就是一个很好的工程声明范式。

Step 1（原文）。准备环境：一个能读写文件、执行命令、联网的 Agent，以及 Python 3.10+、Git、curl；PDF 文字与图片提取需要 Poppler（Obsidian 与 Zotero 都是可选）。

Step 8（本文补充的建议）。把它做成「只读不写」的检查习惯：先看推荐页的分流理由，只看你同意的那些，用一周时间验证它的判断是否合你的口味，再决定是否让它自动生成笔记。

12｜踩坑

以下均为项目 README / docs 自述或本文据其整理的提醒：

  • 成本对照是「单次测量」，不是月度账单。作者已明确标注：该数据为 2026-10-05 单次评分测量、计入主模型缓存、不代表整个阅读流程的费用、也不是账户实际扣款。不要把它当成「用这个方案每月只花几厘钱」。
  • 重合率不等于质量。9/10 的重合只说明两组选出的论文高度重叠，不代表推荐质量经过人工评估。
  • Jev 评分需要额外的 key。没有 TYPESAFE_API_KEY 就只能退回关键词筛选——效果会明显不同，这一点容易被忽略。
  • 环境依赖不可省。Python 3.10+、Git、curl 是必需；处理 PDF 还需 Poppler。纯聊天、无法读写文件或执行命令的客户端不能独立运行。
  • 不会自动每天运行。默认由你发起；需要定时得自己接系统调度，安装不会创建后台任务（Git 自动提交、推送默认关闭）。
  • 仓库的时间线需要注意。该仓库 created_at 显示为 2026-02-26，但窗口内出现了「Initial commit」与主分支合并提交（10-05 14:39 / 14:46），显示其历史在此期间发生过重建或重写。本文以窗口内提交作为收录依据，并如实标注这一点。

13｜中国用户能不能直接做？

  • 国内访问：GitHub 直连不稳定；运行时需要访问 arXiv 与 HuggingFace，这两处对国内网络也可能不稳定，是本案例最实际的门槛。
  • 注册：无账号体系；Jev 评分需额外的 API key。
  • API：需要 TYPESAFE_API_KEY（可用关键词模式绕过）；宿主 Agent 的模型由你自选，可换国产模型。
  • 成本：软件免费；成本 = 少量判定模型调用 + 主模型调用。这正是本案例要解决的问题（把高频判断的成本压下来）。
  • 技术门槛：有一定门槛 需要 Python 环境、命令行操作，以及能读写文件与联网的 Agent。

今日 AI 实战观察

10-06 这一天的两个案例，主题都是「造尺子」——一个量品牌的 AI 可见度，一个量论文与你的相关性。它们共同揭示了一个正在发生的变化：当 AI 开始替人做筛选，能定义「怎么衡量」的人就掌握了主动。

第一，GEO 正在从玄学变成可审计的工程。EEO 的难得之处不在于它有 154 万条品牌数据，而在于它回答了单次 AI 审计的两个致命质疑：分数不稳定（用冻结快照 + 固定面板解决）、把提及当成推荐（用双裁判立场判定 + 公开 kappa 解决）。当一个新兴服务品类有了这样的度量标准，它就具备了被采购、被验收的条件——这是「GEO 能不能成为一门正经生意」的关键一步。值得注意的是，它的 26 个引擎预设里有 11 个是中国本土引擎，说明这个方法论的需求在中国同样成立。

第二，「判断用便宜模型、生成用贵模型」是 Agent 流水线的通用分工。dailypaper-skills 给出的成本对照（$0.109 → $0.00058，约 20 倍速度差）虽然只是单次测量，但它指向的结构性问题是真的：每天都在发生的判断，不该由最强的模型来做。这条原则可以套用到邮件分诊、工单分类、情报筛选、线索评分——几乎所有企业级 Agent 场景。

第三，两个案例都选择了「公开方法与数据」而不是「藏起来卖服务」。EEO 把逐条判定文件存档在仓库里，dailypaper-skills 把成本基准连同「这是单次测量、不代表全流程费用」的说明一起公开。在一个「效果全靠一张嘴」的赛道里，可复现本身就是最强的主张。这也给做 AI 服务的中国团队一个提示：客户越来越不吃「我们效果很好」这套说法，他们要的是「你怎么量的、我能不能自己验一遍」。

第四，专业门槛正在被「流程化」抹平。品牌营销里的 GEO、学术研究里的文献筛选，过去都依赖资深人士的判断力。今天它们都被拆成了「固定面板 + 分流规则 + 结构化输出」——不是让外行变成专家，而是让专家的判断标准可以被复制。
