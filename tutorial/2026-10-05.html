01

自托管的 AI 盯盘系统 PanWatch：把九 Agent 研究团队装进自己的服务器，盯 A股 / 港股 / 美股并推送到飞书与企微

AI Agent AI + 金融 自托管 / MCP 窗口内 Release 0.17.3（10-04 19:28）与 0.17.4（10-04 23:48） 开源 MIT 投资类工具，非投资建议
一句话结论：它把「一个能自己跑来跑去的投研团队」做成了一个 Docker 容器——这是自托管 AI Agent 落地在金融场景里完成度相当高的一个样本。

01｜案例是什么？

PanWatch（盯盘侠）是一个自托管的 AI 选股与盯盘系统（MIT，Python）：一条 docker run 起在自己服务器上，然后在网页里建账号、配 AI 服务与通知渠道即可用。它同时覆盖 A股、港股、美股，核心是基于开源项目 TradingAgents 的「九 Agent 研究团队」——从一个持仓出发，让牛熊双方辩论、风险审查、最终给出 PM（组合经理）决策备忘录与完整推理链，并通过 Telegram、企业微信、钉钉、飞书、Bark 或 Webhook 在 3–5 分钟内推送到你的手机。此外还有定时 Agent（盘前 / 盘中 / 收盘）、组合式价格提醒、机会榜、模拟盘（Paper Trading）与 PWA 移动端。

02｜为什么今天值得关注？

  • 窗口内的事实（可用 API 核实）：在 2026-10-04 12:00 → 10-05 12:00（北京时间）内，项目发布了 0.17.3（10-04 19:28） 与 0.17.4（10-04 23:48） 两个版本，并有多次实质提交，包括「让 TradingAgents 深度分析的超时时间可配置」「保留已配置的超时并暴露 provider 错误」「加速多平台镜像构建」等。
  • 它解决的是一个具体痛点：做股票研究的复杂度不在「查到数据」，而在「把技术面、消息面、基本面、风险审查串成一条能解释的推理链」并持续盯住。人工做这件事成本极高，而云端产品又要求你把持仓数据交出去。
  • 为什么现在变得容易：① TradingAgents 这类多 Agent 投研框架开源了；② 国产模型（项目话题里就含 deepseek）让长推理链条的成本降下来；③ MCP 与 akshare 之类数据接口让「A股数据」可以合法低成本获取；④ Docker 让自托管变成一条命令。
  • 为什么值得花时间：这是极少数同时具备「中国本地市场覆盖 + 自托管数据主权 + 多 Agent 真实编排 + 通知渠道接地气」的 AI 金融开源项目。通知走飞书、企微、钉钉，这一点已经说明了它的目标用户是谁。

03｜案例的前世今生

前世。个人量化与盯盘的第一阶段是「写脚本 + 看 Excel」：用 tushare / akshare 拉数据、算指标、定阈值发提醒。这条路可靠但只能做机械判断，遇到「这条消息算利好还是利空」就无能为力。

发展。两件事接连发生：① LLM 让「读新闻、写研报、辩论多空」变得可能；② 多 Agent 编排框架（如 TradingAgents）把「研究员 → 辩论 → 风险审查 → 决策」这条流程做成了可复用的结构。与此同时，「自托管」的价值在数据敏感场景里被不断放大。

今生。PanWatch 做的是「把上述零件装成一个能长期运行的产品」：Web 界面、账号体系、多账户持仓管理、定时任务、通知渠道、移动端 PWA——这些「不性感」的工程恰恰是把 Demo 变成可用系统的那部分。窗口内的提交（超时可配置、provider 错误暴露、镜像构建加速）也说明它正处在「从能跑向跑得稳」的阶段。

下一步可能怎么发展（分析 / 推演）。这类系统的演进方向大概率是「更少的人工介入、更强的可解释性」：Agent 自己发现值得研究的标的、自动生成研究档案、并把「为什么这么判断」完整留痕。同时，随着合规要求收紧，它也可能走向「只做研究与提醒、不碰交易执行」。以上为推演，非事实。

06｜解决了什么真实问题？

从需求侧看，痛点是「研究成本」而非「信息获取」：

  • 需求一（个人投资者）。同时看 A股、港股、美股时，数据工具、新闻源、提醒渠道是三套系统；想给一只票做一次完整分析，需要手工查技术指标、翻新闻、再自己权衡多空——每次至少一小时。
  • 需求二（数据敏感用户）。把持仓交给云端 SaaS 意味着暴露自己的仓位与策略；自托管是这类用户的硬需求。
  • 需求三（想系统化的人）。需要的不只是「一个信号」，而是「这个结论是怎么推出来的」——推理链本身才是可学习、可复盘的东西。
  • 共同点：不是「看不到数据」，而是「没人帮我把它想清楚，还得天天想」。

08｜完整 Workflow

路径 A：一次深度研究（源自 README 的 demo 描述）

① 起点：一个持仓　从组合里的某只票出发
↓
② 九 Agent 研究团队启动　技术面 / 情绪面 / 新闻 / 基本面并行分析
↓
③ 多空辩论　看多方与看空方各自陈述，暴露分歧点
↓
④ 风险审查　对结论做风险复核
↓
⑤ PM 决策备忘录　给出结论 + 完整推理链
↓
⑥ 推送到手机　经飞书 / 企微 / 钉钉 / Telegram / Bark / Webhook，3–5 分钟内到达

路径 B：日常自动盯盘

① 定时 Agent 按交易所日历触发　盘前 / 盘中 / 收盘三个时点
↓
② 条件提醒判定　组合式条件（AND/OR）+ 冷却时间 + 每日上限 + 有效期，避免通知轰炸
↓
③ 机会榜更新　AI 打分排序，附入场位、目标位与风险上下文
↓
④ 模拟盘验证　按信号做模拟进出，跟踪净值曲线
↓
⑤ 推送与复盘　结果进手机；推理链留档，供事后复盘

09｜它到底是怎么实现的？

这个项目的技术价值在于四个「不性感但决定成败」的工程决定：

① 把「研究」做成有结构的 Agent 编排，而不是一次提问。九 Agent + 多空辩论 + 风险审查的结构，本质上是在用对抗换取推理质量——单一模型容易被一个叙事带跑，而被迫站在反方陈述会逼出分歧点。这是多 Agent 相比单 Agent 最实在的收益。

② 把「数据主权」当成产品前提。自托管 + 自配模型（可指向本地 Ollama）= 持仓与推理过程不出你的服务器。对金融场景，这不是加分项，是准入门槛。

③ 通知渠道做了本地化。飞书 / 企微 / 钉钉 / Bark 都在列表里，说明作者清楚「中国用户的手机通知入口在哪里」。这一点比多加十个指标更有价值。

④ 在「跑得稳」上持续投入。窗口内的提交——「让深度分析的超时时间可配置」「保留已配置的超时并暴露 provider 错误」「加速多平台镜像构建」——全都是典型的运维与可靠性工作。能把超时和 provider 错误当成一等公民的项目，通常已经在真实使用中出现过这些问题。

12｜踩坑

以下为依据项目公开信息整理的提醒，本文未独立复现：

  • 这是一款「研究辅助」工具，不是投资建议。九 Agent 的结论同样可能错，且错得很有说服力。任何把它当信号源直接下单的用法，风险自负。
  • 深度分析有时长。窗口内作者专门在修「超时时间可配置」「暴露 provider 错误」——说明长链条推理在弱网络或慢模型下容易超时；弱模型 + 长链条是最容易出问题的地方。
  • 数据源依赖第三方。A股数据依赖 akshare 一类接口，接口变更或限流会直接影响功能；交易日历判断也需要正确配置。
  • 自托管意味着你要自己运维。服务器安全、镜像更新、数据卷备份都归你——这既是它的优点（数据主权），也是它的成本。
  • 通知量需要节制。项目本身提供了冷却、每日上限与有效期，说明作者预期到「提醒过多会让人关掉它」；使用前应先把这些参数设好。

13｜中国用户能不能直接做？

  • 国内访问：GitHub 与 Docker Hub 直连不稳定，通常需要镜像加速。运行起来之后全部在本地，无境外依赖。
  • 注册：无需注册；首次访问时自己在网页里创建本地账号。
  • API：需要自备一个 OpenAI 兼容的模型服务——用 DeepSeek / 智谱 / 本地 Ollama 即可，不必用境外 API。
  • 成本：软件免费；成本主要是「服务器（或用你自己的机器）+ 模型调用」。本地 Ollama 可把模型成本压到接近零（代价是速度与质量）。
  • 技术门槛：有一定门槛 需要会跑 Docker、能配模型 API 与通知渠道；不需要 GPU（除非本地跑大模型）。

15｜中国企业可以怎么用？

  • 企业场景 1｜投研团队的研究加速器。分析师把「初筛 + 基本面速览 + 多空分歧点梳理」交给系统，自己聚焦在判断与决策上。
  • 企业场景 2｜私域数据不出内网。自托管 + 本地模型，让持仓与策略讨论留在公司内网，满足数据合规要求。
  • 企业场景 3｜培训与复盘素材。系统留存的推理链可作为投研新人的学习材料——「这个结论是怎么推出来的」比结论本身更有教学价值。

16｜中国消费者可以怎么用？

  • 个人盯盘：把自选股交给定时 Agent，收盘后收到一份带推理链的复盘，减少「盯盘焦虑」。
  • 学习投资逻辑：用模拟盘 + 推理链，理解多空双方各自的理由，而不是只看结论。
  • 管理多账户：把不同券商账户汇总成一个组合视图，看清真实仓位与盈亏。

17｜如何变成一个赚钱的项目？

产品化：不做通用盯盘，而做「某个细分策略的自托管研究助手」——例如专注红利股、专注港股通、专注行业轮动，卖的是内置的研究框架而非软件本身。

服务化：为企业做「投研 AI 助手」的私有化部署与调优服务（模型选型、提示词调优、数据接入、通知集成）。

咨询化：帮机构设计「AI 参与投研的边界」——哪些环节可以交给 Agent、哪些必须人工签字，这在强合规行业是刚需。

培训化：《用多 Agent 做投研初筛》——面向个人投资者与投研新人，重点教「怎么读推理链」。

内容化：拆解「九 Agent 如何辩论」本身极具传播性，适合公众号、B站、雪球。

19｜如果我是一个中国独立开发者（7 天 MVP）

  1. Day 1：Docker 起一套 PanWatch，配 DeepSeek + 飞书机器人，跑通一只自选股的深度分析。
  2. Day 2：把它限制到一个人群（建议：只做红利股 / 只做一只宽基成分股），砍掉多余功能。
  3. Day 3：把「推理链 → 一份结构化复盘」做成固定输出模板（这是最有价值的产物）。
  4. Day 4：找 3 位有真实持仓的朋友试用，问「哪一段推理链对你有用」。
  5. Day 5：按反馈收敛：只保留他们愿意每天看的那一份报告。

把 Codex 的独占生图能力接出来给任何 Agent 用：先给四个风格方向、你选定后再出图（MCP + CLI + Skill 三形态）

MCP 实战 Agent Skill AI + 内容设计 仓库创建 10-04 16:47；窗口内 Release v0.2.0 / v0.3.0 开源 MIT 依赖 Codex 生图，可能有账号门槛
一句话结论：它示范了一条很实用的路子——当一个好用的能力被锁在某个产品的界面里，就把它包成 MCP / CLI / Skill 三件套接出来。

01｜案例是什么？

中文开发者「向阳乔木」（joeseesun）开源了 乔木 Codex 生图（qiaomu-codex-imagegen，MIT）：Codex 的内置生图工具只在 Codex 里能用，这个项目把它接出来，做成一个 MCP 服务、一个命令行、一个 Agent Skill，三者共用同一套核心。于是 Claude Code、Codex、Cursor 或任何能执行命令的 Agent，都能「说一句『做一张小红书配图』就拿到图片文件」。它最有特色的不是生图本身，而是流程：每次生图会先给出至少四个机制不同的风格方向，你选定后再展开提示词、生成、并按验收条件自检。

02｜为什么今天值得关注？

  • 窗口内的事实（可用 API 核实）：该仓库创建于 2026-10-04T08:47:02Z（北京时间 10-04 16:47），当天 16:49 发布 v0.2.0、17:34 发布 v0.3.0，两次发布都落在本期窗口（10-04 12:00 → 10-05 12:00）内。

  • 为什么现在变得容易：MCP 成为事实标准后，「把一个能力包成工具挂给任意 Agent」有了统一插座；Skill 规范让「怎么用这个能力」也可以随能力一起分发。于是「能力搬运」从重工程变成了小工程。
  • 为什么值得花时间：它的价值不在生图，而在「能力封装」这一模式——中国有大量开发者正在做「把某个模型/工具的能力接到自己的工作流里」这件事，这个案例把标准答案展示了一遍，而且连「防止 AI 编造事实、乱写文字」的规则都写进去了。

03｜案例的前世今生

前世。设计素材生产的老路径是：找设计师排期 → 提需求 → 改稿 → 交付。AI 生图出现后，变成「自己写提示词抽卡」——快，但结果不可控，而且大多数人根本不知道该怎么描述风格。

发展。三件事逐步到位：① 生图质量跨过「能用」的临界点；② MCP / Skill 让「能力 + 用法」可以一起打包分发；③ 社区开始沉淀「提示词方法论」——不再靠玄学，而是按机制分类（文字主导、平面结构、摄影人物、产品近摄、材料空间等）。

今生。这个项目把三者结合起来，且解决了一个被普遍忽略的问题：用户不知道该要什么风格。它的做法是「先给四个机制不同的方向让你选，而不是直接抽一张」——把「抽卡」变成「选方案」。这也更接近真实的设计流程：先对齐方向，再出稿。

下一步可能怎么发展（分析 / 推演）。「能力搬运 + 方向先行」这套模式很可能复用到其他被锁住的能力上：把某个产品里的语音、视频、检索、分析能力分别包成 MCP，让 Agent 自由编排。同时，「先给方案再执行」也可能成为 Agent 与人类协作的默认礼仪——任何不可逆的操作，都该先给选项。以上为推演，非事实。

↓

↓
⑦ 交付　返回文件路径与像素尺寸

09｜它到底是怎么实现的？

这个案例最值得拆的是它把「设计流程」而不是「生图命令」做进了工具：

① 方向先行，对抗抽卡。suggest_directions 的关键约束是「至少四个机制不同的方向」。它防止的是「同一张图换个滤镜」——因为方向来自不同家族（文字主导 / 物象破框 / 纸雕与织物地貌 / 巨物微缩剧场 / Mondo 丝网印），出来的东西才有真正的选择价值。

② 把「验收」写进流程。compose_prompt 输出的不只是提示词，还有避免项与验收条件；生成后由 Agent 逐条核对，不合格只改对应那一句。这是把设计师的「改稿」动作结构化了——避免「整个重来」。

③ 用 JSON 留存提示词，让系列化成为可能。每张图旁边留一份 JSON 记录实际提示词，意味着「同系列再做十张」是有依据的，而不是重新抽卡。

④ 一套核心、三种外壳。MCP / CLI / Skill 三形态共用核心，这是一个很成熟的工程决定：MCP 面向「能被 Agent 调用」，CLI 面向「能被脚本调用」，Skill 面向「能被 Agent 理解怎么用」。同能力多入口，而不是多份实现。

Step 4（原文）。选定方向后由 compose_prompt 展开提示词并生成；若你已指定风格（如「用 Mondo 风格」「T03」）或直接说「直接出」，会跳过选择步骤。

产品化：做「垂直行业的视觉素材工厂」——例如只服务电商，内置类目化的方向库与平台预设，卖的是「出图即合规可用」。

服务化：帮企业把品牌规范封装成一套「风格锁 + 验收条件」，交付后按季度维护。

咨询化：帮品牌解决「AI 出图风格不稳定」的问题，本质是把设计规范翻译成可执行的提示词约束。

  3. Day 3：为这个预设写 6 个机制不同的方向模板（不是 6 个滤镜）。
  4. Day 4：找 3 位电商/自媒体朋友试用，看他们选方向的偏好。
  5. Day 5：补上「验收条件」（尺寸、留白、主体位置），减少返工。
  6. Day 6：做一个极简界面或 MCP 服务，让不会写提示词的人也能用。
  7. Day 7：定一个按张/按月的价格，先用一个小众类目（如零食、宠物）验证。

今日 AI 实战观察

10-05 这一天的两个案例，指向同一个趋势：能力正在从产品里被「拆出来」。

第一，自托管正在成为 AI Agent 落地的重要形态。PanWatch 用一条 docker run 把「九 Agent 研究团队 + 定时任务 + 多账户持仓 + 通知渠道」装进用户自己的服务器。它满足的是中国用户最实际的两个诉求：数据不出门和通知进手机（飞书、企微、钉钉）。这也解释了为什么它能把 ★2,040 拿到手——它不是 Demo，是一个能长期跑的系统。

第二，多 Agent 的真正价值是「对抗」而非「分工」。PanWatch 的九 Agent 结构里最关键的一环是多空辩论。分工只提升速度，对抗才提升质量——被迫站在反方陈述，会逼出单模型容易忽略的反面证据。这条经验可以直接迁移到任何高风险决策场景。

第三，MCP 正在从「协议」变成「能力搬运工具」。案例 02 做的事很直白：Codex 的生图只在 Codex 里能用，那就把它包成 MCP / CLI / Skill 三件套接出来。这说明 MCP 的实际价值不只是「让 Agent 能调工具」，而是让「能力」和「界面」解耦——能力可以脱离它出生的产品，被任何 Agent 编排。

第四，「先给方案再执行」正在成为 Agent 交互的默认礼仪。案例 02 的「四个方向先给你选」、案例 01 的「先说清推理链再给结论」，本质上是同一个原则：对不可逆、有偏好的动作，先给选项而不是直接做。这比「模型更强」更能决定用户是否信任一个 Agent 系统。

合起来看，今天两个案例提示的是同一件事：AI 落地的竞争点，正在从「谁的能力强」转向「谁的能力能被安全、可控、本地化地使用」。
