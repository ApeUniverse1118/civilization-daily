用 AI 编程工具做 4K 产品宣传片：把「写脚本→截图→卡点→配音校验」整条工序写成 AI 能执行的规范

AI + 内容生产 Agent Skill Remotion 完整 Workflow 首次开源 2026-10-09 257★ / 44 Fork
一句话结论：过去外包一支产品宣传片要几千到上万元，这个项目把制作流程写成一份 AI 能读懂、能执行的作业规范——它证明「营销物料」是可以被标准化交付的第一类创意工作。

01｜案例是什么？

ai-promo-video-maker 是一个开源项目（同时是一个 Agent Skill）。你对 Cursor、Claude Code、Codex 这类 AI 编程工具说一句话——「帮我给 https://example.com 做一支宣传片」——它会自己完成剩下的活：先花几分钟调研你的产品，然后分两轮向你提问（画幅时长、目标受众、风格方向、开场方式、配乐、截图来源），每个问题都附一个针对你产品的推荐项和理由；接着提出 3–4 个差异明显的风格方向并各画一张样帧给你挑；确认后自动完成深度调研、4K 真实页面截图、按音乐节拍卡点剪辑、配音与混音、逐张截图审查，最后交付一支 4K 商业宣传视频和一个可以直接部署的网页播放版。全程你只在三处参与：拍板需求、试听配乐与音色、登录需要截图的网站。

02｜为什么今天值得关注？

  • 为什么是现在：2026-10-09 首次开源（单次提交即全部上线），到 10-14 数据快照时已 257★ / 44 Fork，且是本期窗口内中国作者项目中星标最高者之一。它不是 Demo，README 里直接附了 5 支已完成成片（编程导航、面试鸭、鱼皮 AI 导航、Claude Fable 5.5、Vibe Coding 教程），每支都经历过数轮真实修改意见。
  • 以前为什么不容易做：「让 AI 生成一段视频」早就可行，难的是做出让人愿意看完的片子。三个死结：① 画面不真实（全靠生成图，看不出产品）；② 节奏没有判断标准（同一支片子会同时收到「太快」和「太慢」两种反馈）；③ AI 听不到声音，无法自查配音是否读错字、是否被音乐盖住。
  • 为什么现在变得容易：① 用代码画视频的框架（Remotion）成熟，画面可精确控制到帧；② 截图可以脚本化（Playwright 直出 3840×2160）；③ 语音可以转写回文字做比对校验（把「听」变成「读」）；④ Agent 能读一整个目录的规范文件并长时间遵守，才有「把工序写进 AGENTS.md」这条路线成立。

03｜案例的前世今生

前世。产品宣传片长期是个「要么花钱、要么花时间」的活：外包一支通常几千到上万元，自己做则要跨过脚本、素材、设计、剪辑、配音五道工序，每一道都有专业软件。此后 AI 出现，第一波解法是「用一个模型直接生成视频」——但生成模型做不出真实的产品界面，做出来的片子千篇一律，且无法保证品牌名读对、价格没写错。

发展。第二波解法转向「用代码生成视频」：Remotion 让画面可以用 React 组件描述，于是「按数据渲染一支视频」成为可能。再往后 Agent 编程工具普及，出现「把制作 SOP 写成文档、交给 Agent 执行」的路线。作者在 README 里记录的演进痕迹很清楚：早期片子曾同时收到「太快，看不过来」和「太慢，看着拖沓」两种相反反馈，于是才在规范里定下量化底线；鱼皮 AI 导航那支片子改了 5 轮，才总结出「配乐要先让用户试听」「截图必须保持原比例」「品牌名要逐字校验读音」三条规则。

今生。2026-10-09，作者把这一整套规范开源：AGENTS.md（核心工作规范）+ template/（Remotion 工程与全套脚本）+ references/（需求问询、风格菜单、素材获取、配乐卡点、配音、校验清单、60 多条真实踩坑记录、案例复盘）+ 5 支成片作为可检验的产出证据。关键在于这些规则不是设计出来的，是踩坑踩出来的——每一轮真实修改意见都被提炼进规范，下一个项目开工前 AI 会先把这些经验读一遍。

下一步可能怎么发展（以下为分析 / 推演，非事实）：① 从「营销物料」扩到「产品更新日志视频」「发布会预演」，成为产品团队的常规产出物；② 与 CI 打通，每次发版自动生成一支更新说明片；③ 规范本身成为可交易的资产（行业化的 style pack / 校验清单）；④ 出现「宣传片代做」的标准化服务。

06｜解决了什么真实问题？

从需求方视角看，问题从来不是「AI 能不能生成视频」，而是：「我要给产品做一支能发出去的片子，怎么在不请外包、不学剪辑软件的前提下做完，而且不要做出来丢人。」

  • 成本痛点：外包一支宣传片常需数千至万元级（README 自述「几千甚至上万元」，未给具体报价来源）；自己做则要学整套专业软件。
  • 质量痛点：AI 生成的片子往往「一眼假」——画面全是生成图，没有真实产品；风格千篇一律的深色科技风；品牌名读错、网址念错。
  • 流程痛点：不知道从哪开始、不知道什么时候算做完。本项目用「10 个阶段 + 每一步的闸门」把这个不确定过程变成有清晰验收点的流程。

↓

09｜它到底是怎么实现的？

让这套东西「真的能工作」的，是几条把主观判断转成可执行检查的设计：

  • 真实产品才是主角（可量化）：规范要求每个功能段落至少一张真实界面截图或作品图，全片不少于 8 张，还要有一段由 8 张以上真实作品组成的快速蒙太奇。AI 生成的图片和代码绘制的画面只负责包装与转场——这一条直接掐死了「一眼假」。
  • 节奏有明确标准（可量化）：快切镜头至少停留 0.65 秒、网址至少停留 3 秒（保证字幕能读完）；开场 3 秒内必须出现痛点或亮点、任何时刻往后 2 秒内必须有新信息（保证不拖沓）。这两条正是「太快 / 太慢」两种相反反馈的产物。
  • 声音靠数据校验（把「听」变成「读」）：AI 听不到声音，所以旁白生成后逐句转写回文字与稿子比对，品牌名和网址错一个字即判定不合格；混音完成后再把整段成品转写一遍，确认每句旁白都没被音乐盖住。即便如此，配乐和音色最终仍需用户亲耳试听。
  • 每一步都有闸门（fail-closed）：渲染前检查缺失文件、分辨率过低的图片、字体缺字；渲染后检查成片规格、渲染日志报错、整体响度，并按场景截图对照校验清单逐张审查，直到全部通过才交付。
  • 经验可累积：references/踩坑记录.md 收录 60 多条真实踩过的坑，references/案例复盘.md 记录每支片子收到的修改意见与解决办法；下个项目开工前 AI 先读一遍——这让「规范质量」随时间单调提升。

12｜踩坑

作者把踩坑直接写进了仓库，以下为公开内容整理：

坑 1 · 节奏的两难。同时收到「太快，看不过来」和「太慢，看着拖沓」两种相反反馈。→ 解法：定下两组量化底线，一条保字幕可读（0.65 秒 / 3 秒），一条保信息密度（3 秒内出痛点、后 2 秒必有新信息）。
坑 2 · 配音错误无法自查。AI 听不到声音，品牌名可能被读错。→ 解法：逐句转写回文字与稿子比对，错一字即不合格；混音后再整段复检一次。
坑 3 · 截图比例被破坏。（来自鱼皮 AI 导航那支片子第 5 轮修改）→ 解法：把「截图必须保持原比例」写成规范条款。
坑 4 · 配乐不能由 AI 直接决定。→ 解法：定「配乐要先让用户试听」为强制环节——AI 可以生成与初筛，但不能替用户拍板听感。
已知限制（作者公开）：① 项目主要在 macOS 上打磨，Windows / Linux 上字体会自动改用微软雅黑或 Noto Sans CJK，遇到问题需提 Issue；② 渲染耗时较长，4K 成片按画面复杂度一般需 4–18 分钟；③ Remotion 授权红线——个人和 3 人以内公司免费，更大团队须购买公司授权；④ ElevenLabs 免费套餐生成的内容不能商用，按分镜作曲需要付费套餐。

15｜中国企业可以怎么用？

17｜如何变成一个赚钱的项目？

01｜案例是什么？

SoloMCN 是一个跑在本机的短视频运营工作台。它把内容生产的每个环节都写成一份中文的 Claude Code 技能（相当于「岗位说明」）：curate-topics（精选选题）、account-ideas（按账号出题）、research-topic（调研，带出处）、write-script（分镜脚本）、precheck-content（预审）、make-video（出片）、revise-video（改片）、review-data（复盘）。它以国内热榜（抖音、微博、B站、知乎、百度、头条）和推特为上游，输出可以一键发布到 抖音、小红书、B站、YouTube、推特。工作台本身只做两件事：给 Claude 递工具（读写账号和素材、截网页、发布），以及给用户留看得见、拍得了板的地方。真正干活的是 Claude Code。

02｜为什么今天值得关注？

  • 为什么是现在：2026-10-09 首次开源（北京 22:01），窗口内持续提交。它代表了一条与「Dify / n8n 式拖拽编排」正面对立的技术路线，而这个对立在 2026 年下半年才第一次变得可讨论——因为模型终于能长时间自主完成一串复杂任务。
  • 以前为什么不容易做：过去做 AI 应用要先搭工作流：拖节点、连线、把每一步的提示词写死。这套做法的隐含代价是——流程搭成什么样，AI 就只能做到什么样。遇到流程没写到的分支就卡住；要改流程就得改节点、改代码；想提升能力只能等每个能力都换更强的模型。
  • 为什么现在变得容易：Agent 编程工具引入了「技能（Skill）」这种形态——一个文件夹 + 一份入口 Markdown。于是「改流程」从「改节点改代码」降级成「改一段中文文字」，而「能力上限」直接等于模型上限：模型升级，整套系统自动变强。

03｜案例的前世今生

前世。短视频账号运营是一个典型的人力密集型生意：一个人很难同时做选题、调研、写稿、剪辑、配封面、发五个平台。行业解法是两条：一是招人（成本高），二是买工具（各平台发布工具、混剪工具、选题工具各买一个，但仍需人工串起来）。AI 出现后的第三代解法是「用一个自动化平台把所有工具串起来」，也就是工作流编排。

发展。工作流编排在 2024–2025 年成为主流，但它有个天花板：编排的复杂度会随业务复杂度指数上升，而真实内容生产充满了异常（配音额度用完、某个平台改规则、素材下载失败）。用作者的话说，「流程没写到的分支就卡住」。2026 年 Agent 编程工具普及后，出现了另一种可能：不预定义流程，只定义岗位职责，让 Agent 在遇到异常时自己判断、换方案、重试。

今生。2026-10-09，作者把这套做法开源。README 里最有说服力的不是架构图，而是三个「真实发生过的」细节：① 做演示视频时托管配音的免费额度用完，没有任何人写过这个分支，Claude 自己装好本地语音，给鹦鹉、乌龟、狮子三个角色各配了一个声音把片子做完；② 作者在工作台写了一句「配音听不懂，换成系统中文语音」，Claude 只重配声音、重新对齐字幕、重新渲染，画面一帧没动，10 分钟交回新版；③ 片中的角色是 Claude 画的原创矢量图，穿插的 GitHub 页面、新闻报道、学者博客是它调研时自己截下来的真网页，还加了荧光笔高亮和红圈。

下一步可能怎么发展（以下为分析 / 推演，非事实）：作者的路线图已写明方向——把每个环节做成可配置的「员工」（素材员、选题编辑、编剧、剪辑、运营），各有岗位说明、工作方向和预算，员工之间用工单协作；再加定时自动跑、各平台数据自动回收形成复盘闭环、扩到快手 / 视频号 / TikTok。

06｜解决了什么真实问题？

从运营者视角，问题非常具体：「我一个人想做几个账号，能不能不招人、不买一堆工具、不写死流程，把从选题到发布整条链跑起来？」

  • 人力痛点：「一个人就是一个 MCN」——多账号、每账号多系列，人群、风格、配音、视觉按系列配置，账号之间不撞车。这是团队才做得成的事。
  • 工具碎片化痛点：选题工具、剪辑工具、发布工具各买一个，数据不互通，仍需人工串接。本项目把它们收进一个本机工作台。
  • 调研失真痛点：AI 写稿容易编造。作者的处理方式是「调研有出处」——写脚本前先上网查真实的价格、能力、步骤和反方观点，每条都有来源；技能里只保留一条红线：不编造事实、数据和真人言论。
  • 「流程僵化」痛点：这是本案例最核心的痛点——传统工作流遇到没预设的异常就卡死，而内容生产恰恰充满异常。

09｜它到底是怎么实现的？

作者的实现思路可以概括成一句：工作台只做「递工具」和「留拍板处」，把判断权全部交给模型。具体分三层：

  • 工具层（MCP）：server/mcp.js 把「读账号和素材、写精选、存脚本、截网页」等能力封装成工具递给 Claude。这是工作台真正干的活——给模型一双手。
  • 岗位层（Skills）：每个环节一份 Markdown 岗位说明。关键差别在于写法——不是「第 1 步做 A、第 2 步做 B」的死流程，而是「你是选题编辑，你的判断标准是……」。规范写的是判断标准，不是执行步骤，所以模型遇到没写到的分支时仍有依据可循。
  • 执行层（Agent 循环）：server/agent.js 在后台调起 claude -p 跑技能，实时把每一步转发到页面上，跑到一半用户还能插话。这是可审计性的来源——不是黑盒跑完给结果，而是过程可见、可打断。

几个值得注意的工程细节：

  • B站素材链路：调研时可从 B站搜视频、按弹幕找高能时刻、把整首直拍剪下来当素材；做视频时把同一首歌的多个场次按音轨对齐、踩拍切换，做成「一键换装」或舞台混剪。扫码登录一个小号即可下到 1080P。
  • 爆款拆解：YouTube 视频点「拆解」，Claude 读字幕、简介和热门评论，写出它为什么火、结构怎么排、开头钩子是什么、评论区在争什么、哪些能借哪些不能碰；产出的是换人群、换角度的原创选题，稿子和画面都自己做。
  • 「看」本机视频：server/watch.js 通过对已有视频抽帧拼图 + 语音转文字，让 Claude 先「看」一遍现成视频，再写各平台文案。
  • 技能是你的本地数据：仓库里只有出厂版本 defaults/skills/，首次启动复制到 .claude/skills/，之后怎么改都不进代码仓库；出厂版本更新时，没改过的直接换上，改过的逐个文件三方合并，合不上的交给 Claude 合并并等用户确认。这是一个相当成熟的分支管理设计。

平台依赖风险。项目深度绑定 Claude Code 与 macOS：Claude 订阅为强依赖，快速开始路径仅给出 Mac 安装方案。若你的环境不满足，需要自行改造（困难度未评估）。

今日 AI 实战观察

把今天这两个案例放在一起，会看到一个非常清晰的对照：同样是「用 AI 做内容」，一个人选择了把流程写死到每一步，另一个人选择了干脆不写流程。

ai-promo-video-maker 走的是「重规范」路线。它的 10 个阶段里，每一步都有闸门：渲染前查缺失文件、低分辨率图、字体缺字；渲染后查规格、日志报错、响度，再逐张截图对照清单审查。更关键的是它把主观判断翻译成了数字——快切镜头至少 0.65 秒、网址至少 3 秒、开场 3 秒内必须出痛点、任何时刻后 2 秒必有新信息、全片不少于 8 张真实截图。这些数字全是从真实返工里提炼的。它还解决了一个很本质的问题：AI 听不到声音，那就把「听」变成「读」——旁白逐句转写回文字比对，品牌名错一个字即不合格。

SoloMCN 走的是完全相反的路线。它不定义步骤，只定义岗位；不预判分支，让 Claude 遇到异常自己判断。README 里那个例子最能说明问题：配音额度用完，没人写过这个分支，Claude 自己装好本地语音给三个角色配音把片子做完——这在任何工作流编排里都是「未覆盖场景」，在岗位说明里却是「岗位职责之内」。

两条路线没有对错，它们的分界很清楚：任务越确定、对可证明性要求越高，越应该重规范；任务越依赖临场判断、异常越多，越应该放权给模型。宣传片有明确的验收标准（尺寸、响度、字幕停留时间），所以适合写死；短视频运营的每一天都不一样，所以适合放权。

对个人开发者来说，今天真正值得带走的是一个判断：不要再问「我该用哪个工作流平台」，先问「我这件事的异常多不多」。答案会直接决定你该把时间花在写规范上，还是花在写岗位上。

  • 可能商业模式：一次交付 + 按季度迭代（因为平台规则会变）
  • 关键风险：多平台自动发布涉及平台条款与账号安全，交付时应默认采用「人工预审 + 手动发布」形态，不把风险转嫁给客户
